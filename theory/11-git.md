Почти все «страшные» ситуации в Git (потерял коммит, сломал историю, конфликт при rebase) становятся простыми, если понять одну модель: **коммиты неизменяемы и связаны в граф, а ветки — это просто подвижные указатели на коммиты**. Первая глава объясняет эту модель, остальные применяют её к слиянию, отмене изменений, переписыванию истории и командной работе.

## Как устроен Git: объекты, коммиты, ветки и HEAD
id: model

> **Суть:** Git хранит **снимки** проекта, а не разницу между версиями. Каждый коммит — неизменяемый объект с хешем, указывающий на снимок файлов и на родительский коммит. **Ветка** — файл с хешем одного коммита, **HEAD** — указатель на текущую ветку. Изменения проходят три области: рабочий каталог → индекс (staging) → репозиторий.

### Объекты

Всё в `.git/objects` — объекты, адресуемые хешем содержимого (SHA-1, в новых репозиториях возможен SHA-256):
- **blob** — содержимое файла (без имени);
- **tree** — каталог: имена, права и ссылки на blob и вложенные tree;
- **commit** — ссылка на корневой tree (снимок всего проекта), ссылки на **родителей**, автор, коммиттер, время, сообщение;
- **tag** (аннотированный) — именованная ссылка на коммит с сообщением и подписью.

Следствия:
- изменить коммит **нельзя**: любое изменение даёт новый хеш, значит, новый коммит. «Переписывание истории» — это создание **новых** коммитов;
- одинаковые файлы хранятся один раз;
- хеш коммита зависит от всей истории до него — целостность проверяется автоматически.

### Ветки, теги и HEAD

- **Ветка** — подвижный указатель: файл `.git/refs/heads/main` с хешем коммита. Новый коммит в ветке → указатель сдвигается на него. Создать ветку — записать 41 байт, поэтому ветки дешёвые.
- **Тег** — неподвижный указатель на коммит (релизы).
- **HEAD** — «где я сейчас»: обычно указывает на ветку (`ref: refs/heads/main`). **Detached HEAD** — HEAD указывает прямо на коммит (после `git checkout <hash>`): новые коммиты не принадлежат ни одной ветке и легко теряются.
- **Удалённые ветки** (`origin/main`) — локальная копия того, где была ветка на сервере при последнем `fetch`.

```
A ← B ← C ← D        main, HEAD → main
         ↖
          E ← F      feature
```

### Три области

| Область | Что | Команды |
|---|---|---|
| Рабочий каталог | файлы, которые вы редактируете | редактор |
| **Индекс** (staging area) | снимок, который войдёт в следующий коммит | `git add`, `git restore --staged` |
| Репозиторий | коммиты | `git commit` |

Индекс позволяет собирать коммит по частям: `git add -p` — добавить только часть изменений файла.

### Работа с удалённым репозиторием

- `git fetch` — скачать новые коммиты и обновить `origin/*`, **не трогая** ваши ветки;
- `git pull` = `fetch` + `merge` (или `rebase` при `pull.rebase=true`);
- `git push` — отправить коммиты и сдвинуть ветку на сервере; отклоняется, если на сервере есть коммиты, которых нет у вас (не fast-forward);
- `git push --force-with-lease` — безопаснее, чем `--force`: перезапишет ветку, только если на сервере она там, где вы ожидаете (не затрёт чужие коммиты).

### Reflog

Git записывает каждое перемещение HEAD и веток в **reflog** — локальный журнал. Это страховка: коммит, на который не указывает ни одна ветка, не исчезает сразу, его можно найти в reflog (подробнее — [Отмена изменений](#/theory/git/undo)). Недостижимые объекты удаляются сборщиком мусора (`git gc`) только через некоторое время (по умолчанию reflog хранится 90 дней, для недостижимых записей — 30).

## Слияние и перебазирование, конфликты
id: merge-rebase

> **Суть:** **merge** объединяет ветки, создавая коммит слияния с двумя родителями, и сохраняет историю как была. **rebase** переносит ваши коммиты поверх другой ветки, создавая их **новые копии**, и даёт линейную историю. Золотое правило: **не делать rebase коммитов, которые уже опубликованы и используются другими**.

### Merge

```
до:    A ← B ← C            main
            ↖
             D ← E          feature

git switch main && git merge feature

после: A ← B ← C ← M        main   (M — коммит слияния, родители C и E)
            ↖     ↙
             D ← E          feature
```
- **Fast-forward**: если в main не было новых коммитов, Git просто сдвигает указатель — коммит слияния не нужен. `--no-ff` создаёт его принудительно (видно, что работа велась в ветке).
- **Squash merge**: все коммиты ветки сжимаются в один новый коммит в main. Чистая история main, но теряются промежуточные коммиты, а ветка Git не считается слитой.

### Rebase

```
git switch feature && git rebase main

после: A ← B ← C            main
                 ↖
                  D' ← E'   feature   (D', E' — новые коммиты с другими хешами)
```
Git берёт изменения каждого вашего коммита и применяет заново поверх `main`. Затем `main` можно fast-forward на `E'`.

**Интерактивный rebase** — редактирование своей истории перед публикацией:
```bash
git rebase -i HEAD~5      # pick, reword, squash, fixup, drop, edit, изменить порядок
git commit --fixup=<hash> && git rebase -i --autosquash main
```

### Что выбрать

| | Merge | Rebase |
|---|---|---|
| История | правдивая, с ветвлениями | линейная, «как будто писали последовательно» |
| Хеши коммитов | сохраняются | **меняются** |
| Безопасность для общих веток | безопасно | **опасно** для опубликованных коммитов |
| Конфликты | разрешаются один раз | могут возникать на каждом переносимом коммите |
| Отмена | `git revert -m 1 <merge>` | сложнее |

Типичная практика:
- **rebase своей локальной или личной ветки** на свежий main перед MR (`git pull --rebase`) — чистая история без лишних коммитов «Merge branch main into feature»;
- **слияние в main** — merge-коммитом или squash, по договорённости команды;
- **никогда** не rebase общих веток (`main`, `release`), которые уже есть у других: их локальные копии разойдутся с вашей переписанной историей.

### Конфликты

Конфликт — оба изменения затронули одни и те же строки (или один удалил файл, а другой изменил). Git останавливается и размечает файл:
```
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature
```
Порядок:
1. `git status` — какие файлы в конфликте.
2. Отредактировать: выбрать или объединить смысл обоих изменений (не просто удалить маркеры!), при необходимости обсудить с автором другого изменения.
3. `git add <файл>`.
4. Продолжить: `git commit` (merge) или `git rebase --continue` (rebase). Передумали — `git merge --abort` / `git rebase --abort`.
5. Прогнать тесты: «разрешённый» конфликт может давать некомпилируемый или неверный код.

Помощь: `git mergetool`, `git diff` во время конфликта, `git checkout --ours/--theirs <file>` (при rebase «ours» и «theirs» меняются местами!), `git config rerere.enabled true` — запоминать разрешения повторяющихся конфликтов.

Как конфликтов меньше: маленькие короткоживущие ветки, частая синхронизация с main, договорённости о форматировании (автоформатер), разделение больших файлов.

## Отмена изменений: restore, reset, revert, reflog, stash, cherry-pick
id: undo

> **Суть:** способ отмены зависит от того, **где** изменения и **опубликованы** ли они. Незакоммиченное — `restore`. Свои локальные коммиты — `reset`. Опубликованные коммиты — только `revert` (новый коммит, отменяющий старый). Потерянный коммит почти всегда находится через `reflog`.

### Карта отмены

| Ситуация | Команда |
|---|---|
| отменить правки файла в рабочем каталоге | `git restore file` |
| убрать файл из индекса (оставив правки) | `git restore --staged file` |
| исправить последний (неопубликованный) коммит | `git commit --amend` |
| убрать последние локальные коммиты, оставив изменения | `git reset --soft HEAD~2` или `--mixed` |
| выбросить последние локальные коммиты вместе с изменениями | `git reset --hard HEAD~2` |
| отменить **опубликованный** коммит | `git revert <hash>` |
| вернуть потерянный коммит | `git reflog` → `git branch rescue <hash>` |

### reset

`git reset <commit>` перемещает **текущую ветку** на указанный коммит. Режимы определяют, что происходит с индексом и рабочим каталогом:

| Режим | Ветка | Индекс | Рабочий каталог |
|---|---|---|---|
| `--soft` | перемещается | без изменений (изменения «отменённых» коммитов остаются подготовленными) | без изменений |
| `--mixed` (по умолчанию) | перемещается | сбрасывается | без изменений (изменения остаются в файлах) |
| `--hard` | перемещается | сбрасывается | **сбрасывается — незакоммиченные изменения потеряны** |

`reset` **переписывает историю** ветки. Если коммиты уже запушены, придётся делать force push, и у коллег история разойдётся. Поэтому для общих веток — `revert`.

Важно: `reset --hard` уничтожает **незакоммиченные** изменения безвозвратно (их нет в reflog). Закоммиченное же можно вернуть.

### revert

`git revert <hash>` создаёт **новый** коммит с обратными изменениями. История не переписывается — безопасно для общих веток.
- Откатить коммит слияния: `git revert -m 1 <merge-hash>` (`-m 1` — относительно первого родителя, т.е. main). Ловушка: после revert слияния повторное слияние той же ветки не принесёт её старые коммиты (Git считает их уже слитыми) — нужно сделать revert самого revert-коммита.
- Откатить несколько: `git revert A..B` или `--no-commit` и один общий коммит.

### Восстановить потерянный коммит после `reset --hard`

```bash
git reflog
# 3f2a1c9 HEAD@{0}: reset: moving to HEAD~3
# 8b7e6d5 HEAD@{1}: commit: add payment retries     ← вот он
git branch rescue 8b7e6d5        # или git reset --hard 8b7e6d5
```
Так же возвращают удалённую ветку (найти последний коммит ветки в reflog) и результат неудачного rebase (`git reset --hard HEAD@{N}` или `ORIG_HEAD` сразу после операции). Если reflog недоступен (другой клон) — `git fsck --lost-found` ищет недостижимые коммиты.

Ограничения: reflog **локальный** (не передаётся при push и clone) и хранится ограниченное время.

### stash

Временно убрать незакоммиченные изменения, чтобы переключиться на другую задачу:
```bash
git stash push -m "wip: retries"     # -u — включить неотслеживаемые файлы
git stash list
git stash pop                         # вернуть и удалить из stash (apply — без удаления)
git stash show -p stash@{1}
git stash branch new-branch stash@{0} # создать ветку из stash (если pop даёт конфликты)
```
Stash — для коротких перерывов. Для долгой работы лучше WIP-коммит в ветке или `git worktree` (второй рабочий каталог для другой ветки).

### cherry-pick

`git cherry-pick <hash>` — применить изменения конкретного коммита к текущей ветке (создаётся новый коммит с другим хешем).
- Применение: перенести исправление из main в ветку релиза (**backport**), забрать нужный коммит из чужой ветки.
- `-x` добавляет в сообщение ссылку на исходный коммит — удобно отслеживать бэкпорты.
- Минусы: дубли изменений в истории с разными хешами, возможные конфликты при последующем слиянии веток. Не замена нормальному слиянию.

## Поиск по истории и её переписывание: bisect, удаление секретов и больших файлов
id: history-rewrite

> **Суть:** **git bisect** бинарным поиском находит коммит, который внёс баг, за log₂(N) шагов. Удалить секрет или большой файл из **всей** истории можно только переписыванием истории (`git filter-repo`) — но секрет, попавший в публичный репозиторий, нужно в первую очередь **отозвать**, потому что копии уже могли разойтись.

### git bisect

```bash
git bisect start
git bisect bad                 # текущий коммит сломан
git bisect good v1.4.0         # здесь всё работало
# Git переключается на середину; проверяем и говорим:
git bisect good    # или: git bisect bad
# ... повторять, пока Git не назовёт первый плохой коммит
git bisect reset
```
Среди 1000 коммитов нужно около 10 проверок.

Автоматически, если есть скрипт проверки (код 0 — хороший, 1–127 — плохой, 125 — пропустить, например, не собирается):
```bash
git bisect run ./test-regression.sh
```
Удобство bisect зависит от истории: маленькие атомарные коммиты, каждый из которых собирается и проходит тесты. Огромный squash-коммит bisect найдёт, но не скажет, какая из 50 правок виновата.

### В репозиторий попал секрет

Порядок важен:
1. **Сразу отозвать (ротировать) секрет**: новый ключ, пароль, токен; проверить логи использования старого. Это главное: даже после очистки истории секрет мог быть склонирован, закеширован, проиндексирован ботами за минуты.
2. Если коммит **ещё не запушен** — `git commit --amend` или `git reset` и пересоздать коммит.
3. Если **запушен** — переписать историю во всех ветках и тегах:
```bash
git filter-repo --path config/secrets.yml --invert-paths          # удалить файл из всей истории
git filter-repo --replace-text replacements.txt                    # заменить строки (ключ==>REMOVED)
```
   Альтернатива — BFG Repo-Cleaner. Старый способ `git filter-branch` медленный и считается устаревшим.
4. Force push всех веток и тегов, попросить всех **переклонировать** репозиторий (старые клоны вернут секрет при следующем push).
5. На стороне хостинга: очистка кешей и ссылок на старые коммиты (pull/merge requests держат ссылки), у GitHub и GitLab — запрос в поддержку или инструменты удаления.
6. **Предотвращение**: pre-commit-хук с gitleaks или trufflehog, push protection / secret detection на сервере, `.gitignore` для `.env`, секреты в менеджере секретов.

### Большой бинарник в истории

Репозиторий раздувается навсегда: каждый клон скачивает всю историю. Удаление файла новым коммитом **не помогает** — он остаётся в старых коммитах.
- Найти большие объекты: `git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n | tail`.
- Удалить из истории: `git filter-repo --strip-blobs-bigger-than 50M` или по пути; затем force push и переклонирование.
- Для бинарных файлов, которые нужно версионировать, — **Git LFS** (в репозитории хранится указатель, сам файл — в отдельном хранилище); артефакты сборки — в репозиторий артефактов, а не в Git.

### Последствия переписывания истории

- Меняются хеши **всех** последующих коммитов: открытые MR, ссылки на коммиты, подписи становятся недействительными.
- Все участники должны переклонировать или сделать жёсткий reset на новую историю.
- Защищённые ветки нужно временно разрешить переписывать — это делается осознанно и по согласованию.

## Модели ветвления: GitFlow, GitHub Flow, trunk-based
id: workflows

> **Суть:** модель ветвления — договорённость команды о том, как ветки создаются, живут и сливаются. **GitFlow** — много долгоживущих веток под плановые релизы. **GitHub Flow** — main всегда готов к деплою, короткие feature-ветки через PR. **Trunk-based** — все интегрируются в main минимум раз в день, незаконченное прячется за feature flags. Чем чаще деплой, тем короче должны быть ветки.

### GitFlow

```
main      ●───────────────●──────────●        (только релизы, теги)
           \             /          /
release     \       ●───●          /
             \     /              /
develop  ●────●───●──────●───────●            (интеграция)
           \     /        \     /
feature     ●───●          ●───●
hotfix                              ● → main и develop
```
- Ветки: `main` (продакшен), `develop` (интеграция), `feature/*`, `release/*` (стабилизация), `hotfix/*`.
- Подходит: продукты с **плановыми релизами** и поддержкой нескольких версий (коробочное ПО, мобильные приложения, библиотеки).
- Минусы: долгоживущие ветки → большие слияния и конфликты, задержка обратной связи, сложность; плохо сочетается с непрерывной поставкой. Сам автор модели позже рекомендовал более простые подходы для веб-сервисов.

### GitHub Flow

- Одна долгоживущая ветка `main`, она **всегда готова к деплою**.
- Работа — в короткой ветке → Pull/Merge Request → CI и ревью → слияние → деплой (часто автоматический).
- Подходит большинству веб-сервисов с непрерывной поставкой. Варианты: GitLab Flow с ветками окружений или релизов.

### Trunk-based development

- Все разработчики интегрируются в `main` (trunk) **часто** — минимум раз в день; ветки живут часы, максимум 1–2 дня (или коммиты прямо в trunk в маленьких командах).
- Незаконченная функциональность скрыта **feature flags**; большие изменения — через **branch by abstraction** (новая реализация рядом со старой за интерфейсом).
- Требует: быстрого и надёжного CI, хорошего покрытия тестами, культуры маленьких изменений и быстрого ревью.
- Релизы: из trunk напрямую или через короткоживущие ветки релиза (только cherry-pick исправлений).
- Исследования DORA связывают trunk-based development с высокой эффективностью поставки.

### Сравнение

| | GitFlow | GitHub Flow | Trunk-based |
|---|---|---|---|
| Долгоживущие ветки | main, develop, release | main | main |
| Жизнь feature-веток | дни–недели | дни | часы–1–2 дня |
| Частота релизов | плановые | частые | непрерывные |
| Feature flags | редко | желательно | обязательно |
| Конфликты слияния | частые и большие | умеренные | редкие и маленькие |
| Когда | версионные продукты | веб-сервисы | высокая зрелость CI/CD |

## Командная работа: hooks, pre-commit, .gitignore, submodule и subtree
id: team-tooling

> **Суть:** **hooks** запускают проверки на событиях Git (до коммита, до push), а фреймворк **pre-commit** делает их общими и версионированными для всей команды. **.gitignore** не даёт попасть в репозиторий мусору и секретам. Общий код между репозиториями подключают через **submodule** (ссылка на коммит другого репозитория) или **subtree** (копия кода внутри), а чаще — через пакеты.

### Git hooks

Скрипты в `.git/hooks/`, срабатывающие на события:
- клиентские: `pre-commit` (перед созданием коммита: линтеры, форматирование, поиск секретов), `commit-msg` (проверка формата сообщения, Conventional Commits), `pre-push` (быстрые тесты);
- серверные: `pre-receive`, `update`, `post-receive` (на сервере Git: запрет force push, проверки политик) — на GitHub и GitLab вместо них используют защищённые ветки, правила push и CI.

Проблема: `.git/hooks` **не версионируется** и не передаётся при клонировании. Хуки легко обойти (`git commit --no-verify`). Поэтому хуки — для **быстрой обратной связи** разработчику, а **обязательные** проверки дублируются в CI.

### pre-commit

Фреймворк с конфигурацией в репозитории:
```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.21.2
    hooks:
      - id: gitleaks
  - repo: https://github.com/antonbabenko/pre-commit-terraform
    rev: v1.96.1
    hooks:
      - id: terraform_fmt
      - id: terraform_tflint
```
```bash
pre-commit install           # установить хук в .git/hooks
pre-commit run --all-files   # прогнать на всём репозитории (так же в CI)
pre-commit autoupdate        # обновить версии
```
Хуки проверяют только изменённые файлы, работают в изолированных окружениях, одинаково у всех. В CI — `pre-commit run --all-files`, чтобы обходы `--no-verify` не проходили.

Альтернативы: Husky и lint-staged (JavaScript-проекты), lefthook.

### .gitignore

```
# зависимости и сборка
node_modules/
dist/
*.pyc
# локальные настройки и секреты
.env
*.tfvars
.terraform/
# IDE и ОС
.idea/
.DS_Store
# но этот файл нужен
!.env.example
```
- Работает только для **неотслеживаемых** файлов. Если файл уже в репозитории, добавление в `.gitignore` ничего не изменит: нужно `git rm --cached file` (а если это секрет — см. [переписывание истории](#/theory/git/history-rewrite)).
- `.gitignore` можно класть в подкаталоги; личные исключения — в `.git/info/exclude` или глобальный `core.excludesFile`.
- Проверить, какое правило игнорирует файл: `git check-ignore -v path`.
- `.gitattributes` — родственный файл: переводы строк (`* text=auto`), бинарные файлы, LFS, стратегии слияния.

### Submodule и subtree

| | Submodule | Subtree |
|---|---|---|
| Что в основном репозитории | **ссылка** на конкретный коммит другого репозитория + `.gitmodules` | **копия** кода в подкаталоге (с историей или squash) |
| Клонирование | нужен `--recurse-submodules` или `git submodule update --init` | обычный `git clone` |
| Обновление | `git submodule update --remote`, затем коммит новой ссылки | `git subtree pull --prefix=lib repo main` |
| Изменение общего кода | в отдельном репозитории, затем обновить ссылку | можно прямо в основном, отправить обратно `subtree push` |
| Типичные проблемы | забыли инициализировать, detached HEAD внутри, рассинхрон ссылок | раздувание истории, сложная обратная синхронизация |

Когда что:
- **submodule** — нужно точно зафиксировать версию внешнего репозитория и изменения в нём редки (вендорные зависимости, общие конфигурации);
- **subtree** — потребителям не нужно знать о Git-механике, код должен быть доступен сразу после clone.

Часто лучший вариант — вообще **не тянуть код**, а распространять общий код как **версионированный пакет** (npm, PyPI, Go modules, Helm-чарт, Terraform-модуль по тегу, общий шаблон CI через `include`), или перейти на **монорепозиторий**.
