Брокеры сообщений позволяют сервисам общаться асинхронно: отправитель не ждёт получателя, нагрузка сглаживается очередью, а одно событие могут получить многие. Главы идут так: зачем нужна асинхронность и чем журнал отличается от очереди → устройство Kafka → её надёжность → потребители и lag → гарантии доставки и паттерны → эксплуатация Kafka → RabbitMQ → Redis и NATS.

## Асинхронное взаимодействие: очереди, журналы и выбор брокера
id: why-async

> **Суть:** брокер развязывает отправителя и получателя по времени и нагрузке. Бывают две модели: **очередь** (сообщение получает и удаляет один из потребителей — RabbitMQ) и **журнал** (сообщения хранятся, каждый потребитель читает со своей позиции и может перечитать — Kafka). Выбор зависит от того, нужны ли повторное чтение, огромная пропускная способность и сложная маршрутизация.

### Зачем асинхронность

При синхронном вызове (HTTP, gRPC) вызывающий **ждёт** ответа, а отказ или медленная работа получателя сразу становятся его проблемой. Очередь между ними даёт:
- **развязку по доступности**: получатель упал — сообщения подождут в брокере;
- **сглаживание пиков**: всплеск запросов копится в очереди, потребители разбирают в своём темпе;
- **масштабирование**: добавили потребителей — обработка ускорилась;
- **один ко многим**: событие `OrderCreated` получают биллинг, склад, аналитика, уведомления — отправитель о них не знает;
- **долгие операции** в фоне: генерация отчёта, отправка писем, обработка видео.

Цена: **итоговая согласованность** (результат появится не сразу), сложнее отладка (трейсинг через брокер), нужно думать о **дублях, порядке и потерях**, ещё одна система для эксплуатации.

### Модели обмена

- **Point-to-point (очередь задач)** — каждое сообщение обрабатывает **один** потребитель из нескольких конкурирующих. Пример: очередь задач на генерацию PDF.
- **Publish/subscribe** — каждое сообщение получают **все** подписчики (каждая подписка получает свою копию).
- **Request-reply** — асинхронный RPC через брокер с очередью ответов.

### Очередь и журнал

| | Очередь (RabbitMQ, SQS) | Журнал (Kafka, Pulsar, Redpanda) |
|---|---|---|
| После обработки | сообщение **удаляется** | сообщение **остаётся** до истечения ретеншна |
| Позиция чтения | брокер отслеживает доставку каждого сообщения | потребитель хранит **offset** |
| Повторное чтение | нет | **да** (replay): новый потребитель может прочитать историю |
| Порядок | в пределах очереди, нарушается при конкурирующих потребителях и повторах | гарантирован **внутри партиции** |
| Маршрутизация | гибкая: exchanges, ключи, шаблоны | по топикам и ключам |
| Пропускная способность | высокая | очень высокая (последовательная запись на диск, батчи) |
| Подходит | очереди задач, RPC, сложная маршрутизация, приоритеты | поток событий, CDC, логи, аналитика, event sourcing, интеграция многих систем |

### Какой брокер выбрать

- **Kafka** — поток событий большого объёма, хранение и повторная обработка истории, экосистема (Kafka Connect, Streams, Debezium).
- **RabbitMQ** — очереди задач, сложная маршрутизация, приоритеты, TTL, гибкое управление доставкой.
- **NATS** — лёгкая шина для микросервисов и edge, минимальная задержка; хранение — через JetStream.
- **Redis Streams / списки** — простые очереди там, где Redis уже есть и объёмы невелики.
- **Облачные** (SQS, SNS, Pub/Sub, Service Bus) — без эксплуатации, когда устраивают их модели и ограничения.

## Устройство Kafka: топики, партиции, ключи, хранение
id: kafka-architecture

> **Суть:** Kafka — распределённый журнал. **Топик** делится на **партиции** — упорядоченные журналы только на добавление, распределённые по **брокерам**. Сообщения с одинаковым **ключом** попадают в одну партицию, поэтому порядок гарантирован для каждого ключа. Сообщения хранятся по **ретеншну** или **компактируются** по ключу, независимо от того, прочитаны ли они.

### Основные понятия

```
producer ──► topic "orders" (3 партиции, replication factor 3)
               ├─ partition 0: offset 0,1,2,...  лидер на broker 1, реплики на 2 и 3
               ├─ partition 1: ...               лидер на broker 2
               └─ partition 2: ...               лидер на broker 3
consumer group "billing":   consumer A ← p0, p1     consumer B ← p2
consumer group "analytics": читает те же сообщения независимо
```
- **Сообщение (record)**: ключ, значение, заголовки, временная метка.
- **Топик** — категория сообщений (`orders`, `payments.events`).
- **Партиция** — единица **параллелизма** и **порядка**. Каждое сообщение в партиции получает возрастающий номер — **offset**.
- **Брокер** — сервер Kafka; партиции распределены между брокерами.
- **Контроллер** — управляет метаданными кластера (лидеры партиций, состав брокеров). В режиме **KRaft** контроллеры используют собственный консенсус Raft; **ZooKeeper** больше не нужен (с Kafka 4.0 его поддержка удалена).

### Ключи и партиционирование

Продюсер выбирает партицию:
- **есть ключ** → `hash(key) % число_партиций`: все события одного заказа (`key = order_id`) попадают в одну партицию и читаются **по порядку**;
- **нет ключа** → распределение по партициям (sticky partitioner набивает батч в одну партицию, затем переключается).

Следствия:
- порядок гарантирован **только внутри партиции**, глобального порядка по топику нет;
- **горячий ключ** (один клиент с огромным трафиком) перегружает одну партицию;
- **изменение числа партиций меняет распределение ключей** — события одного ключа после увеличения могут оказаться в другой партиции, и порядок на переходе нарушится.

### Почему Kafka быстрая

- **Последовательная запись** в конец файлов-сегментов — диски (даже HDD) отлично с этим справляются.
- **Page cache ОС** вместо собственного кеша: свежие данные читаются из памяти. Поэтому брокеру важнее свободная память под page cache, чем большой heap JVM.
- **Zero-copy** (`sendfile`) — данные идут с диска в сокет без копирования через приложение.
- **Батчи и сжатие** на продюсере (`linger.ms`, `batch.size`, `compression.type=zstd` или `lz4`).
- Потребители сами **забирают** данные (pull) в своём темпе.

### Хранение: retention и compaction

Партиция на диске — набор **сегментов** (`segment.bytes`, по умолчанию 1 ГБ). Удаление идёт целыми сегментами.

**`cleanup.policy=delete`** (по умолчанию):
- `retention.ms` (7 дней по умолчанию) — удалять сегменты старше срока;
- `retention.bytes` — ограничение размера **на партицию**;
- **активный** сегмент не удаляется — данные могут жить дольше ретеншна.

**`cleanup.policy=compact`**:
- для каждого **ключа** остаётся **последнее значение**; старые версии удаляются фоновой очисткой;
- сообщение с ключом и пустым значением (**tombstone**) означает удаление ключа;
- топик становится «таблицей текущего состояния»: последнее состояние каждого клиента, конфигурация, changelog Kafka Streams. Служебный `__consumer_offsets` — компактируемый.

Можно сочетать `compact,delete`.

**Tiered storage** (Kafka 3.6+) — старые сегменты выгружаются в объектное хранилище, на локальных дисках только свежие данные: дешевле долгое хранение и быстрее восстановление брокеров.

Повторная обработка (replay) возможна только в пределах ретеншна — это нужно учитывать в планах восстановления после ошибок в потребителях.

## Надёжность Kafka: репликация, ISR и acks
id: kafka-replication

> **Суть:** каждая партиция хранится в **replication factor** копиях на разных брокерах: один **лидер** принимает запись, **фолловеры** копируют. Реплики, не отставшие от лидера, составляют **ISR**. Продюсер с `acks=all` получает подтверждение, только когда запись есть во всех репликах ISR, а `min.insync.replicas` не даёт писать, если копий слишком мало. Классика: **RF=3, min.insync.replicas=2, acks=all**.

### Лидеры и фолловеры

- Продюсеры пишут в **лидера** партиции; потребители читают у лидера (или у ближайшей реплики — follower fetching, полезно для экономии межзонального трафика).
- Фолловеры постоянно забирают новые данные у лидера.
- **ISR** (in-sync replicas) — реплики, отстающие не дольше `replica.lag.time.max.ms` (30 с). Лидер — всегда в ISR.
- При падении лидера контроллер выбирает **нового лидера из ISR** — у него есть все подтверждённые данные.

### acks — когда запись успешна

| `acks` | Подтверждение | Риск |
|---|---|---|
| `0` | не ждать | потеря при любом сбое |
| `1` | записал лидер | потеря, если лидер упал до репликации |
| **`all`** (по умолчанию с Kafka 3.0) | записали **все реплики из ISR** | нет потери, пока жива хотя бы одна реплика из ISR |

**`min.insync.replicas`** — минимальный размер ISR для приёма записи с `acks=all`. Без него `acks=all` при ISR из одной реплики (только лидер) по сути равен `acks=1`.

Расчёт для **RF=3, min.insync.replicas=2**:
- потерян один брокер → ISR = 2, запись продолжается, данные в двух копиях;
- потеряны два → ISR = 1 < 2 → продюсеры получают `NotEnoughReplicas`: **запись останавливается, но данные не теряются**. Это осознанный выбор согласованности вместо доступности.

### Другие настройки надёжности

- **`unclean.leader.election.enable=false`** (по умолчанию) — не выбирать лидером реплику **вне** ISR: если все реплики из ISR недоступны, партиция будет недоступна, зато не потеряются данные. `true` — доступность ценой потери данных.
- **Идемпотентный продюсер** (`enable.idempotence=true`, по умолчанию с 3.0): брокер отбрасывает дубликаты, возникшие из-за ретраев продюсера (по номеру продюсера и последовательности), и сохраняет порядок.
- **`retries`** и **`delivery.timeout.ms`** — продюсер повторяет отправку при временных ошибках.
- **Rack awareness** (`broker.rack` = зона доступности) — реплики одной партиции размещаются в **разных зонах**: отказ зоны не уничтожит все копии.
- `fsync` Kafka по умолчанию не делает на каждую запись — надёжность обеспечивается **репликацией** на разные машины, а не диском одной.

### Что мониторить

- **`UnderReplicatedPartitions`** > 0 — какие-то реплики отстают (брокер перегружен, упал, проблемы сети или диска);
- **`OfflinePartitionsCount`** > 0 — партиции **без лидера**, недоступны;
- **`UnderMinIsrPartitionCount`** > 0 — запись с `acks=all` в эти партиции отклоняется;
- `ActiveControllerCount` — ровно один активный контроллер;
- частота смены лидеров и размеры ISR.

## Потребители: consumer groups, offset, rebalance и lag
id: kafka-consumers

> **Суть:** потребители с одинаковым `group.id` образуют **группу** и **делят партиции** между собой: каждая партиция читается одним потребителем группы, поэтому параллелизм ограничен числом партиций. Позиция чтения — **offset** — коммитится в Kafka. При изменении состава группы происходит **rebalance**. **Consumer lag** — сколько сообщений ещё не обработано — главная метрика здоровья потребителей.

### Группы

- Каждая партиция в каждый момент назначена **одному** потребителю группы; один потребитель может читать несколько партиций.
- 6 партиций и 8 потребителей → **двое простаивают**. Масштабировать потребителей больше числа партиций бессмысленно.
- **Разные группы** читают топик **независимо**, каждая со своими offset’ами: одно событие получают и биллинг, и аналитика.

### Offset и коммиты

Offset’ы групп хранятся в служебном топике `__consumer_offsets`.
- **Автокоммит** (`enable.auto.commit=true`) — периодически коммитит то, что выдал `poll()`. Если упасть после коммита, но до обработки, — сообщения **потеряются**; если до коммита, но после обработки — **повторятся**.
- **Ручной коммит после обработки** — at-least-once: повторы возможны, потери — нет (см. [гарантии доставки](#/theory/messaging/delivery)).
- `auto.offset.reset` — откуда начать новой группе: `earliest` (с начала) или `latest` (только новые).
- Сброс offset’ов для повторной обработки: `kafka-consumer-groups.sh --reset-offsets --to-datetime ... --execute` (группа должна быть остановлена).

### Rebalance

Перераспределение партиций, когда:
- потребитель присоединился или ушёл (деплой, масштабирование);
- потребитель перестал слать heartbeat дольше `session.timeout.ms` (упал, завис, долгая пауза GC);
- потребитель не вызвал `poll()` дольше **`max.poll.interval.ms`** (5 минут по умолчанию) — **слишком долгая обработка пачки**;
- изменилось число партиций.

Почему вреден:
- в классическом (eager) протоколе на время ребаланса **вся группа перестаёт читать** — растёт lag;
- **шторм ребалансов**: rolling update десятков подов, флапающий потребитель, долгая обработка → группа почти не работает;
- **повторная обработка**: обработанные, но не закоммиченные сообщения достанутся другому потребителю.

Как смягчить:
- **cooperative-sticky** назначение — переназначаются только затронутые партиции, остальные читаются дальше;
- **static membership** (`group.instance.id`) — перезапуск пода с тем же ID в пределах `session.timeout.ms` не вызывает ребаланс (удобно для StatefulSet и rolling update);
- **новый протокол групп** (KIP-848, `group.protocol=consumer`, Kafka 4.0) — ребалансы инкрементально на стороне брокера;
- `max.poll.records` и `max.poll.interval.ms` такие, чтобы пачка точно успевала обработаться;
- обработка **идемпотентна**, потому что повторы неизбежны.

### Consumer lag

`lag = последний offset в партиции − закоммиченный offset группы`.
```bash
kafka-consumer-groups.sh --bootstrap-server kafka:9092 --describe --group billing
# TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG    CONSUMER-ID
```
Мониторинг: kafka-exporter, kminion, Burrow; лучше алертить на **время** отставания (сколько секунд назад было записано самое старое необработанное сообщение), а не на число сообщений — 10 000 сообщений при потоке 50 000 в секунду не проблема, а 100 при потоке раз в минуту — проблема.

Диагностика по картине:

| Картина | Вероятная причина | Что делать |
|---|---|---|
| lag растёт на **всех** партициях равномерно | вырос входящий поток или замедлилась обработка (медленная БД, внешний API, GC, троттлинг CPU) | трейсы и метрики обработки; масштабировать потребителей (до числа партиций), батчевая обработка, больше партиций |
| lag растёт на **одной-двух** партициях | горячий ключ, зависший потребитель, **«ядовитое» сообщение** (падение на одном и том же сообщении) | распределение ключей, логи потребителя этих партиций, DLQ |
| lag скачет, частые ребалансы | обработка не укладывается в `max.poll.interval.ms`, флапают поды (OOM, liveness) | настройки poll, ресурсы, static membership |
| потребители простаивают, а lag растёт | проблемы брокеров: under-replicated, диски, сеть, квоты | метрики брокеров |
| в группе нет потребителей | сервис упал или не подключается (авторизация, DNS, сеть) | статус сервиса, логи |

Автомасштабирование потребителей по lag в Kubernetes — **KEDA** со скейлером Kafka (с потолком в число партиций).

## Гарантии доставки, идемпотентность, outbox и DLQ
id: delivery

> **Суть:** бывают три гарантии: **at-most-once** (возможна потеря), **at-least-once** (возможны дубли) и **exactly-once** (ровно один раз). На практике почти везде используют **at-least-once + идемпотентную обработку**: exactly-once в Kafka работает только внутри Kafka. Проблему «записать в БД и отправить событие» решает **transactional outbox**, а неперевариваемые сообщения уходят в **dead letter queue**.

### Три гарантии

- **At-most-once** — не более одного раза: коммит позиции **до** обработки. Упал посреди обработки — сообщение потеряно. Допустимо для некритичной телеметрии.
- **At-least-once** — не менее одного раза: коммит **после** обработки. Упал между обработкой и коммитом — сообщение обработается **повторно**. Самый распространённый режим.
- **Exactly-once** — ровно один раз.

Дубли возникают на всех звеньях: ретраи продюсера, повторная доставка после ребаланса, повтор после падения потребителя, ретраи в RabbitMQ после отсутствия ack. Поэтому их надо **ожидать по умолчанию**.

### Exactly-once в Kafka

Работает в сценарии **«прочитать из Kafka → обработать → записать в Kafka»**:
- **идемпотентный продюсер** — нет дублей от ретраев;
- **транзакции** (`transactional.id`): запись результатов в несколько партиций **и** коммит offset’ов входного топика — атомарно;
- потребители результатов читают с `isolation.level=read_committed` (не видят незакоммиченные транзакции);
- в Kafka Streams — одним параметром `processing.guarantee=exactly_once_v2`.

Как только обработка затрагивает **внешнюю систему** (БД, HTTP API, письмо, платёж), гарантии Kafka на неё не распространяются.

### Идемпотентная обработка

Сделать так, чтобы повтор не менял результат:
- **ключ идемпотентности** (ID события) + таблица обработанных событий или уникальный индекс — повторное событие отбрасывается;
- в одной транзакции БД: записать результат **и** отметить событие обработанным;
- операции «установить значение» вместо «прибавить», **upsert** вместо insert;
- для внешних API — передавать idempotency key (платёжные системы его поддерживают).

### Transactional outbox

**Проблема двойной записи**: сервис должен сохранить заказ в БД **и** отправить `OrderCreated` в брокер. Две независимые операции — при сбое между ними получим заказ без события или событие без заказа. Распределённые транзакции (2PC) между БД и брокером — сложно, медленно и часто недоступно.

Решение:
1. В **той же транзакции БД**, что и бизнес-изменение, записать событие в таблицу `outbox`.
2. Отдельный процесс (**relay**) читает outbox и публикует события в брокер:
   - **опрос** таблицы (polling) с отметкой отправленных — просто, но задержка и нагрузка на БД;
   - **CDC**: **Debezium** читает журнал БД (WAL в PostgreSQL через логическую репликацию) и публикует изменения таблицы outbox в Kafka — без опроса, с минимальной задержкой.
3. Доставка — at-least-once, потребители идемпотентны.

Зеркальный паттерн на стороне получателя — **inbox**: сохранить входящее событие с уникальным ID, а обработать уже из своей таблицы.

### Dead letter queue

Сообщение, которое **не удаётся обработать** (невалидный формат, ошибка бизнес-логики, «ядовитое» сообщение, роняющее потребителя), не должно блокировать очередь или крутиться бесконечно.
- После N попыток сообщение перекладывается в отдельную очередь или топик (**DLQ / DLT**) с причиной ошибки в заголовках.
- **RabbitMQ** — встроенный **dead letter exchange** (`x-dead-letter-exchange`): сообщение уходит туда при `nack`/`reject` без возврата в очередь, истечении TTL, переполнении очереди; у quorum-очередей — лимит доставок `x-delivery-limit`.
- **Kafka** — встроенного DLQ нет: реализуют в потребителе (топик `orders.DLT`), есть поддержка в Spring Kafka и Kafka Connect.
- **Retry-топики с задержкой** (5 секунд, 1 минута, 10 минут) перед DLQ — временные сбои зависимостей обрабатываются без людей.

Обязательно: **алерт на размер DLQ**, инструмент просмотра и **повторной отправки** (replay) после исправления, владелец, который разбирает DLQ. DLQ, в которую никто не смотрит, — это тихая потеря данных.

Для Kafka есть нюанс порядка: если сообщение ключа ушло в DLQ, а следующие по тому же ключу обработались, порядок для ключа нарушен. Для строго упорядоченных потоков иногда приходится останавливать обработку ключа до исправления.

## Эксплуатация Kafka: партиции, ёмкость, Kubernetes и мониторинг
id: kafka-ops

> **Суть:** эксплуатация Kafka — это правильное число партиций (увеличить можно, уменьшить нельзя), расчёт дисков (поток × ретеншн × RF), распределение по зонам, быстрые диски и память под page cache, безопасность клиентов и мониторинг состояния реплик и consumer lag. В Kubernetes — через оператор **Strimzi**, в облаке — через управляемый сервис.

### Сколько партиций

Партиции — единица параллелизма: одна партиция читается одним потребителем группы, а запись в неё последовательна.

Оценка: `партиций ≥ max(целевой поток / поток одного потребителя, целевой поток / поток в одну партицию)` с **запасом на рост**, потому что **увеличить число партиций можно, а уменьшить — нет** (только пересоздать топик), и увеличение меняет распределение ключей (`hash % N`).

| Слишком мало | Слишком много |
|---|---|
| нельзя масштабировать потребителей | больше файлов, памяти и метаданных на брокерах |
| горячие партиции, упор в один брокер и диск | дольше выборы лидеров и восстановление после сбоя |
| | меньше батчи на партицию у продюсеров → хуже сжатие и пропускная способность |
| | дольше ребалансы |

Практика: для нагруженных топиков — десятки партиций, кратно числу брокеров для равномерного распределения лидеров; для топиков с важным порядком по ключу — сразу с запасом. KRaft сильно поднял предел партиций на кластер, но тысячи партиций на топик без нужды — всё равно антипаттерн.

### Ёмкость и ресурсы

- **Диски**: `входящий поток × ретеншн × replication factor` + запас 30–50%. Заполненный диск **останавливает брокер**. Быстрые SSD, мониторинг заполнения, tiered storage для долгого хранения.
- **Память**: свободная RAM под **page cache** важнее большого heap JVM (обычно heap 4–8 ГБ, остальное — ОС).
- **Сеть**: репликация умножает трафик на RF; межзональный трафик платный в облаке (follower fetching для потребителей).
- **Перебалансировка партиций** между брокерами после добавления узлов — Cruise Control или встроенные инструменты; без неё новые брокеры простаивают.

### Kafka в Kubernetes: Strimzi

Варианты размещения: **управляемый сервис** (Amazon MSK, Confluent Cloud, Managed Kafka в Yandex Cloud), ВМ с Ansible, Kubernetes с оператором.

**Strimzi** (проект CNCF): ресурсы `Kafka` и `KafkaNodePool` (брокеры и контроллеры KRaft), `KafkaTopic`, `KafkaUser` (пользователи и ACL), `KafkaConnect`/`KafkaConnector`. Оператор управляет TLS-сертификатами, выполняет **rolling update по одному брокеру** с проверкой синхронизации реплик, интегрирует Cruise Control.

Особенности:
- **хранилище**: PVC на быстрых дисках, `WaitForFirstConsumer` (см. [хранение в Kubernetes](#/theory/kubernetes/storage)), мониторинг заполнения;
- **распределение по зонам**: rack awareness с `topology.kubernetes.io/zone`, anti-affinity брокеров, PodDisruptionBudget;
- **сеть для внешних клиентов**: клиент должен подключаться к **каждому** брокеру напрямую (advertised listeners) — LoadBalancer или NodePort на брокер, Ingress с TLS passthrough;
- **безопасность**: TLS, аутентификация (SCRAM, mTLS, OAuth), ACL по топикам с минимальными правами;
- **ресурсы**: Guaranteed QoS, память под page cache, выделенные узлы;
- **обновления** Kafka — постепенно, с проверкой совместимости клиентов.

### Мониторинг

Метрики через JMX exporter (Strimzi отдаёт сам), kafka-exporter или kminion для lag:
- **состояние кластера**: `UnderReplicatedPartitions`, `OfflinePartitionsCount`, `UnderMinIsrPartitionCount`, активный контроллер (см. [надёжность](#/theory/messaging/kafka-replication));
- **производительность**: трафик по брокерам, латентность Produce/Fetch, `RequestHandlerAvgIdlePercent` и загрузка сетевых потоков (ниже ~20–30% — брокер перегружен), латентность дисков;
- **ресурсы**: диск, page cache, GC;
- **клиенты**: **consumer lag** по группам, ошибки продюсеров, частота ребалансов (см. [потребители](#/theory/messaging/kafka-consumers));
- инструменты: дашборды Strimzi для Grafana, UI для топиков — AKHQ, Kafka UI, Redpanda Console.

## RabbitMQ
id: rabbitmq

> **Суть:** RabbitMQ — брокер по модели AMQP: продюсер публикует в **exchange**, тот по **bindings** раскладывает сообщения по **очередям**, потребители забирают и **подтверждают** (ack), после чего сообщение удаляется. Чтобы не терять сообщения, нужны **publisher confirms**, **durable/quorum** очереди с persistent-сообщениями и **ручные ack** — на каждом звене.

### Модель

```
producer ──► exchange ──binding (routing key / шаблон)──► queue ──► consumer (ack)
```

Типы exchange:
- **direct** — в очереди, у которых binding key **равен** routing key (`order.created`);
- **topic** — по шаблону: `order.*` (одно слово), `order.#` (любое число слов) — подписка на категории событий;
- **fanout** — во **все** привязанные очереди (широковещание), ключ игнорируется;
- **headers** — по заголовкам сообщения;
- **default exchange** — отправка прямо в очередь по её имени.

Publish/subscribe в RabbitMQ — это fanout или topic exchange с отдельной очередью на каждого подписчика.

### Как не потерять сообщения

1. **Продюсер → брокер**: **publisher confirms** — брокер подтверждает приём (и запись на диск для persistent); без подтверждения продюсер повторяет. Флаг `mandatory` — узнать, что сообщение не попало ни в одну очередь (иначе молча отбрасывается).
2. **Хранение**: **durable** очереди и **persistent** сообщения (`delivery_mode=2`) переживают перезапуск брокера.
3. **Отказоустойчивость**: **quorum queues** — репликация на основе Raft на нечётное число узлов (3 или 5), потеря меньшинства узлов не теряет данные. Классические зеркалируемые очереди устарели и удалены в RabbitMQ 4.0.
4. **Брокер → потребитель**: **ручные ack** после обработки, а не автоподтверждение. Если потребитель упал без ack, сообщение вернётся в очередь и уйдёт другому — значит, возможны **дубли**, обработка должна быть идемпотентной.
5. **Ошибки обработки**: `nack`/`reject` без возврата в очередь → **dead letter exchange**; лимит доставок (`x-delivery-limit`), иначе «ядовитое» сообщение крутится бесконечно (см. [DLQ](#/theory/messaging/delivery)).

### Производительность и эксплуатация

- **prefetch** (`basic.qos`) — сколько неподтверждённых сообщений выдаётся потребителю: 1 — справедливое распределение, но медленно; слишком много — один потребитель набирает всё, растёт память. Обычно десятки–сотни.
- **Длинные очереди** — признак проблемы: брокер тратит память и диск. При превышении порогов срабатывают **memory alarm** и **disk alarm** — брокер **блокирует всех продюсеров** (flow control). Это частая причина «всё встало».
- Лимиты очередей: `x-max-length`, TTL сообщений, **lazy**-поведение (хранение на диске) по умолчанию у quorum-очередей.
- **Соединения и каналы**: открывать соединение на каждое сообщение — антипаттерн; утечка каналов — частая проблема клиентов.
- Приоритеты сообщений, отложенная доставка (плагин delayed message), TTL — сильные стороны RabbitMQ.
- **Streams** — журналоподобные очереди с повторным чтением и большой пропускной способностью: ответ на часть сценариев Kafka.

**Кластеризация**: узлы объединяются в кластер (метаданные на всех узлах); quorum-очереди реплицируются; для связи площадок — плагины Federation и Shovel. Сетевые разделения обрабатываются стратегией `partition_handling` (обычно `pause_minority`).

**Мониторинг** (встроенный плагин Prometheus и management UI): длина очередей (ready и unacked), скорость публикации, доставки и ack, число потребителей на очередь (0 — проблема), соединения и каналы, memory и disk alarms, состояние quorum-очередей.

В Kubernetes — **RabbitMQ Cluster Operator** и Messaging Topology Operator (очереди, exchanges, пользователи как ресурсы).

## Redis и NATS: лёгкие альтернативы
id: redis-nats

> **Суть:** **Redis** — хранилище в памяти: прежде всего кеш, но также сессии, счётчики, блокировки и простые очереди (списки, Streams, Pub/Sub). **NATS** — лёгкая и очень быстрая шина сообщений для микросервисов и edge: без хранения в базовом режиме и с хранением через **JetStream**. Оба уместны там, где Kafka избыточна.

### Redis: применения

- **Кеш** (`SET key value EX 300`) — самое частое: стратегия cache-aside (прочитать из кеша, при промахе — из БД и положить в кеш), TTL, защита от лавины запросов при истечении популярного ключа (см. [thundering herd](#/theory/sre/resilience-patterns)).
- **Сессии**, **rate limiting** (`INCR` + `EXPIRE`, скользящее окно на sorted set), счётчики, рейтинги (sorted sets), распределённые блокировки (с оговорками: Redlock спорен для строгой корректности).
- **Очереди**:
  - **списки** (`LPUSH` / `BRPOP`) — просто, но сообщение теряется, если потребитель упал после извлечения (частично решает `LMOVE` в очередь обработки);
  - **Streams** (`XADD`, группы потребителей, `XACK`, `XPENDING`) — подтверждения и повторная доставка, похоже на упрощённую Kafka;
  - **Pub/Sub** — без хранения: сообщение получают только подписчики, подключённые прямо сейчас.

Redis обрабатывает команды **в одном потоке** (сетевой ввод-вывод многопоточный): очень быстро, но тяжёлая команда (`KEYS *`, огромный `SMEMBERS`, `DEL` большого ключа) **блокирует всех** — используют `SCAN` и `UNLINK`.

**Устойчивость данных**:
- **RDB** — периодические снимки (быстрое восстановление, возможна потеря данных за интервал);
- **AOF** — журнал операций (`appendfsync everysec` — потеря не больше секунды);
- обычно оба; для чистого кеша — можно без persistence.

**Политика вытеснения** при `maxmemory`: `allkeys-lru` или `allkeys-lfu` для кеша; `noeviction` (по умолчанию) — ошибки записи при нехватке памяти, правильно для данных, которые нельзя терять.

**Отказоустойчивость**:
- репликация master → replicas (**асинхронная**: при failover возможна потеря последних записей);
- **Sentinel** — мониторинг и автоматический failover, клиенты узнают адрес мастера у Sentinel;
- **Redis Cluster** — шардирование по 16 384 слотам между мастерами с репликами; клиент должен поддерживать кластерный режим; операции с несколькими ключами — только в пределах одного слота (hash tags `{user:1}`);
- управляемые сервисы в облаках.

Лицензии: в 2024 году Redis сменил лицензию, сообщество создало форк **Valkey** (Linux Foundation), который используют многие облака; в 2025 Redis 8 снова доступен под открытой лицензией AGPL.

Эксплуатация: память и фрагментация, hit ratio, вытеснения, `SLOWLOG`, подключения, лаг репликации; ACL и переименование опасных команд; **никогда не открывать Redis в интернет** без пароля и TLS.

### NATS

Один бинарник на Go, мегабайты памяти, задержки в доли миллисекунды, простая эксплуатация (CNCF).

- **Core NATS** — publish/subscribe **без хранения** (at-most-once): нет подписчика в момент публикации — сообщение потеряно. **Subjects** с иерархией и шаблонами (`orders.*.created`, `orders.>`), встроенный **request-reply** (удобный RPC), **queue groups** — балансировка между подписчиками одной группы.
- **JetStream** — встроенное хранение: потоки с ретеншном, повторное чтение, подтверждения, push и pull consumer’ы, at-least-once, дедупликация публикаций, репликация на Raft. Поверх — **Key-Value** и **Object Store**.
- **Топология**: кластеры, суперкластеры между регионами, **leaf nodes** — лёгкие узлы на edge и устройствах, подключающиеся к центру; изоляция арендаторов через accounts.

Когда NATS удачен: шина событий и RPC для микросервисов с минимальной задержкой, edge и IoT с нестабильной связью, управляющие сообщения платформы, хранение сообщений умеренного объёма без сложности Kafka. Когда лучше другое: огромные объёмы и долгое хранение истории, экосистема Connect/Streams/CDC — Kafka; сложная маршрутизация и приоритеты — RabbitMQ.
