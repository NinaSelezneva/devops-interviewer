Контейнеры — это не отдельная технология, а сборка из механизмов ядра Linux плюс удобный формат упаковки (образ). Поэтому глава 1 опирается на [namespaces и cgroups](#/theory/linux/isolation) из теории Linux, а остальные главы идут по жизненному циклу: образ → Dockerfile → запуск и падения → сеть → данные → архитектура рантаймов → compose → безопасность.

## Что такое контейнер и чем он отличается от ВМ
id: what-is-container

> **Суть:** контейнер — это обычный процесс на ядре хоста, который **namespaces** изолируют (он видит свою ФС, свои PID и сеть), **cgroups** ограничивают по ресурсам, а файловая система собрана из слоёв образа. Виртуальная машина эмулирует целый компьютер со своим ядром.

### Как это выглядит со стороны хоста

```bash
docker run -d --name web nginx
ps aux | grep nginx         # процессы nginx видны на хосте как обычные процессы
docker inspect -f '{{.State.Pid}}' web
ls -l /proc/<PID>/ns        # его namespaces
cat /proc/<PID>/cgroup      # его cgroup
```
Никакой «виртуализации» здесь нет: ядро одно, процесс один, просто ему показывают другой мир.

Из чего собран контейнер:
- **namespaces**: pid, net, mnt, uts, ipc, user — что процесс видит;
- **cgroups**: сколько CPU, памяти, PID ему можно;
- **корневая ФС из образа**: overlayfs из слоёв только для чтения и тонкого слоя для записи;
- **ограничения безопасности**: урезанные capabilities, seccomp-фильтр системных вызовов, профиль AppArmor или SELinux.

### Контейнер и виртуальная машина

| | Контейнер | Виртуальная машина |
|---|---|---|
| Ядро | общее с хостом | своё |
| Изоляция | механизмы ядра; уязвимость ядра затрагивает всех | гипервизор, аппаратная виртуализация — сильнее |
| Старт | миллисекунды–секунды | десятки секунд |
| Накладные расходы | почти нет | своя ОС, память под ядро |
| Размер | мегабайты | гигабайты |
| Другая ОС | только Linux-контейнеры на Linux-ядре | любая ОС |

Почему контейнеры победили для приложений: одинаковый артефакт от ноутбука разработчика до продакшена, плотная упаковка, быстрый старт для масштабирования. Где нужна изоляция сильнее — используют **песочницы**: gVisor (перехватывает syscalls в своём «ядре» в пространстве пользователя), Kata Containers и Firecracker (лёгкие ВМ для каждого контейнера).

### Docker на Mac и Windows

Контейнерам нужно ядро Linux, поэтому Docker Desktop запускает **скрытую Linux-ВМ** и контейнеры внутри неё. Отсюда особенности: медленные bind mount’ы, другая сеть, `host.docker.internal`.

## Образы: слои, теги, digest и реестры
id: images

> **Суть:** образ — это набор **слоёв** только для чтения (каждый — изменения ФС) плюс конфигурация (команда запуска, переменные, порты). Слои общие между образами и кешируются. Тег — изменяемое имя, digest — неизменяемый хеш содержимого.

### Слои и overlayfs

Каждая инструкция Dockerfile, меняющая файлы (`RUN`, `COPY`, `ADD`), создаёт новый слой — архив с изменениями относительно предыдущего. При запуске контейнера **overlayfs** складывает слои в одну картину:
```
upperdir   (слой контейнера, запись)       ← изменения контейнера, исчезают вместе с ним
lowerdir   (слои образа, только чтение)     ← общие для всех контейнеров этого образа
merged     (то, что видит процесс)
```
- Изменение файла из нижнего слоя — **copy-up**: файл целиком копируется в верхний слой. Поэтому писать большие файлы в слой контейнера медленно — для данных нужны volumes.
- Удаление файла в верхнем слое создаёт «whiteout» — пометку, а сам файл в нижнем слое остаётся. Отсюда важное следствие: **удаление в отдельной инструкции не уменьшает образ**:
```dockerfile
RUN curl -o /tmp/big.tar.gz ... && tar xzf /tmp/big.tar.gz
RUN rm /tmp/big.tar.gz      # бесполезно: архив уже лежит в предыдущем слое
```
Правильно — скачать, распаковать и удалить в **одном** `RUN`.

Посмотреть слои: `docker history image`, `dive image` — какой слой сколько весит.

### Теги и digest

- **Репозиторий и тег**: `registry.example.com/team/api:1.4.2`. Тег — **указатель**, его можно перезаписать. `latest` — просто тег по умолчанию, не «последняя версия».
- **Digest**: `api@sha256:3f1a...` — хеш манифеста, однозначно определяет содержимое. Не меняется никогда.

Практика:
- в продакшене не использовать `latest`: непонятно, что запущено, и откат невозможен;
- версии по semver или git SHA (`api:1.4.2`, `api:git-3f2a1c`);
- для полной воспроизводимости и безопасности (никто не подменит тег) — ссылаться по digest;
- теги в реестре делать неизменяемыми (immutable tags в Harbor, ECR).

### Устройство образа и мультиархитектура

Формат стандартизирован **OCI**:
- **манифест** — список слоёв (по digest) и ссылка на конфиг;
- **конфиг** — команда, переменные, пользователь, архитектура;
- **индекс** (manifest list) — набор манифестов для разных платформ: `linux/amd64`, `linux/arm64`.

При `docker pull nginx` клиент берёт индекс и скачивает манифест под свою архитектуру. Собрать мультиархитектурный образ: `docker buildx build --platform linux/amd64,linux/arm64 -t repo/app:1.0 --push .` (через эмуляцию QEMU или нативные сборщики для каждой архитектуры). Это важно, когда разработчики на Mac с Apple Silicon, а продакшен на amd64 — или наоборот, при переезде на ARM-инстансы ради экономии.

### Реестры

Реестр (registry) хранит образы и раздаёт их по HTTP API: Docker Hub, GHCR, Quay, облачные (ECR, GCR/Artifact Registry, ACR), self-hosted (Harbor, Nexus, GitLab Registry).
- Слои хранятся по digest и **дедуплицируются**: общие слои не скачиваются повторно.
- Docker Hub ограничивает частоту анонимных скачиваний: для CI и кластеров нужны зеркало или прокси-кеш.
- Harbor добавляет сканирование уязвимостей, подпись, репликацию, политики хранения.

### Чистка места

```bash
docker system df                    # кто сколько занимает
docker image prune -a               # неиспользуемые образы
docker builder prune                # кеш сборки
docker system prune -a --volumes    # всё неиспользуемое, ВКЛЮЧАЯ тома (осторожно: данные!)
```

## Dockerfile: инструкции, кеш и multi-stage
id: dockerfile

> **Суть:** Dockerfile — рецепт сборки образа, выполняемый сверху вниз. Каждая инструкция кешируется, и при изменении одной **все последующие пересобираются**. Поэтому редко меняющиеся вещи (зависимости) идут выше часто меняющихся (код), а инструменты сборки остаются в отдельной стадии.

### Основные инструкции

| Инструкция | Что делает |
|---|---|
| `FROM` | базовый образ (начало стадии) |
| `RUN` | выполнить команду при сборке, результат — новый слой |
| `COPY` | скопировать файлы из контекста сборки |
| `ADD` | как COPY, плюс распаковка локальных tar и скачивание по URL (лучше избегать) |
| `WORKDIR` | рабочий каталог |
| `ENV` | переменная окружения — есть и при сборке, и **в контейнере** |
| `ARG` | переменная **только для сборки** (`--build-arg`) |
| `USER` | от какого пользователя запускать |
| `EXPOSE` | документация порта (сам порт не публикует) |
| `ENTRYPOINT`, `CMD` | что запускать |
| `HEALTHCHECK` | проверка здоровья |

**COPY и ADD**: используйте COPY — его поведение предсказуемо. ADD неожиданно распакует архив или скачает файл без проверки контрольной суммы.

**ARG и ENV**: `ARG` не попадает в окружение контейнера, но **виден в истории образа** (`docker history`) — поэтому секреты через ARG передавать нельзя. Для секретов при сборке — `RUN --mount=type=secret,id=npmrc ...` (BuildKit), они не сохраняются в слоях.

### Кеш сборки

Docker проверяет для каждой инструкции, есть ли в кеше слой с тем же родителем и той же инструкцией (для `COPY` — с тем же содержимым файлов). Первая же «промахнувшаяся» инструкция инвалидирует **все последующие**.

Плохо — любое изменение кода переустанавливает зависимости:
```dockerfile
COPY . .
RUN npm ci
```
Хорошо — зависимости кешируются, пока не изменился lock-файл:
```dockerfile
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
```
И обязательно `.dockerignore`: `node_modules`, `.git`, локальные `.env`, артефакты. Иначе контекст сборки огромный, кеш постоянно инвалидируется, а секреты попадают в образ.

Кеш в CI: раннеры часто «чистые», поэтому кеш передают явно: `docker buildx build --cache-from type=registry,ref=repo/app:cache --cache-to type=registry,ref=repo/app:cache,mode=max`. Для менеджеров пакетов — `RUN --mount=type=cache,target=/root/.cache/pip`.

### ENTRYPOINT и CMD

- **ENTRYPOINT** — исполняемый файл, «что это за контейнер».
- **CMD** — аргументы по умолчанию; легко переопределяются при `docker run image <аргументы>`.
- Вместе: `ENTRYPOINT ["python", "app.py"]` + `CMD ["--port", "8080"]`.

**Exec-форма** `["node", "server.js"]` — процесс запускается напрямую и становится **PID 1**, получает сигналы. **Shell-форма** `node server.js` превращается в `/bin/sh -c "node server.js"`: PID 1 становится shell, который не передаёт SIGTERM приложению. Итог — каждая остановка ждёт таймаут и заканчивается SIGKILL. Подробнее о сигналах и PID 1 — в [теории Linux](#/theory/linux/signals).

Если нужен entrypoint-скрипт для подготовки, последней строкой пишите `exec "$@"` — тогда приложение заменит shell и станет PID 1.

### Multi-stage сборка

Компиляторы, dev-зависимости и исходники не нужны в итоговом образе:
```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/api

FROM gcr.io/distroless/static:nonroot
COPY --from=build /app /app
USER nonroot
ENTRYPOINT ["/app"]
```
Итоговый образ — несколько мегабайт без shell и пакетного менеджера: меньше скачивать, меньше уязвимостей.

### Пример для Python

```dockerfile
FROM python:3.12-slim AS base
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app

FROM base AS deps
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM base
COPY --from=deps /install /usr/local
COPY . .
RUN useradd -r -u 10001 app
USER 10001
EXPOSE 8000
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]
```
`PYTHONUNBUFFERED=1` — чтобы логи сразу шли в stdout, а не застревали в буфере.

### Выбор базового образа

- `alpine` — маленький, но на **musl** вместо glibc: возможны проблемы с бинарными колёсами Python, DNS-поведением, производительностью.
- `-slim` (Debian) — компромисс размера и совместимости.
- **distroless** и `scratch` — только приложение и минимальные файлы; нет shell, отладка через `kubectl debug` или отладочные варианты образа.
- Версию базового образа фиксируют (`python:3.12.7-slim`, лучше с digest) и регулярно обновляют ради патчей безопасности (Renovate, Dependabot).

### Частые ошибки

1. `latest` в `FROM` — сборка невоспроизводима.
2. `COPY . .` до установки зависимостей — кеш не работает.
3. Нет `.dockerignore` — огромный контекст, секреты в образе.
4. `apt-get update` в отдельном `RUN` от `install` — устаревший кеш метаданных; не чистится `/var/lib/apt/lists`.
5. Запуск от root.
6. Секреты в `ENV`, `ARG` или скопированные файлы — остаются в слоях навсегда.
7. Shell-форма CMD — сигналы не доходят.
8. Несколько процессов в одном контейнере без init-системы.
9. Инструменты сборки в итоговом образе вместо multi-stage.

Проверка: линтер **hadolint**, сканеры **Trivy** и **Grype**.

## Запуск, падения, рестарты и healthcheck
id: lifecycle

> **Суть:** контейнер живёт, пока жив его **главный процесс** (PID 1). Код выхода этого процесса объясняет, почему контейнер остановился. Restart policy решает, перезапускать ли его, а HEALTHCHECK проверяет, что процесс не просто жив, а работает.

### Жизненный цикл

`created` → `running` → (`paused`) → `exited` → удалён. Контейнер останавливается, когда PID 1 завершается. Поэтому контейнер с `CMD ["bash"]` без терминала завершается сразу, а демон, ушедший в фон (nginx без `daemon off`), «убивает» свой контейнер: главный процесс завершился.

Остановка: `docker stop` шлёт **SIGTERM** (или `STOPSIGNAL` из образа), ждёт 10 секунд (`-t`), затем **SIGKILL**.

### Коды выхода

| Код | Значение |
|---|---|
| 0 | нормальное завершение (для сервиса это тоже проблема — он не должен завершаться) |
| 1 | ошибка приложения |
| 125 | ошибка самого docker run (неверный флаг) |
| 126 | команда найдена, но не исполняется (права) |
| 127 | команда не найдена (опечатка, нет бинарника в образе, CRLF в скрипте) |
| 137 | 128 + 9 — **SIGKILL**: OOM killer или не завершился за отведённое время |
| 139 | 128 + 11 — SIGSEGV |
| 143 | 128 + 15 — SIGTERM |

### Контейнер постоянно перезапускается: порядок разбора

1. `docker ps -a` — статус и код выхода; `docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' c`.
2. `docker logs c` (`--tail 100`, `-f`; для упавшего — логи последнего запуска тоже доступны).
3. По коду:
   - **137 + OOMKilled=true** — не хватает лимита памяти (`--memory`), смотреть потребление и утечки;
   - **127/126** — не тот entrypoint, нет файла, нет прав, скрипт с Windows-переводами строк;
   - **1** — читать лог приложения: нет переменной окружения, недоступна база, неверный конфиг;
   - **0** — процесс вышел сам: ушёл в фон (демон) или это разовая команда.
4. Запустить образ интерактивно и проверить руками: `docker run -it --entrypoint sh image`.
5. Проверить окружение и монтирования: `docker inspect` (Env, Mounts), права на тома (контейнер работает не от root, а том принадлежит root).
6. Зависимости: приложение стартует раньше базы и падает. Нужно ретраить подключение в приложении, а не надеяться на порядок запуска.

### Restart policy

| Политика | Поведение |
|---|---|
| `no` | не перезапускать (по умолчанию) |
| `on-failure[:N]` | только при ненулевом коде, не более N раз |
| `always` | всегда, в том числе после рестарта демона Docker; ручной `docker stop` уважается до перезапуска демона |
| `unless-stopped` | как always, но не поднимает контейнер, остановленный вручную, после рестарта демона |

Перезапуски идут с растущей задержкой, чтобы не крутить падающий контейнер в цикле. В Kubernetes перезапусками управляет kubelet (`restartPolicy` пода), а не Docker.

### HEALTHCHECK

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:8080/health || exit 1
```
- Статусы: `starting` → `healthy` / `unhealthy` (видно в `docker ps`).
- Сам Docker **не перезапускает** unhealthy-контейнер. Статус используют Docker Swarm, `depends_on: condition: service_healthy` в compose и внешние инструменты.
- В Kubernetes HEALTHCHECK из образа **игнорируется**: там есть свои liveness, readiness и startup пробы.
- Нужна утилита для проверки (`curl`, `wget`) в образе или встроенная команда приложения; в distroless их нет.

### Повседневные команды

```bash
docker ps -a; docker images
docker run -d --name api -p 8080:80 -e KEY=val -v data:/data image:tag
docker logs -f --tail 100 api
docker exec -it api sh              # зайти внутрь
docker inspect api                  # всё о контейнере: сеть, монтирования, окружение, состояние
docker stats                        # потребление ресурсов в реальном времени
docker cp api:/app/log.txt .
docker top api                      # процессы контейнера
docker events                       # события демона
```

## Сеть Docker
id: networking

> **Суть:** по умолчанию каждый контейнер получает свой сетевой namespace с интерфейсом в мосте `docker0`, выходит наружу через NAT, а снаружи доступен только через опубликованные порты (DNAT). В пользовательских сетях контейнеры находят друг друга по имени через встроенный DNS.

### Режимы

| Режим | Как работает | Когда |
|---|---|---|
| `bridge` (по умолчанию) | свой namespace, veth-пара в мост `docker0`, NAT наружу | обычные контейнеры на одном хосте |
| пользовательская bridge-сеть | то же, плюс **DNS по именам** контейнеров и изоляция от других сетей | compose, связанные сервисы |
| `host` | контейнер использует сеть хоста напрямую | максимальная производительность, сетевые агенты; нет изоляции, конфликты портов |
| `none` | только loopback | изолированные задачи |
| `container:<имя>` | общий namespace с другим контейнером | sidecar; так устроен под в Kubernetes |
| `overlay` | сеть между хостами (VXLAN) | Docker Swarm |
| `macvlan` / `ipvlan` | контейнер получает адрес в физической сети | интеграция с legacy-сетью |

### Как устроен bridge

```
контейнер eth0 (172.17.0.2) ⇄ veth ⇄ мост docker0 (172.17.0.1) ⇄ iptables NAT ⇄ eth0 хоста
```
- **Исходящий** трафик: SNAT (masquerade) в адрес хоста.
- **Входящий**: `-p 8080:80` создаёт правило DNAT «порт 8080 хоста → 172.17.0.2:80» (видно в `iptables -t nat -L -n`).
- Docker правит iptables сам, и его правила обходят правила `ufw`: опубликованный порт может оказаться открытым в интернет, хотя ufw «закрыт». Публикуйте только на нужный адрес: `-p 127.0.0.1:8080:80`.

### Общение контейнеров

- В **пользовательской** сети: `docker network create app`, контейнеры `api` и `db` в ней обращаются друг к другу по именам (`db:5432`) через встроенный DNS `127.0.0.11`.
- В сети `bridge` по умолчанию DNS по именам **нет** (только устаревшие `--link`).
- Контейнеру не нужно публиковать порт, чтобы к нему ходили соседи по сети: `-p` нужен только для доступа **с хоста и снаружи**.
- Доступ из контейнера к сервису на хосте: `host.docker.internal` (в Linux — с `--add-host=host.docker.internal:host-gateway`) или адрес шлюза моста.

### 0.0.0.0 и 127.0.0.1: «в контейнере работает, снаружи — нет»

- `127.0.0.1` — loopback **внутри своего** network namespace. Приложение, слушающее `127.0.0.1:8080` в контейнере, доступно только изнутри этого контейнера. DNAT от Docker приходит на интерфейс `eth0` контейнера, и соединение отклоняется.
- `0.0.0.0` — слушать на всех интерфейсах, включая `eth0` контейнера.

Многие dev-серверы по умолчанию слушают localhost (Flask, Vite, Rails в dev-режиме). Решение — настроить приложение на `0.0.0.0` (`--host 0.0.0.0`).

Порядок диагностики «не открывается снаружи»:
1. `docker ps` — опубликован ли порт и на какой адрес;
2. `docker exec c ss -tlnp` (или `nsenter -t PID -n ss -tlnp`) — на каком адресе слушает приложение;
3. `curl` изнутри контейнера, с хоста, извне — где обрывается цепочка;
4. файрвол хоста, Security Group облака.

## Данные: volumes, bind mounts и tmpfs
id: storage

> **Суть:** записываемый слой контейнера временный и медленный для данных — он исчезает вместе с контейнером. Постоянные данные хранят в **volumes** (управляет Docker) или **bind mounts** (каталог хоста), временные — в **tmpfs** (память).

### Три вида монтирования

| | Volume | Bind mount | tmpfs |
|---|---|---|---|
| Где лежат данные | `/var/lib/docker/volumes/<имя>/_data`, управляет Docker | любой путь на хосте | в памяти |
| Создание | `-v data:/var/lib/postgresql/data` | `-v /srv/conf:/etc/app:ro` | `--tmpfs /tmp` |
| Переносимость | не зависит от структуры хоста | зависит от путей хоста | — |
| Начальное содержимое | пустой том заполняется данными из образа | каталог хоста **перекрывает** содержимое образа | пусто |
| Для чего | данные БД, постоянное состояние | конфиги, исходники в разработке, сокеты | секреты, временные файлы |

Синтаксис `--mount type=volume,src=data,dst=/data` явнее, чем `-v`, и не создаёт молча пустой каталог на хосте, если путь опечатан.

### Подводные камни

- **Права**: контейнер работает от UID 10001, а каталог bind mount принадлежит root → `Permission denied`. Решения: `chown` каталога на нужный UID, создание каталога с правильными правами в образе (для volume), `--user`.
- **Bind mount перекрывает** содержимое образа: смонтировали пустой каталог хоста в `/app` — и код приложения «пропал».
- **SELinux**: для bind mount на RHEL нужен суффикс `:z` или `:Z`, иначе доступ запрещён меткой.
- **Volume не удаляется** вместе с контейнером (кроме анонимных при `docker rm -v`). Отсюда накопление «висящих» томов: `docker volume prune`.
- `docker system prune --volumes` удаляет данные безвозвратно.
- Производительность на Mac и Windows: bind mount идёт через границу ВМ и медленный.

### Бэкап тома

```bash
docker run --rm -v data:/data -v "$PWD":/backup alpine tar czf /backup/data.tgz -C /data .
```
Для баз данных правильнее логический или физический бэкап средствами СУБД (`pg_dump`, `pg_basebackup`), а не копирование файлов работающей БД.

### В Kubernetes

Аналоги: `emptyDir` (временный каталог пода, можно в памяти), `hostPath` (bind mount, избегать), PersistentVolume для постоянных данных — см. [хранение в Kubernetes](#/theory/kubernetes/storage).

## Архитектура: Docker, containerd, runc, CRI и Podman
id: runtimes

> **Суть:** «Docker» — это стопка компонентов. Внизу **runc** создаёт контейнер (namespaces, cgroups) по спецификации OCI, выше **containerd** управляет образами и жизненным циклом, ещё выше **dockerd** даёт удобный API и CLI. Kubernetes разговаривает с рантаймом через интерфейс **CRI**, и Docker для этого не нужен.

### Слои

```
docker CLI ──► dockerd (API, сборка, сети, тома)
                  │
                  ▼
              containerd (образы, снапшоты, жизненный цикл)
                  │
                  ▼
           containerd-shim ──► runc (создать namespaces, cgroups, запустить процесс и выйти)
```
- **runc** — низкоуровневый рантайм по спецификации **OCI runtime-spec**. Создал контейнер и завершился.
- **shim** — остаётся родителем процесса контейнера, держит его stdio и код выхода. Благодаря этому containerd и dockerd можно перезапускать, не убивая контейнеры.
- **containerd** — высокоуровневый рантайм: скачивает образы, распаковывает слои, управляет контейнерами. Есть свой CLI `ctr` и более удобный `nerdctl`.
- **dockerd** — то, что видит разработчик: `docker build`, сети, тома, compose.

Стандарты **OCI**: формат образа (image-spec), запуск (runtime-spec), раздача из реестра (distribution-spec). Поэтому образ, собранный Docker, запускается в containerd, CRI-O, Podman.

Альтернативные низкоуровневые рантаймы: **crun** (на C, быстрее), **gVisor** (`runsc`), **Kata Containers** — песочницы с более сильной изоляцией.

### CRI и уход Kubernetes от Docker

**CRI** (Container Runtime Interface) — gRPC-интерфейс, через который kubelet просит рантайм запустить под. containerd и **CRI-O** реализуют CRI напрямую. Docker CRI не реализовывал, и Kubernetes держал прослойку **dockershim**, которую удалили в версии 1.24.

Что это значит на практике:
- образы, собранные Docker, **продолжают работать** — это OCI-образы;
- на узлах вместо `docker ps` используют `crictl ps`, `crictl logs`, `crictl images`;
- то, что зависело от сокета Docker на узле (`/var/run/docker.sock` в подах для сборки образов, мониторинг через Docker API), перестало работать. Для сборки в кластере используют BuildKit, Kaniko, Buildah.

### Podman и rootless

**Podman** — совместимый с Docker CLI инструмент (Red Hat), но:
- **без демона**: каждый `podman run` — дочерний процесс вашего пользователя (через conmon), нет постоянного процесса от root с доступом ко всему;
- **rootless по умолчанию**: контейнеры работают от обычного пользователя с помощью **user namespace** — root внутри контейнера отображается на ваш непривилегированный UID на хосте (диапазоны `/etc/subuid`, `/etc/subgid`);
- умеет **поды** (группы контейнеров с общей сетью, как в Kubernetes) и генерирует YAML Kubernetes и юниты systemd (Quadlet).

Rootless-режим есть и в Docker. Ограничения rootless: нельзя слушать порты ниже 1024 без настройки, своя медленнее реализация сети (slirp4netns, pasta), часть функций cgroups требует делегирования (cgroup v2).

Почему важен **сокет Docker**: доступ к `/var/run/docker.sock` = root на хосте (можно запустить привилегированный контейнер с корнем хоста). Поэтому членство в группе `docker` равносильно root, а монтирование сокета в контейнер — серьёзный риск.

## Docker Compose
id: compose

> **Суть:** Compose описывает в одном YAML-файле набор контейнеров, их сети, тома и зависимости и поднимает всё одной командой. Идеален для локальной разработки, тестов в CI и небольших установок на одном хосте; не заменяет оркестратор.

### Пример

```yaml
services:
  api:
    build: .
    image: registry.example.com/api:${TAG:-dev}
    ports:
      - "127.0.0.1:8080:8080"
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 512M

  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data
    environment:
      POSTGRES_PASSWORD: secret
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

volumes:
  pgdata:
```
- Compose создаёт для проекта **отдельную сеть**, сервисы видят друг друга по имени (`db:5432`).
- Имя проекта (по умолчанию — имя каталога) становится префиксом контейнеров, сетей и томов.

### Команды

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f api
docker compose exec api sh
docker compose down          # остановить и удалить контейнеры и сеть
docker compose down -v       # ...и тома (данные!)
docker compose config        # итоговая конфигурация после подстановки переменных
```

### Подводные камни

- **`depends_on` без условия** ждёт только **запуска** контейнера, а не готовности сервиса. Нужен `condition: service_healthy` с healthcheck, а приложение всё равно должно ретраить подключение.
- Переменные: `.env` рядом с compose-файлом подставляется в **сам YAML** (`${TAG}`), а `env_file` передаёт переменные **в контейнер** — это разные вещи.
- Секреты в `environment` в репозитории — плохо; использовать `.env` вне git или `secrets:`.
- Тома переживают `down` и сохраняют старые данные: «почему база не пересоздалась с новым паролем?» — потому что `POSTGRES_PASSWORD` применяется только при инициализации пустого тома.
- Порты публикуются на `0.0.0.0` и обходят файрвол хоста — публикуйте на `127.0.0.1` то, что не должно быть доступно снаружи.
- Нет самовосстановления между хостами, rolling update, автомасштабирования — это задачи оркестратора.

Где уместен Compose: локальная разработка, интеграционные тесты в CI (поднять приложение с базой и брокером), небольшие сервисы на одном сервере. Несколько файлов: `compose.yaml` + `compose.override.yaml` (для разработки, подхватывается автоматически) или явные `-f`, а также `profiles`.

## Безопасность контейнеров
id: security

> **Суть:** безопасность строится в три слоя: **образ** (минимальный, без уязвимостей и секретов, подписанный), **запуск** (не root, без лишних capabilities, read-only ФС, лимиты) и **хост/платформа** (обновлённое ядро, изоляция, политики, мониторинг поведения).

### Образ

- **Минимальная база**: distroless, slim, scratch — меньше пакетов, меньше уязвимостей и инструментов для злоумышленника.
- **Сканирование уязвимостей**: Trivy, Grype, сканер реестра (Harbor, ECR) — в CI с порогом по критичности и регулярно для уже выпущенных образов (новые CVE появляются каждый день).
- **Никаких секретов** в слоях: проверка `gitleaks`/`trufflehog`, секреты при сборке через BuildKit secrets.
- **Фиксированные версии** и регулярные обновления базовых образов.
- **Подпись и происхождение**: cosign (Sigstore), SBOM (Syft), аттестации SLSA; в кластере проверка подписи при допуске (Kyverno, policy-controller).

### Запуск

- **Не root**: `USER 10001` в образе, `runAsNonRoot: true` в Kubernetes. Root в контейнере при побеге — root на хосте (если нет user namespaces).
- **Capabilities**: `--cap-drop ALL`, добавлять только нужное (`--cap-add NET_BIND_SERVICE`).
- **Без повышения привилегий**: `--security-opt no-new-privileges` (запрет SUID-повышения).
- **Read-only корень**: `--read-only` + `--tmpfs /tmp` для временных файлов.
- **Лимиты**: память, CPU, `--pids-limit` (защита от fork-бомбы).
- **seccomp** и **AppArmor/SELinux** — профили по умолчанию не отключать.
- **Никогда**: `--privileged` (почти полный доступ к хосту), монтирование `/var/run/docker.sock`, `hostPath` на `/`, `--pid=host` и `--net=host` без необходимости.

```bash
docker run --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges \
  --user 10001 --memory 256m --pids-limit 100 image:1.2.3
```

### Хост и платформа

- Обновлённое ядро и рантайм: уязвимости побега из контейнера исправляются именно там.
- **Rootless**-режим или user namespaces.
- Изоляция сильнее для недоверенного кода: gVisor, Kata, отдельные узлы.
- Сетевые политики: контейнеры видят только нужные сервисы.
- **Мониторинг поведения** во время работы: Falco, Tetragon — алерт на shell внутри контейнера, неожиданные процессы, запись в системные каталоги.
- В Kubernetes: Pod Security Standards (`restricted`), admission-политики (Kyverno, Gatekeeper).
