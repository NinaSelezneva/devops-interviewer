Главная идея Terraform: **код описывает, что должно быть, state помнит, что Terraform создал, а plan показывает разницу**. Почти все вопросы на собеседовании — о том, как эти три вещи взаимодействуют и что происходит, когда они расходятся.

Порядок глав: что такое IaC и чем отличаются инструменты → как работает Terraform → язык HCL → state → модули и окружения → рефакторинг, импорт и дрейф → секреты → тестирование и обновления.

## Infrastructure as Code: подходы и инструменты
id: concepts

> **Суть:** IaC — описание инфраструктуры кодом в Git вместо ручных действий в консоли: воспроизводимо, с ревью и историей. Инструменты отличаются подходом: **декларативный** (описать результат: Terraform) или **императивный** (описать шаги), а также тем, что они делают — **создают ресурсы** (Terraform, Pulumi, Crossplane) или **настраивают серверы** (Ansible).

### Зачем IaC

- **Воспроизводимость**: окружение поднимается из кода, staging и прод одинаковы.
- **Ревью и история**: изменения проходят через MR, видно кто, когда и зачем.
- **Скорость и масштаб**: десять одинаковых окружений — одна переменная.
- **Документация**: код показывает, что реально существует.
- **Восстановление после аварии**: инфраструктура пересоздаётся из кода.

### Декларативный и императивный

- **Декларативный**: «должно быть 3 сервера такого типа». Инструмент сам вычисляет, что создать, изменить или удалить. Повторный запуск без изменений ничего не делает (**идемпотентность**).
- **Императивный**: «создай сервер, потом ещё один». Повторный запуск создаст лишние, если скрипт сам не проверяет состояние.

### Mutable и immutable

- **Mutable** — серверы живут долго и меняются на месте (Ansible применяет новую конфигурацию). Риск — **дрейф** и «снежинки»: каждый сервер немного уникален.
- **Immutable** — сервер не меняют, а **заменяют** новым из заранее собранного образа. Предсказуемо, легко откатить (вернуть старый образ), подходит облакам и контейнерам.

### «Золотые» образы и Packer

**Packer** собирает образы ВМ (AMI, образы GCP, Azure, vSphere, qcow2) по шаблону: базовый образ → установка пакетов, агентов, харденинг (часто Ansible-ролью) → снапшот.
- Пайплайн образов: сборка по расписанию и при изменениях → тесты (Goss, InSpec) → сканирование уязвимостей → публикация с версией → Terraform ссылается на новую версию образа.
- Плюсы: быстрый старт инстансов (всё предустановлено), одинаковость, автоскейлинг без долгой настройки при запуске.
- Минус: любое изменение — пересборка образа; поэтому в образ кладут стабильную базу, а конфигурацию приложения — при запуске (cloud-init, переменные).

### Сравнение инструментов

| | Terraform / OpenTofu | Pulumi | Crossplane | Ansible | CloudFormation / Bicep |
|---|---|---|---|---|---|
| Язык | HCL | Python, TS, Go, C# | YAML (ресурсы Kubernetes) | YAML | YAML/JSON, Bicep |
| Модель | декларативная, state-файл | декларативная, программы на обычных языках | контроллеры Kubernetes, непрерывное согласование | процедурная, push по SSH | декларативная, состояние у облака |
| Облака | все | все | все | есть модули, но не основное | одно облако |
| Сильная сторона | экосистема, стандарт индустрии | логика, тесты на привычном языке | самообслуживание через Kubernetes API, исправление дрейфа | настройка ОС и приложений | интеграция с облаком |

Частая связка: **Terraform** создаёт сеть, кластеры, базы данных; **Packer** собирает образы; **Ansible** настраивает ОС там, где есть долгоживущие серверы; приложения в Kubernetes деплоятся через **Helm и GitOps**.

**OpenTofu** — форк Terraform в Linux Foundation после смены лицензии Terraform на BSL (2023), совместим по языку и state.

## Как работает Terraform: блоки, провайдеры, граф, plan и apply
id: terraform-basics

> **Суть:** Terraform читает конфигурацию, через **провайдеры** узнаёт реальное состояние ресурсов, сравнивает его с кодом и state, строит **граф зависимостей** и показывает **план** изменений. `apply` выполняет план, вызывая API облака параллельно в порядке зависимостей.

### Основные блоки

```hcl
terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
  backend "s3" {
    bucket = "acme-tfstate"
    key    = "prod/network/terraform.tfstate"
    region = "eu-central-1"
  }
}

provider "aws" {
  region = var.region
}

variable "region" {
  type    = string
  default = "eu-central-1"
}

data "aws_availability_zones" "available" {}        # чтение существующего

resource "aws_vpc" "main" {                           # управляемый ресурс
  cidr_block = "10.0.0.0/16"
  tags       = { Name = "main" }
}

locals {
  azs = slice(data.aws_availability_zones.available.names, 0, 3)
}

module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"
  vpc_id  = aws_vpc.main.id
}

output "vpc_id" {
  value = aws_vpc.main.id
}
```

| Блок | Назначение |
|---|---|
| `terraform` | версии Terraform и провайдеров, backend |
| `provider` | настройки провайдера: регион, учётные данные, alias для нескольких регионов |
| `resource` | объект, которым Terraform **управляет** (создаёт, меняет, удаляет) |
| `data` | **чтение** существующего объекта, не управляемого этой конфигурацией |
| `variable` | входные параметры |
| `locals` | вычисляемые значения внутри модуля |
| `output` | выходные значения (для других модулей, CI, людей) |
| `module` | вызов модуля |
| `moved`, `import`, `removed` | рефакторинг и импорт (см. [Рефакторинг](#/theory/iac/refactoring)) |

### Провайдеры

Провайдер — плагин, который переводит ресурсы Terraform в вызовы API (AWS, GCP, Kubernetes, Cloudflare, Vault, GitHub). Скачивается при `terraform init` из реестра; точные версии фиксируются в **`.terraform.lock.hcl`** — этот файл коммитят.

### Жизненный цикл команд

```bash
terraform init        # скачать провайдеры и модули, настроить backend
terraform fmt         # форматирование
terraform validate    # синтаксис и типы
terraform plan -out=tfplan   # план изменений
terraform apply tfplan       # применить именно этот план
terraform destroy
```
В CI план сохраняют (`-out`) и применяют **тот же** файл плана после ревью — иначе между plan и apply мир может измениться.

### Как строится план

1. **Refresh**: провайдер читает реальное состояние ресурсов из state через API.
2. **Сравнение** реального состояния с конфигурацией.
3. **План** по каждому ресурсу: `+` create, `~` update in-place, `-/+` **replace** (удалить и создать — часто из-за изменения неизменяемого атрибута, например имени или подсети), `-` destroy, `<=` read.
4. **Граф зависимостей**: ссылки (`aws_vpc.main.id`) создают неявные зависимости, `depends_on` — явные. Независимые ресурсы создаются **параллельно** (по умолчанию 10 одновременно).

Внимательно смотреть на **replace** в плане: пересоздание базы данных или диска с данными — потеря данных. Защита: `lifecycle { prevent_destroy = true }`, а также защита от удаления на стороне облака (deletion protection).

### lifecycle

```hcl
lifecycle {
  create_before_destroy = true      # сначала создать замену, потом удалить старое (без простоя)
  prevent_destroy       = true      # запретить удаление (plan упадёт)
  ignore_changes        = [tags["LastModified"], desired_count]   # не трогать поля, которые меняют извне
  replace_triggered_by  = [aws_launch_template.app]
}
```

## Язык HCL: переменные, выражения, count и for_each
id: hcl

> **Суть:** HCL — декларативный язык с типами, выражениями и функциями. Входные данные приходят через **переменные** (с чётким порядком приоритета), промежуточные вычисления — в **locals**. Для нескольких однотипных ресурсов есть `count` (по номеру) и `for_each` (по ключу); `for_each` почти всегда безопаснее.

### Переменные и их приоритет

```hcl
variable "instance_type" {
  type        = string
  description = "Тип инстанса"
  default     = "t3.small"
  validation {
    condition     = can(regex("^t3\\.", var.instance_type))
    error_message = "Разрешены только t3."
  }
}
variable "db_password" {
  type      = string
  sensitive = true          # не показывать в выводе plan
}
```
Источники значений, **от низшего приоритета к высшему** (последний побеждает):
1. `default` в объявлении;
2. переменные окружения `TF_VAR_instance_type`;
3. файл `terraform.tfvars`;
4. `terraform.tfvars.json`;
5. файлы `*.auto.tfvars` (в алфавитном порядке);
6. `-var-file=prod.tfvars` и `-var 'instance_type=t3.large'` в командной строке — в порядке указания.

Если значение не задано нигде и нет default, Terraform спросит его интерактивно (в CI это ошибка — используйте `-input=false`).

Типы: `string`, `number`, `bool`, `list(...)`, `set(...)`, `map(...)`, `object({...})`, `tuple`, `optional()` для полей объектов.

### Выражения и функции

```hcl
locals {
  name_prefix = "${var.project}-${var.env}"
  is_prod     = var.env == "prod"
  instance    = local.is_prod ? "m6i.large" : "t3.small"
  subnets     = [for i, az in local.azs : cidrsubnet(var.vpc_cidr, 4, i)]
  tags        = merge(var.common_tags, { Environment = var.env })
}
```
Полезные функции: `cidrsubnet` (разбиение сети), `merge`, `lookup`, `try`, `coalesce`, `jsonencode`, `templatefile`, `file`, `toset`, `flatten`. Попробовать — `terraform console`.

**Dynamic blocks** — генерация вложенных блоков:
```hcl
dynamic "ingress" {
  for_each = var.ports
  content {
    from_port   = ingress.value
    to_port     = ingress.value
    protocol    = "tcp"
    cidr_blocks = ["10.0.0.0/8"]
  }
}
```

### count и for_each

```hcl
resource "aws_instance" "web" {
  count = 3
  tags  = { Name = "web-${count.index}" }
}
# адреса: aws_instance.web[0], [1], [2]

resource "aws_iam_user" "u" {
  for_each = toset(["alice", "bob", "carol"])
  name     = each.key
}
# адреса: aws_iam_user.u["alice"], ["bob"], ["carol"]
```

**Проблема count**: ресурсы адресуются по **индексу**. Удалите `bob` из середины списка `["alice", "bob", "carol"]` — `carol` сдвинется с индекса 2 на 1. Terraform увидит: «ресурс [1] теперь должен быть carol (изменить или пересоздать), ресурс [2] удалить». Пострадал ресурс, который вы не трогали.

С **for_each** адрес — **ключ**: удаление `bob` удаляет только `["bob"]`.

Правила:
- `count` — для «0 или 1» (условное создание: `count = var.enabled ? 1 : 0`) и для действительно одинаковых безымянных копий;
- `for_each` — для наборов объектов с идентичностью (пользователи, подсети, бакеты);
- ключи `for_each` должны быть известны **на этапе plan**: нельзя использовать значения, которые появятся только после создания других ресурсов (ID). Ошибка «The for_each value depends on resource attributes that cannot be determined until apply».

- Когда `count` всё же уместен?

## State: зачем он нужен и как с ним работать в команде
id: state

> **Суть:** state — карта соответствия «ресурс в коде ↔ реальный объект в облаке» (по ID) плюс кеш атрибутов и зависимостей. Без него Terraform не знает, что уже создал. В команде state хранят в **удалённом backend с блокировкой**, шифрованием и версионированием, а не в Git.

### Зачем нужен state

1. **Сопоставление**: в коде `aws_instance.web`, в облаке `i-0abc123`. Только state знает, что это один и тот же объект. Без него Terraform создаст дубликат.
2. **Удаление**: убрали ресурс из кода → Terraform по state понимает, что его нужно удалить. Без state он бы просто «забыл» о нём.
3. **Зависимости** для правильного порядка удаления, когда кода уже нет.
4. **Производительность**: кеш атрибутов (можно обойти полный опрос API через `-refresh=false`).

### Удалённый backend

| Backend | Блокировка |
|---|---|
| S3 | файл блокировки в том же бакете (`use_lockfile = true`, Terraform ≥ 1.10); раньше — таблица DynamoDB |
| GCS, Azure Blob | встроенная |
| Terraform Cloud / HCP, Spacelift, env0 | встроенная, плюс запуски, политики, UI |
| GitLab managed state | встроенная по HTTP |

Требования:
- **блокировка** — два одновременных `apply` повредят state или создадут дубликаты;
- **шифрование** — в state лежат секреты в открытом виде (пароли БД, ключи, если они были атрибутами ресурсов);
- **версионирование** бакета — откат к предыдущей версии при повреждении;
- **минимальный доступ**: читать state — значит читать секреты;
- **не в Git**.

### Разделение state

Один огромный state на всё — плохо: долгий plan, большой радиус поражения ошибки, конфликты блокировок между командами. Делят по:
- **окружениям** (dev, stage, prod — отдельные state, лучше и отдельные аккаунты облака);
- **слоям** с разной частотой изменений: сеть → кластеры и базы → приложения;
- **командам** и зонам ответственности.

Связь между state: `terraform_remote_state` (читать outputs другого state — но получает доступ ко всему state) или, лучше, **data sources** по тегам и именам, SSM Parameter Store, явная передача через Terragrunt.

### Команды работы со state

```bash
terraform state list
terraform state show aws_instance.web
terraform state mv aws_instance.web aws_instance.app     # переименовать (лучше блоком moved)
terraform state rm aws_instance.legacy                   # забыть ресурс, не удаляя его
terraform import aws_instance.web i-0abc123              # (лучше блоком import)
terraform state pull > backup.tfstate                    # снять копию
terraform force-unlock <LOCK_ID>
```
Любые операции со state — после резервной копии и с пониманием, что делаете.

### Workspaces

`terraform workspace new staging` — несколько state для одной конфигурации. Удобно для временных одинаковых окружений, но для dev/prod многие предпочитают **отдельные каталоги** или Terragrunt: разные backend и учётные данные, явная разница в коде, меньше шансов применить к проду по ошибке.

### apply упал посередине или state заблокирован

**Блокировка «висит»** (`Error acquiring the state lock`):
1. Убедиться, что **никто реально не выполняет** apply (CI-джоб, коллега) — в ошибке указаны кто и когда.
2. Только потом `terraform force-unlock <ID>`. Снятие блокировки при работающем apply — путь к повреждённому state.

**apply упал посередине** (таймаут API, нет прав, квота):
- Terraform записывает в state всё, что **успел создать**: ресурсы не «теряются», state обновляется по мере работы.
- Ресурс, созданный частично, помечается **tainted** и будет пересоздан при следующем apply.
- Действия: прочитать ошибку → исправить причину → `terraform plan` (увидеть, что осталось) → `apply`. Обычно этого достаточно.
- Если ресурс создан в облаке, но не попал в state (сбой в момент записи) — **импортировать** его, иначе следующий apply попытается создать дубликат и упадёт на конфликте имён.
- Если state повреждён — восстановить предыдущую версию из версионированного бакета.

## Модули, структура окружений и Terragrunt
id: modules-structure

> **Суть:** модуль — переиспользуемый каталог с ресурсами, входами (`variable`) и выходами (`output`). Окружения строят из одних и тех же модулей с разными параметрами, а их state разделяют. Terragrunt убирает дублирование конфигурации backend и параметров между десятками окружений и компонентов.

### Модули

```hcl
module "vpc" {
  source   = "git::https://git.example.com/infra/modules.git//vpc?ref=v1.4.0"
  name     = "prod"
  cidr     = "10.0.0.0/16"
  azs      = ["eu-central-1a", "eu-central-1b", "eu-central-1c"]
}
resource "aws_eks_cluster" "this" {
  vpc_config { subnet_ids = module.vpc.private_subnet_ids }
}
```
Источники: локальный путь, Git с **тегом версии** (`?ref=v1.4.0`), реестр модулей (с `version`).

Хороший модуль:
- решает одну задачу (сеть, кластер, база), а не «всё сразу»;
- имеет понятный интерфейс: типизированные переменные с описаниями и валидацией, необходимые outputs;
- версионируется и имеет changelog;
- не создаёт провайдеров внутри (их передают из корневого модуля);
- не слишком тонкая обёртка над одним ресурсом — такие модули добавляют сложность без пользы.

### Структура для нескольких окружений

Вариант с каталогами:
```
modules/
  network/  eks/  rds/
envs/
  dev/
    network/   main.tf  backend.tf  terraform.tfvars
    eks/
  prod/
    network/
    eks/
```
- каждое окружение и компонент — свой **корневой модуль** со своим state;
- окружения отличаются **параметрами** и версией модулей: новую версию модуля сначала выкатывают в dev, потом в prod;
- лучше отдельные **аккаунты облака** для окружений: изоляция прав, лимитов и счетов;
- минус — дублирование `backend.tf`, `provider`, вызовов модулей.

Почему не workspaces для dev/prod: один и тот же код без возможности различий в структуре, один backend и учётные данные, легко ошибиться с выбранным workspace.

### Terragrunt

Тонкая обёртка над Terraform/OpenTofu для больших инфраструктур:
```hcl
# live/prod/eks/terragrunt.hcl
include "root" { path = find_in_parent_folders("root.hcl") }

terraform {
  source = "git::https://git.example.com/infra/modules.git//eks?ref=v2.1.0"
}

dependency "vpc" {
  config_path = "../vpc"
}

inputs = {
  cluster_name = "prod"
  subnet_ids   = dependency.vpc.outputs.private_subnet_ids
}
```
Что даёт:
- **DRY backend**: конфигурация state задаётся один раз в корне и генерируется для каждого компонента (ключ по пути каталога);
- **зависимости между компонентами** с передачей outputs;
- запуск по многим компонентам с учётом порядка (`terragrunt run --all plan`);
- общие параметры на уровне аккаунта или региона через иерархию файлов.

Когда нужен: десятки компонентов и окружений, много аккаунтов. Когда лишний: небольшая инфраструктура — обычных каталогов и модулей хватает, а Terragrunt добавляет ещё один инструмент и уровень абстракции. Альтернативы оркестрации: Terraform Stacks, Atlantis, Spacelift, Terramate.

## Рефакторинг, импорт и дрейф
id: refactoring

> **Суть:** адрес ресурса в коде — его идентичность в state. Если просто переименовать ресурс или перенести в модуль, Terraform решит «старый удалить, новый создать». Блоки **`moved`**, **`import`** и **`removed`** позволяют менять код, не трогая реальные объекты. **Дрейф** — расхождение реальности с кодом из-за ручных изменений; его обнаруживают регулярным plan и предотвращают процессом.

### Переименование и перенос в модуль

```hcl
moved {
  from = aws_instance.web
  to   = aws_instance.app
}

moved {
  from = aws_s3_bucket.logs
  to   = module.logging.aws_s3_bucket.this
}

moved {
  from = aws_iam_user.u[1]          # переход с count на for_each
  to   = aws_iam_user.u["bob"]
}
```
- Plan покажет `has moved to` вместо destroy/create.
- В отличие от `terraform state mv`, блок `moved` в коде проходит ревью, применяется во **всех** окружениях одинаково и работает для потребителей модуля.
- Блоки `moved` держат в коде, пока все state не применили изменение (в модулях — долго).

### Импорт существующих ресурсов

Ресурс создан вручную или другим инструментом, нужно взять под управление:
```hcl
import {
  to = aws_s3_bucket.legacy
  id = "acme-legacy-bucket"
}
```
```bash
terraform plan -generate-config-out=generated.tf   # Terraform сгенерирует черновик кода ресурса
```
Процесс: сгенерировать или написать код → добиться plan **без изменений** (код точно описывает реальность) → apply (импорт записывается в state) → удалить блок `import`. Импорт в массовом порядке — Terraformer, или генерация блоков `import` скриптом.

### Удаление из управления без удаления ресурса

```hcl
removed {
  from = aws_instance.legacy
  lifecycle { destroy = false }      # забыть, но не удалять в облаке
}
```
Аналог `terraform state rm`, но через код и ревью. Применяется при переносе ресурса в другой state: в новом — `import`, в старом — `removed`.

### Дрейф

**Дрейф** — реальное состояние отличается от описанного: кто-то поменял Security Group в консоли, автомасштабирование изменило число инстансов, другой инструмент поменял теги.

Обнаружение:
- `terraform plan` показывает изменения, которых нет в коде; `terraform plan -refresh-only` — только расхождения с реальностью без изменений кода;
- **регулярный plan по расписанию** в CI (например, каждую ночь) с алертом при ненулевом плане (`-detailed-exitcode`: код 2 — есть изменения);
- платформы (Terraform Cloud, Spacelift) имеют встроенное обнаружение дрейфа.

Что делать с найденным дрейфом:
- изменение было **ошибкой** — `apply` вернёт как в коде;
- изменение **нужное** (горячий фикс во время инцидента) — перенести в код, чтобы plan стал пустым;
- поле **законно управляется извне** (desired_count от автоскейлера) — `ignore_changes`.

Предотвращение:
- права на изменения в продакшене только у CI, у людей — чтение (break-glass доступ для аварий с аудитом);
- все изменения через MR с plan в комментарии (Atlantis, CI);
- политики и SCP в облаке, запрещающие ручные изменения;
- дрейф часто сигнализирует, что процесс неудобен: если инженеры правят руками, значит, путь через код слишком медленный.

## Секреты в Terraform
id: secrets

> **Суть:** главная ловушка — **секреты попадают в state** в открытом виде, даже если отмечены `sensitive`. Поэтому state защищают как секрет, а сами секреты стараются вообще не пропускать через Terraform: генерировать и хранить их в менеджере секретов, передавать ссылками, использовать временные учётные данные.

### Где секреты утекают

- **state**: атрибуты ресурсов (пароль `aws_db_instance`, ключ `tls_private_key`, `random_password`) сохраняются открытым текстом;
- **код и tfvars** в Git;
- **вывод plan и логи CI** (без `sensitive`);
- **outputs**;
- переменные окружения в логах.

### Что делать

1. **Защитить state**: шифрование backend (KMS), строгий доступ, версионирование, отдельные state для чувствительных компонентов.
2. **`sensitive = true`** для переменных и outputs — скрывает значения в выводе plan и apply. Но **не** из state.
3. **Не хранить секреты в коде**: значения приходят из переменных окружения CI (`TF_VAR_db_password` из защищённой переменной) или из менеджера секретов.
4. **Читать из менеджера секретов**: `data "vault_kv_secret_v2"`, `data "aws_secretsmanager_secret_version"`. Значение всё равно окажется в state, если его передать в атрибут ресурса.
5. **Лучше — не пропускать секрет через Terraform вовсе**:
   - пусть облако генерирует и хранит секрет само: `manage_master_user_password = true` в RDS — пароль создаётся и хранится в Secrets Manager, в state только ссылка;
   - приложение читает секрет из менеджера во время работы (External Secrets, Vault Agent, CSI driver), Terraform создаёт только **пустой** секрет и права доступа к нему;
   - **write-only** атрибуты (`*_wo`) и эфемерные ресурсы (`ephemeral`) в новых версиях Terraform — значения используются при apply, но не сохраняются в state.
6. **Учётные данные самого Terraform**: никаких статических ключей облака в CI — **OIDC**-федерация и роли с минимальными правами; динамические секреты Vault.
7. **SOPS** — если секреты всё же нужно хранить рядом с кодом: зашифрованный файл в Git, расшифровка провайдером `sops` или в CI.

## Тестирование, проверки и обновления версий
id: testing-lifecycle

> **Суть:** Terraform-код проверяют на нескольких уровнях: форматирование и валидация → линтеры и сканеры безопасности → политики над планом → тесты модулей (`terraform test`, Terratest) → ревью плана человеком. Версии Terraform, провайдеров и модулей фиксируют и обновляют осознанно, сначала в непродуктивных окружениях.

### Уровни проверок

| Уровень | Инструменты | Что ловит |
|---|---|---|
| Форматирование и синтаксис | `terraform fmt -check`, `terraform validate` | ошибки синтаксиса и типов |
| Линтеры | **TFLint** (с плагинами облаков) | неверные типы инстансов, устаревший синтаксис, неиспользуемые переменные |
| Безопасность | **Trivy** (бывший tfsec), **Checkov**, KICS | открытые бакеты, `0.0.0.0/0` в Security Group, отсутствие шифрования |
| Политики | **OPA/Conftest**, Sentinel | правила компании над **планом**: обязательные теги, разрешённые регионы, запрет удаления БД |
| Тесты модулей | **`terraform test`** (`.tftest.hcl`), **Terratest** (Go) | модуль действительно создаёт работающую инфраструктуру |
| Стоимость | Infracost | сколько изменение добавит к счёту |
| Ревью | plan в комментарии MR (Atlantis, CI) | всё остальное |

`terraform test`:
```hcl
# tests/vpc.tftest.hcl
run "creates_three_private_subnets" {
  command = plan
  assert {
    condition     = length(aws_subnet.private) == 3
    error_message = "Ожидалось 3 приватные подсети"
  }
}
```
`command = plan` — быстрые проверки логики без создания ресурсов; `command = apply` — интеграционный тест в тестовом аккаунте с последующим удалением. Возможны **моки провайдеров**.

Политики над планом: `terraform show -json tfplan > plan.json` → Conftest проверяет JSON правилами на Rego.

### Пайплайн для Terraform

1. MR: `fmt`, `validate`, TFLint, сканер безопасности, `plan` для затронутых компонентов, политики, plan в комментарий.
2. Ревью плана.
3. После мержа: `apply` **сохранённого** плана (или повторный plan с проверкой, что он не изменился).
4. Регулярно: plan для обнаружения дрейфа.

### Обновление версий

Ограничения версий:
```hcl
terraform {
  required_version = "~> 1.9.0"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.60" }   # 5.60 и новее в пределах 5.x
  }
}
```
- Точные версии провайдеров фиксирует **`.terraform.lock.hcl`** (коммитить!). Обновление — `terraform init -upgrade`, изменение lock-файла проходит ревью.
- Версии модулей — через `ref` или `version`.

Процесс обновления:
1. Прочитать changelog и upgrade guide (особенно мажорные версии провайдеров: удалённые атрибуты, изменение поведения по умолчанию).
2. Обновлять **по одному**: сначала Terraform, потом провайдеры, не всё сразу.
3. Обновить в dev, посмотреть **plan**: он должен быть пустым или содержать понятные изменения. Неожиданные `replace` — стоп.
4. Затем stage и prod.
5. Автоматизация: Renovate или Dependabot создают MR с обновлениями, CI показывает plan.

Важно: state, записанный новой версией Terraform, может не читаться старой — все участники и CI должны обновиться синхронно (отсюда фиксация `required_version`).
