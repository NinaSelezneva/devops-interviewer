DevOps-инженер редко пишет сложные запросы, но отвечает за то, чтобы база данных **не теряла данные, переживала отказы и не тормозила**. Поэтому главы идут от того, как БД обеспечивает надёжность изнутри, к эксплуатации: транзакции и MVCC → SQL и индексы → WAL → VACUUM → репликация → отказоустойчивость → бэкапы → подключения и права → диагностика → логика в БД → выбор БД и Kubernetes. Примеры — на PostgreSQL, самой частой СУБД на собеседованиях.

## Транзакции, ACID, уровни изоляции и MVCC
id: transactions

> **Суть:** транзакция — группа операций, которая выполняется **целиком или никак**. Свойства **ACID** гарантируют атомарность, согласованность, изоляцию и долговечность. PostgreSQL реализует изоляцию через **MVCC**: каждая транзакция видит свой согласованный снимок данных, и читатели не блокируют писателей.

### Транзакция

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;        -- или ROLLBACK, чтобы отменить всё
```
Если между двумя `UPDATE` сервер упадёт, после восстановления не будет «списали, но не зачислили»: незавершённая транзакция откатывается. `SAVEPOINT` позволяет откатиться к промежуточной точке внутри транзакции.

Без явного `BEGIN` каждая команда — отдельная транзакция (autocommit).

### ACID

| Свойство | Значение | Как обеспечивается в PostgreSQL |
|---|---|---|
| **Atomicity** — атомарность | всё или ничего | статус транзакции в журнале; незафиксированные изменения невидимы и считаются откатившимися |
| **Consistency** — согласованность | после транзакции данные удовлетворяют всем ограничениям | constraints, foreign keys, триггеры |
| **Isolation** — изоляция | параллельные транзакции не мешают друг другу (в рамках уровня изоляции) | MVCC и блокировки |
| **Durability** — долговечность | зафиксированное не потеряется при сбое | WAL сбрасывается на диск до подтверждения COMMIT (см. [WAL](#/theory/databases/wal)) |

### Аномалии и уровни изоляции

Аномалии параллельного доступа:
- **грязное чтение** — видны незафиксированные изменения другой транзакции;
- **неповторяющееся чтение** — повторное чтение строки даёт другое значение (её изменили и зафиксировали);
- **фантомы** — повторный запрос с условием возвращает другой набор строк;
- **аномалия сериализации** — результат параллельных транзакций невозможен ни при каком последовательном порядке (например, write skew: двое дежурных одновременно снимают себя с дежурства, проверив, что «другой ещё дежурит»).

| Уровень | Грязное чтение | Неповторяющееся | Фантомы | Сериализация |
|---|---|---|---|---|
| Read Uncommitted (в PG = Read Committed) | нет | возможно | возможно | возможно |
| **Read Committed** (по умолчанию в PG) | нет | возможно | возможно | возможно |
| Repeatable Read | нет | нет | нет (в PG) | возможно |
| Serializable | нет | нет | нет | нет |

- **Read Committed**: каждый **запрос** видит данные, зафиксированные к его началу.
- **Repeatable Read**: вся **транзакция** видит снимок на момент первого запроса.
- **Serializable**: PostgreSQL отслеживает опасные зависимости и **откатывает** одну из транзакций с ошибкой сериализации — приложение должно **повторить** транзакцию.

Более строгий уровень — меньше аномалий, но больше откатов и ожиданий. Для конкретных случаев используют явные блокировки: `SELECT ... FOR UPDATE`.

### MVCC

**Multi-Version Concurrency Control**: при изменении строки PostgreSQL не перезаписывает её, а создаёт **новую версию** (кортеж). У каждой версии есть `xmin` (транзакция, создавшая её) и `xmax` (транзакция, удалившая или заменившая её). Транзакция по своему **снимку** решает, какие версии ей видны.

Следствия:
- **читатели не блокируют писателей и наоборот** — главное преимущество;
- `UPDATE` = вставка новой версии + пометка старой; `DELETE` = пометка;
- старые версии (**мёртвые кортежи**) остаются в таблице, пока их не уберёт **VACUUM** (см. [VACUUM](#/theory/databases/vacuum));
- **долгие транзакции** мешают очистке: пока открыта транзакция со старым снимком, версии, которые ей могут понадобиться, удалять нельзя. Поэтому `idle in transaction` — враг здоровья базы.

Блокировки всё же есть: две транзакции, меняющие **одну строку**, — вторая ждёт первую. DDL (`ALTER TABLE`) берёт сильные блокировки, и даже короткая операция может встать в очередь за долгим запросом и заблокировать всех за собой — отсюда `lock_timeout` для миграций. Взаимные блокировки (**deadlock**) PostgreSQL обнаруживает и откатывает одну из транзакций.

## SQL: JOIN, индексы и планы запросов
id: sql-indexes

> **Суть:** JOIN соединяет строки таблиц по условию: INNER — только совпадения, LEFT — все слева плюс совпадения справа. **Индекс** — отдельная структура (обычно B-tree), позволяющая найти строки без полного просмотра таблицы. Использует ли база индекс, показывает `EXPLAIN ANALYZE`; индекс не помогает, если запрос возвращает большую часть таблицы или условие написано так, что индекс неприменим.

### Виды JOIN

```sql
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;
```

| JOIN | Результат |
|---|---|
| `INNER JOIN` | только пары, где условие выполнено |
| `LEFT JOIN` | все строки левой таблицы; для несовпавших — NULL справа |
| `RIGHT JOIN` | все строки правой таблицы |
| `FULL JOIN` | все строки обеих таблиц |
| `CROSS JOIN` | декартово произведение (каждая с каждой) |
| self join | таблица с самой собой (сотрудник и его руководитель) |

Типичные задачи: «пользователи без заказов» — `LEFT JOIN ... WHERE o.id IS NULL` (или `NOT EXISTS`). Ловушка: условие на правую таблицу в `WHERE` превращает LEFT JOIN в INNER (строки с NULL отфильтровываются) — такое условие пишут в `ON`.

Агрегация: `GROUP BY` с `COUNT`, `SUM`, `AVG`; фильтр по агрегату — `HAVING`.

### Индексы

**B-tree** (по умолчанию) — сбалансированное дерево по отсортированным значениям: поиск по равенству и диапазону, сортировка, `LIKE 'abc%'`. Поиск — O(log N) вместо полного просмотра.

Другие типы в PostgreSQL:
- **Hash** — только равенство;
- **GIN** — массивы, JSONB, полнотекстовый поиск, `pg_trgm` для `LIKE '%abc%'`;
- **GiST**, **SP-GiST** — геоданные, диапазоны;
- **BRIN** — очень большие таблицы с естественным порядком (время вставки логов): крошечный индекс по блокам.

Варианты:
- **составной** `(user_id, created_at)` — работает для условий по первой колонке или по обеим; порядок колонок важен (сначала равенство, потом диапазон);
- **частичный** `WHERE status = 'active'` — меньше и быстрее;
- **по выражению** `ON lower(email)`;
- **покрывающий** `INCLUDE (total)` — запрос обслуживается только индексом (index-only scan).

### Когда индекс не помогает

1. **Низкая селективность**: условие выбирает большую долю таблицы (`status = 'active'` у 90% строк). Последовательное чтение таблицы быстрее, чем тысячи случайных переходов по индексу — планировщик правильно выбирает Seq Scan.
2. **Функция или выражение над колонкой**: `WHERE lower(email) = ...`, `WHERE created_at::date = ...`, `WHERE id + 1 = 5` — нужен индекс по выражению или переписать условие.
3. **Несоответствие типов** (сравнение с другим типом, неявное приведение).
4. **`LIKE '%abc'`** — ведущий подстановочный символ (нужен trigram GIN).
5. **Составной индекс без первой колонки** в условии.
6. **`OR`** по разным колонкам (иногда спасает BitmapOr или переписывание на UNION).
7. **Устаревшая статистика** — планировщик ошибается в оценке числа строк (`ANALYZE`).
8. **Маленькая таблица** — проще прочитать целиком.

Цена индексов: место, замедление `INSERT`/`UPDATE`/`DELETE` (каждый индекс обновляется), меньше HOT-обновлений. Неиспользуемые индексы находят в `pg_stat_user_indexes` (`idx_scan = 0`) и удаляют.

Создание на продакшене — без блокировки записи: `CREATE INDEX CONCURRENTLY`.

### EXPLAIN

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10;
```
- `EXPLAIN` — план с **оценками**; `ANALYZE` — реально выполняет и показывает **фактическое** время и число строк (осторожно с `UPDATE`/`DELETE` — оборачивать в транзакцию с откатом); `BUFFERS` — сколько страниц прочитано из кеша и с диска.
- Узлы: `Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Heap Scan`; соединения `Nested Loop` (мало строк снаружи + индекс внутри), `Hash Join` (большие наборы, равенство), `Merge Join` (отсортированные входы); `Sort`, `Aggregate`.
- Главное, что искать: **большое расхождение оценки и факта** числа строк (статистика, коррелированные колонки), Seq Scan по большой таблице с маленьким результатом, сортировки на диске (`external merge` — мало `work_mem`), Nested Loop с миллионами итераций.
- Удобная визуализация: explain.dalibo.com, explain.depesz.com.

## WAL, checkpoint и архивирование
id: wal

> **Суть:** **WAL** (журнал упреждающей записи) — сначала изменение записывается в последовательный журнал и сбрасывается на диск, и только потом, когда-нибудь, меняются сами файлы данных. Это даёт долговечность при сбоях и быструю запись. **Checkpoint** периодически сбрасывает изменённые страницы на диск, чтобы ограничить объём журнала для восстановления. **Архив WAL** — основа репликации и восстановления на момент времени (PITR).

### Зачем WAL

Таблицы и индексы лежат на диске страницами по 8 КБ. Если при каждом `COMMIT` писать все изменённые страницы в файлы данных, будет много случайной записи, и сбой посреди записи оставит файлы в несогласованном состоянии.

Решение:
1. Изменения делаются в страницах **в памяти** (shared buffers), страницы становятся «грязными».
2. Описание изменения записывается в **WAL** — последовательный журнал (`pg_wal/`, сегменты по 16 МБ).
3. При `COMMIT` журнал **сбрасывается на диск** (`fsync`) — только после этого клиент получает подтверждение. Последовательная запись журнала намного быстрее случайной записи страниц.
4. Грязные страницы пишутся в файлы данных позже — фоновым процессом и при checkpoint.

При падении сервер при старте **проигрывает WAL** от последнего checkpoint (crash recovery) и восстанавливает все зафиксированные транзакции.

Позиция в журнале — **LSN** (log sequence number), например `0/3A2B1C8`. По разнице LSN измеряется, например, отставание реплики.

### Checkpoint

**Checkpoint** — момент, когда все грязные страницы сбрасываются на диск. После него WAL до этой точки не нужен для восстановления после сбоя (может быть удалён или переиспользован, если не нужен архиву и репликам).

Настройки:
- `checkpoint_timeout` (по умолчанию 5 мин) и `max_wal_size` (1 ГБ) — что наступит раньше;
- `checkpoint_completion_target` (0.9) — растянуть запись на интервал, чтобы не было всплеска нагрузки на диск.

Компромисс: частые checkpoint → больше записи (особенно из-за **full page writes**: первое изменение страницы после checkpoint пишет в WAL страницу целиком) и нагрузки; редкие → дольше восстановление после сбоя и больше WAL. В логах предупреждение «checkpoints are occurring too frequently» — повод увеличить `max_wal_size`.

### Параметры долговечности

- `fsync = on` — **никогда не выключать** в продакшене: без него сбой питания может повредить базу.
- `synchronous_commit` — ждать ли сброса WAL на диск (и на синхронные реплики) перед ответом клиенту. `off` для некритичных данных ускоряет запись ценой потери последних транзакций (но не повреждения базы).
- `wal_level`: `replica` (для физической репликации и архива), `logical` (для логической репликации и CDC — Debezium).

### Архивирование WAL

Чтобы восстановиться на **любой момент** времени, нужны базовый бэкап + **все** сегменты WAL после него. Архивирование копирует каждый заполненный сегмент в надёжное хранилище:
```
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'
```
На практике используют **pgBackRest**, **WAL-G**, Barman: сжатие, шифрование, параллельность, хранение в S3, проверка целостности.

Опасности:
- если `archive_command` падает, сегменты **копятся** в `pg_wal` и могут **заполнить диск** — сервер остановится. Мониторинг: `pg_stat_archiver` (`failed_count`, время последней успешной архивации), размер `pg_wal`;
- то же делает **заброшенный слот репликации**: слот удерживает WAL для реплики, которая давно не подключалась (`pg_replication_slots`, параметр `max_slot_wal_keep_size` как страховка).

Как WAL используется дальше: **потоковая репликация** (реплики получают и проигрывают WAL — см. [Репликация](#/theory/databases/replication)) и **PITR** (см. [Бэкапы](#/theory/databases/backups)).

## VACUUM, bloat и transaction ID wraparound
id: vacuum

> **Суть:** из-за MVCC старые версии строк остаются в таблицах. **VACUUM** помечает место мёртвых версий как свободное для повторного использования, обновляет карту видимости и «замораживает» старые строки. Без него таблицы раздуваются (**bloat**), а через ~2 млрд транзакций наступает **wraparound** — и база перестаёт принимать запись, чтобы не потерять данные.

### Что делает VACUUM

- находит **мёртвые кортежи** (версии, не видимые ни одной транзакции) и помечает их место свободным (free space map) — новые строки займут его;
- очищает ссылки на них из индексов;
- обновляет **visibility map** (позволяет делать index-only scan и пропускать страницы);
- **замораживает** (freeze) старые строки, защищая от wraparound;
- `VACUUM ANALYZE` дополнительно обновляет **статистику** для планировщика.

Обычный `VACUUM` **не возвращает место ОС** (кроме пустого хвоста файла) и не блокирует чтение и запись. **`VACUUM FULL`** переписывает таблицу целиком и возвращает место, но берёт **эксклюзивную блокировку** — таблица недоступна на всё время. На продакшене для удаления bloat используют **pg_repack** или pg_squeeze (перестройка без долгой блокировки).

### Autovacuum

Фоновый процесс запускает VACUUM и ANALYZE автоматически, когда доля изменённых строк превышает порог: `autovacuum_vacuum_scale_factor` (20% по умолчанию) + `autovacuum_vacuum_threshold`.

Для больших таблиц 20% — слишком много (таблица в 1 млрд строк будет ждать 200 млн мёртвых), поэтому на них настраивают более агрессивные параметры:
```sql
ALTER TABLE events SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_cost_limit = 2000);
```
Также увеличивают `autovacuum_max_workers` и снижают торможение (`autovacuum_vacuum_cost_delay`) на быстрых дисках. **Отключать autovacuum нельзя.**

### Bloat

Раздувание таблиц и индексов: место занято мёртвыми или пустыми областями. Последствия: больше диска, больше чтения с диска, хуже кеширование, медленнее запросы.

Причины:
- autovacuum не успевает (слишком мягкие пороги, мало воркеров);
- **долгие транзакции** и `idle in transaction`: пока они открыты, VACUUM не может удалить версии, которые им могут быть видны;
- забытые **слоты репликации** и **подготовленные транзакции** (`pg_prepared_xacts`);
- реплика с `hot_standby_feedback = on` и долгими запросами на ней;
- массовые `UPDATE`/`DELETE`.

Диагностика:
```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

SELECT pid, state, xact_start, now() - xact_start AS age, query
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 5;
```
Оценка bloat — расширение `pgstattuple` или известные запросы оценки. Профилактика: `idle_in_transaction_session_timeout`, мониторинг возраста самой старой транзакции.

### Transaction ID wraparound

Идентификатор транзакции (**XID**) — 32-битный счётчик, около 4 млрд значений, сравнение идёт **по кругу**: для каждой транзакции примерно 2 млрд «в прошлом» и 2 млрд «в будущем». Если строка старше 2 млрд транзакций, её `xmin` внезапно окажется «в будущем» — и строка станет **невидимой** (данные как бы исчезнут).

Защита — **заморозка**: VACUUM помечает достаточно старые строки как «видимые всем всегда», после чего их XID не важен.
- `autovacuum_freeze_max_age` (200 млн) — при достижении такого возраста таблицы autovacuum принудительно запускает **агрессивную** заморозку (даже если autovacuum для таблицы отключён). На больших таблицах это может быть долгой и тяжёлой операцией.
- Если заморозка не успевает, PostgreSQL сначала пишет **предупреждения**, а при приближении к пределу (около 3 млн оставшихся XID) **перестаёт выдавать новые XID** — база фактически становится только для чтения, пока не будет выполнен VACUUM (в старых версиях — в однопользовательском режиме). Это серьёзная авария.

Мониторинг:
```sql
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
SELECT relname, age(relfrozenxid) FROM pg_class WHERE relkind = 'r' ORDER BY 2 DESC LIMIT 10;
```
Алерт, например, при возрасте больше 500 млн–1 млрд. Причины, по которым заморозка не происходит, — те же, что у bloat: долгие транзакции, забытые слоты, подготовленные транзакции, неуспевающий autovacuum.

## Репликация: физическая и логическая, синхронная и асинхронная, лаг
id: replication

> **Суть:** физическая (потоковая) репликация передаёт **WAL** с основного сервера (primary) на реплики, и они проигрывают его — получается побайтовая копия всего кластера. **Асинхронная** быстрее, но при отказе primary последние транзакции могут потеряться; **синхронная** гарантирует сохранность, но добавляет задержку и зависимость от реплики. Реплики используют для отказоустойчивости и чтения, учитывая **лаг**.

### Физическая потоковая репликация

1. Реплика создаётся из базового бэкапа (`pg_basebackup`).
2. Процесс **walreceiver** на реплике подключается к primary, **walsender** отправляет ему WAL в реальном времени.
3. Реплика проигрывает WAL (**startup** процесс) и находится в режиме **hot standby** — доступна для чтения.
4. **Слот репликации** гарантирует, что primary не удалит WAL, который реплика ещё не получила (но может заполнить диск, если реплика пропала — см. [WAL](#/theory/databases/wal)).

Особенности: копия **всего** кластера (все базы), одинаковые мажорные версии PostgreSQL, реплика только для чтения. **Каскадная** репликация: реплика раздаёт WAL следующим репликам.

### Асинхронная и синхронная

| | Асинхронная (по умолчанию) | Синхронная |
|---|---|---|
| Когда клиент получает COMMIT | после записи WAL локально | после подтверждения от синхронной реплики |
| Потеря данных при отказе primary | возможна (транзакции, не дошедшие до реплики) | нет (RPO = 0) |
| Задержка записи | минимальная | + сетевой круг до реплики |
| Если реплика недоступна | не влияет | **запись встаёт**, если нет другой синхронной реплики |

Настройка: `synchronous_standby_names = 'ANY 1 (replica1, replica2)'` — кворум: достаточно подтверждения от любой одной из двух (одна реплика может упасть без остановки записи). `synchronous_commit` управляет строгостью: `remote_write`, `on` (WAL на диске реплики), `remote_apply` (уже применён и виден на реплике — для чтения своих записей).

Практика: синхронная реплика в той же зоне или регионе (малая задержка) плюс асинхронные — в других зонах и регионах для катастрофоустойчивости.

### Логическая репликация

Передаёт не байты страниц, а **логические изменения строк** (INSERT, UPDATE, DELETE) по публикациям и подпискам:
```sql
-- на источнике
CREATE PUBLICATION shop_pub FOR TABLE orders, users;
-- на приёмнике
CREATE SUBSCRIPTION shop_sub CONNECTION 'host=src dbname=shop' PUBLICATION shop_pub;
```
Применение: выборочные таблицы, **обновление мажорной версии с минимальным простоем** (реплицировать в новую версию и переключиться), консолидация баз, передача изменений в другие системы (CDC через Debezium → Kafka). Ограничения: не реплицируются DDL и последовательности, нужен первичный ключ (replica identity), конфликты на приёмнике.

### Лаг репликации и чтение с реплик

**Лаг** — насколько реплика отстаёт: в байтах WAL или во времени.
```sql
-- на primary
SELECT client_addr, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes, replay_lag
FROM pg_stat_replication;
-- на реплике
SELECT now() - pg_last_xact_replay_timestamp() AS lag;
```
Причины лага: сеть, медленный диск реплики, тяжёлая нагрузка записи на primary, **конфликты** с долгими запросами на реплике (проигрывание WAL приостанавливается до `max_standby_streaming_delay`, потом запрос отменяется — ошибка «canceling statement due to conflict with recovery»).

Чем лаг грозит приложению:
- **read-your-writes**: пользователь сохранил профиль (запись на primary), страница перечитала его с реплики — видит старые данные, «сохранение не сработало»;
- **монотонность**: повторные запросы попадают на разные реплики с разным отставанием — данные «прыгают во времени»;
- **неверные решения**: проверка «товар в наличии» по устаревшей реплике;
- при асинхронной репликации и отказе primary — потеря транзакций на величину лага.

Как работать с репликами для чтения:
- читать с реплик только то, что **терпит устаревание** (отчёты, каталоги, аналитика, поиск);
- после записи читать **с primary** некоторое время (по сессии пользователя или флагу), либо передавать LSN записи и ждать, пока реплика его догонит;
- `synchronous_commit = remote_apply` для критичных записей;
- маршрутизация: отдельные строки подключения (read-write и read-only), `target_session_attrs=read-write` в драйвере, пулер или прокси (pgcat, HAProxy с проверками);
- мониторинг лага с алертом и **исключение отстающей реплики** из балансировки чтения.

## Отказоустойчивость: failover, Patroni, split-brain
id: ha

> **Суть:** автоматический failover — это не только «повысить реплику», а целая задача: **надёжно обнаружить** отказ primary, **выбрать** самую актуальную реплику, **гарантировать**, что старый primary не продолжит принимать запись (иначе **split-brain**), и **переключить клиентов**. Для PostgreSQL стандарт — **Patroni** с распределённым хранилищем консенсуса (etcd, Consul) плюс точка входа для клиентов (HAProxy, VIP, DNS) и пулер (PgBouncer).

### Почему это сложно

- **Отказ или сетевая проблема?** Primary может быть жив, но недоступен для части узлов. Если повысить реплику, а старый primary продолжит принимать запись от части клиентов — получится два мастера с расходящимися данными: **split-brain**, самая опасная авария.
- **Потеря данных**: при асинхронной репликации повышенная реплика может не иметь последних транзакций.
- **Переключение клиентов**: приложения должны узнать о новом primary.

### Patroni

Patroni — агент рядом с каждым экземпляром PostgreSQL, использующий **DCS** (etcd, Consul, ZooKeeper или API Kubernetes) как источник истины о лидере.
- Лидер владеет **ключом лидера** в DCS с TTL (например, 30 с) и постоянно его продлевает.
- Если primary не может продлить ключ (упал или потерял связь с DCS), он **сам понижает себя** до read-only — так предотвращается split-brain: без кворума DCS писать нельзя.
- Когда ключ истёк, реплики соревнуются за лидерство; побеждает самая актуальная (по LSN), с учётом `maximum_lag_on_failover` и тегов (`nofailover`).
- Новый лидер повышается (`pg_promote`), остальные реплики переподключаются к нему; старый primary после возвращения перестраивается как реплика (**pg_rewind**).
- **REST API** Patroni на каждом узле: `/primary` (200 только на лидере), `/replica`, `/health` — используется балансировщиками.
- Плановое переключение: `patronictl switchover`, статус: `patronictl list`.
- Watchdog (`/dev/watchdog`) — дополнительная защита: если Patroni завис, ядро перезагрузит узел.

Кворум DCS — 3 или 5 узлов etcd, желательно в разных зонах.

**Stolon** — похожий проект для PostgreSQL (keeper, sentinel, proxy), менее популярен; **pg_auto_failover**, **repmgr** — альтернативы. В Kubernetes — операторы (**CloudNativePG**, Zalando Postgres Operator на Patroni, Crunchy PGO).

### Типовая схема

```
приложения
    │
    ▼
PgBouncer (пул соединений) ──► HAProxy (или VIP/DNS) ──► узел с /primary = 200
                                     │ health-check по REST API Patroni (порт 8008)
         ┌───────────────────────────┼───────────────────────────┐
     PostgreSQL + Patroni       PostgreSQL + Patroni        PostgreSQL + Patroni
       (primary)                  (sync replica)              (async replica)
         └──────────── etcd / Consul (3 узла, кворум) ───────────┘
```
- **HAProxy** проверяет `/primary` у Patroni и направляет запись только на лидера; отдельный порт с проверкой `/replica` — для чтения.
- Альтернативы HAProxy: **VIP** через vip-manager или keepalived (адрес переезжает на лидера), **DNS** с коротким TTL, **libpq с несколькими хостами** и `target_session_attrs=read-write` (драйвер сам найдёт primary).
- **PgBouncer** — пул соединений перед базой (см. [Подключения](#/theory/databases/connections-access)); при переключении обрывает старые соединения, клиенты переподключаются.
- **Синхронная реплика** (через Patroni `synchronous_mode`) — для нулевой потери данных.

### Что ещё важно

- Приложение должно **переподключаться** и повторять идемпотентные операции: failover занимает от секунд до десятков секунд.
- **Регулярно тестировать** переключение (switchover и имитация отказа), иначе в реальной аварии что-то не сработает.
- Мониторинг: кто лидер, лаг реплик, состояние DCS, число переключений (частые — признак проблем с сетью или ресурсами).
- Fencing — гарантированная изоляция старого лидера (Patroni делает это через DCS и watchdog).

## Бэкапы и восстановление на момент времени (PITR)
id: backups

> **Суть:** репликация — **не бэкап**: ошибочный `DROP TABLE` мгновенно реплицируется. Бэкапы бывают **логические** (`pg_dump`, SQL-представление) и **физические** (копия файлов кластера + WAL). Физический базовый бэкап с непрерывным архивом WAL позволяет восстановиться на **любой момент** (PITR). Бэкап считается существующим, только если **восстановление регулярно проверяется**.

### RPO и RTO

- **RPO** (Recovery Point Objective) — сколько данных допустимо потерять (последние 5 минут? сутки?).
- **RTO** (Recovery Time Objective) — за сколько нужно восстановиться.

Эти цифры определяют стратегию: суточный `pg_dump` даёт RPO до суток; архив WAL — секунды–минуты; синхронная реплика — ноль для отказа сервера (но не для логической ошибки).

### Логические бэкапы

```bash
pg_dump -Fc -d shop -f shop.dump          # формат custom: сжатый, выборочное восстановление
pg_restore -d shop_new -j 4 shop.dump     # параллельное восстановление
pg_dumpall --globals-only > globals.sql    # роли и табличные пространства
```
- Плюсы: переносимость между версиями и платформами, выборочное восстановление таблиц, простота.
- Минусы: долго для больших баз (часы), восстановление ещё дольше (перестроение индексов), снимок только на момент начала — без PITR, нагрузка на базу.
- Подходит для небольших баз, миграций между версиями, копий отдельных таблиц.

### Физические бэкапы и PITR

- **Базовый бэкап** — копия файлов данных во время работы (`pg_basebackup` или инструменты), согласованность восстанавливается за счёт WAL.
- **Непрерывный архив WAL** (см. [WAL](#/theory/databases/wal)).
- **Восстановление на момент времени**: развернуть базовый бэкап, проигрывать WAL из архива и остановиться в нужной точке:
```
restore_command = 'pgbackrest --stanza=main archive-get %f "%p"'
recovery_target_time = '2026-10-07 14:31:00+03'
recovery_target_action = 'promote'
```
  Типичный сценарий: в 14:32 кто-то выполнил `DELETE` без `WHERE` — восстанавливаемся на 14:31:59 в **отдельный** экземпляр и переносим потерянные данные или переключаемся на него.

Инструменты:
- **pgBackRest** — полные, дифференциальные и инкрементальные бэкапы, параллельность, сжатие, шифрование, S3/GCS/Azure, проверка, политики хранения;
- **WAL-G** — бэкапы и архив WAL в объектное хранилище, дельта-бэкапы;
- **Barman** — централизованный сервер бэкапов;
- в Kubernetes — встроено в операторы (CloudNativePG использует Barman Cloud);
- в облаке — автоматические бэкапы и PITR управляемых БД (RDS, Cloud SQL) — проверить срок хранения.

Снапшоты дисков (EBS, LVM) — быстрый вариант, но нужна согласованность (снапшот всех томов атомарно или `pg_backup_start`/`pg_backup_stop`) и хранение вне того же аккаунта или региона.

### Правила хороших бэкапов

- **3-2-1**: три копии, два разных носителя, одна вне площадки (другой регион или аккаунт).
- **Неизменяемость** (Object Lock, WORM) — защита от шифровальщиков и злоумышленника с админским доступом.
- **Шифрование** бэкапов и раздельный доступ к ключам.
- **Мониторинг**: успешность бэкапов, возраст последнего, непрерывность архива WAL.
- **Регулярное тестовое восстановление** — автоматическое (например, еженедельно развернуть бэкап, проверить целостность и запросами) с замером времени — так проверяется и RTO.
- Документированный **runbook** восстановления.

## Подключения и доступ: пулинг, роли, права и pg_hba.conf
id: connections-access

> **Суть:** в PostgreSQL каждое подключение — **отдельный процесс** с заметной памятью, поэтому тысячи подключений от микросервисов убивают базу. **PgBouncer** держит небольшой пул реальных соединений и раздаёт их клиентам. Доступ управляется двумя уровнями: **pg_hba.conf** решает, кто и откуда может подключиться и как аутентифицироваться, а **роли и GRANT** — что можно делать внутри.

### Зачем пулер

- На каждое подключение PostgreSQL создаёт процесс (форк): мегабайты памяти, время на установку, накладные расходы на переключение контекста и блокировки при большом числе активных процессов.
- Оптимальное число **активных** соединений — порядка нескольких на ядро CPU; сотни и тысячи только мешают.
- Микросервисы с автомасштабированием: 50 подов × пул 20 = 1000 соединений, из которых большинство простаивают.
- `max_connections` ограничен, и каждое увеличение стоит памяти.

### Режимы PgBouncer

| Режим | Соединение с БД выдаётся клиенту | Совместимость | Эффективность |
|---|---|---|---|
| **session** | на всю сессию клиента | полная | низкая: только экономия на установке соединений |
| **transaction** | на одну **транзакцию** | ломаются сессионные возможности | **высокая**, самый популярный |
| **statement** | на один запрос | только autocommit, без многооператорных транзакций | максимальная, редко нужен |

Что ломается в **transaction**-режиме: всё, что привязано к сессии, — `SET` (параметры сессии), `LISTEN/NOTIFY`, advisory-блокировки на сессию, временные таблицы между транзакциями, классические подготовленные операторы (новые версии PgBouncer поддерживают протокольные prepared statements через `max_prepared_statements`). Приложения нужно проверять.

Основные параметры: `pool_mode`, `default_pool_size` (соединений на пару база/пользователь), `max_client_conn`, `reserve_pool_size`, `server_idle_timeout`. Консоль администрирования: `SHOW POOLS;` — `cl_waiting` (клиенты ждут свободного соединения — пул мал или запросы долгие).

Где ставить: рядом с базой (общий пул на всех клиентов), рядом с приложением (sidecar), или оба уровня. Альтернативы: **Odyssey** (многопоточный, от Яндекса), **pgcat** и **PgDog** (с шардированием и балансировкой чтения), встроенные пулеры в облаках (RDS Proxy) и в операторах (CloudNativePG Pooler).

### Роли и права

В PostgreSQL пользователь и группа — это **роль** (`LOGIN` даёт право входить).
```sql
CREATE ROLE app_rw LOGIN PASSWORD 'xxx';        -- лучше SCRAM и пароль из менеджера секретов
CREATE ROLE readonly NOLOGIN;                    -- групповая роль

GRANT CONNECT ON DATABASE shop TO readonly;
GRANT USAGE ON SCHEMA public TO readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO readonly;   -- для будущих таблиц
GRANT readonly TO analyst;                        -- членство в группе
```
Подводные камни:
- `GRANT ... ON ALL TABLES` действует только на **существующие** таблицы; для новых нужны `ALTER DEFAULT PRIVILEGES` (причём они привязаны к роли, которая будет создавать таблицы);
- права нужны на каждом уровне: база (`CONNECT`), схема (`USAGE`), объекты (`SELECT`...), последовательности (`USAGE` для `serial`);
- владелец объекта имеет на него все права; приложение не должно быть владельцем схемы (отдельная роль для миграций, отдельная — для работы);
- `SUPERUSER` — только для администраторов, не для приложений;
- в PostgreSQL 15+ у роли `PUBLIC` нет права создавать объекты в схеме `public`.

Принцип: отдельные роли для приложения (чтение-запись данных), миграций (DDL), только чтения (аналитика), администраторов. Лучше — **динамические учётные данные** из Vault (см. [динамические секреты](#/theory/security/dynamic-secrets)) или IAM-аутентификация в облаке.

### pg_hba.conf

Файл правил аутентификации на уровне подключения: **тип, база, пользователь, адрес, метод**. Правила проверяются **сверху вниз**, срабатывает **первое** подходящее (дальше не смотрит).
```
# TYPE  DATABASE    USER         ADDRESS          METHOD
local   all         postgres                      peer
hostssl shop        app_rw       10.0.0.0/16      scram-sha-256
hostssl all         all          10.0.0.0/16      scram-sha-256
host    replication replicator   10.0.1.0/24      scram-sha-256
host    all         all          0.0.0.0/0        reject
```
- Типы: `local` (Unix-сокет), `host` (TCP), `hostssl` (только TLS), `hostnossl`.
- Методы: `scram-sha-256` (рекомендуется), `md5` (устарел), `peer` (имя пользователя ОС = роль, для локального входа), `cert` (клиентский сертификат), `ldap`, `trust` (**без пароля** — никогда для сетевых подключений), `reject`.
- Применение изменений: `SELECT pg_reload_conf();` (перезапуск не нужен). Проверка: представление `pg_hba_file_rules` (покажет ошибки разбора).
- Ошибка «no pg_hba.conf entry for host ...» — нет подходящего правила (или порядок правил не тот).
- Плюс `listen_addresses` в `postgresql.conf` — на каких интерфейсах вообще слушать.

## Диагностика производительности базы данных
id: performance

> **Суть:** «приложение тормозит из-за базы» разбирается по шагам: подтвердить, что дело в базе (время запросов в приложении и трейсах) → найти **какие запросы** тратят время (`pg_stat_statements`) → понять, **почему**: план (`EXPLAIN ANALYZE`), ожидания и блокировки (`pg_stat_activity`), ресурсы сервера (CPU, диск, память), соединения, bloat и статистика.

### Шаг 1. Подтвердить и сузить

- Метрики приложения и **трейсы**: какая доля времени запроса пользователя — это БД? Один медленный запрос или проблема N+1 (тысячи мелких)?
- Когда началось и что менялось: деплой (новый запрос, убранный индекс), рост данных, миграция, изменение нагрузки, обновление статистики.
- Все запросы медленные или конкретные? (Всё медленно — ресурсы, блокировки или соединения; конкретные — план запроса.)

### Шаг 2. Что происходит прямо сейчас

```sql
SELECT pid, now() - query_start AS duration, state, wait_event_type, wait_event, left(query, 80)
FROM pg_stat_activity
WHERE state <> 'idle' ORDER BY duration DESC;
```
- `wait_event_type = Lock` — запрос **ждёт блокировку**. Кто блокирует:
```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, left(query, 60) FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;
```
  Частая картина: миграция с `ALTER TABLE` ждёт долгий запрос, а за ней в очереди встали все остальные.
- `IO` — ожидание диска; `LWLock` — внутренняя конкуренция; `Client` — ждёт приложение.
- `idle in transaction` — открытая транзакция без активности: держит блокировки и мешает VACUUM.
- Отмена: `pg_cancel_backend(pid)` (запрос), `pg_terminate_backend(pid)` (соединение).

### Шаг 3. Какие запросы дороже всего

Расширение **pg_stat_statements** агрегирует статистику по нормализованным запросам:
```sql
SELECT calls, round(total_exec_time) AS total_ms, round(mean_exec_time, 1) AS mean_ms,
       rows, shared_blks_read, left(query, 80)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
```
Смотреть по **суммарному** времени (запрос по 5 мс, вызываемый миллион раз, важнее редкого запроса на 2 секунды) и по среднему. Плюс `log_min_duration_statement` (логировать медленные запросы) и **auto_explain** (логировать их планы).

### Шаг 4. Почему запрос медленный

`EXPLAIN (ANALYZE, BUFFERS)` (см. [индексы и планы](#/theory/databases/sql-indexes)):
- нет подходящего индекса или он не используется;
- ошибка оценки числа строк из-за устаревшей статистики → `ANALYZE`, увеличить `default_statistics_target`, расширенная статистика для коррелированных колонок;
- сортировка или хеш на диске → `work_mem`;
- bloat таблицы или индекса → больше страниц читать (см. [VACUUM](#/theory/databases/vacuum));
- плохо написанный запрос: `SELECT *`, отсутствие `LIMIT`, функции над колонками в условиях, OFFSET-пагинация глубоко в таблицу (лучше keyset-пагинация).

### Шаг 5. Ресурсы и конфигурация

- **CPU** — много тяжёлых запросов или параллельных процессов;
- **диск** — `iostat`: задержки, насыщение; **cache hit ratio** (`blks_hit / (blks_hit + blks_read)` в `pg_stat_database`, норма для OLTP — выше 99%): если низкий, рабочий набор не помещается в память;
- **память**: `shared_buffers` (обычно ~25% RAM), `effective_cache_size`, `work_mem` (на операцию сортировки, умножается на число операций и соединений — осторожно);
- **соединения**: число подключений и ожидание в пулере (см. [пулинг](#/theory/databases/connections-access));
- **checkpoint** и запись WAL — всплески записи;
- **реплики**: долгие запросы на реплике с `hot_standby_feedback` раздувают таблицы primary.

Инструменты: pg_stat_statements, `pg_stat_activity`, `pg_stat_user_tables`, `pg_stat_io` (PG 16+), postgres_exporter + дашборды, pgBadger (анализ логов), pganalyze и PMM.

### Шаг 6. Исправить и предотвратить

Индекс (`CONCURRENTLY`), переписать запрос, кеш на уровне приложения, перенос тяжёлого чтения на реплику, пулер, настройка autovacuum, тайм-ауты (`statement_timeout`, `idle_in_transaction_session_timeout`, `lock_timeout` для миграций). И мониторинг, который покажет проблему раньше пользователей.

- Почему `idle in transaction` вреден?

## Логика в базе: функции, процедуры и триггеры
id: procedures

> **Суть:** СУБД умеет выполнять код рядом с данными: **функции** (возвращают значение, вызываются в запросах), **процедуры** (могут управлять транзакциями, вызываются `CALL`), **триггеры** (автоматически срабатывают на INSERT, UPDATE, DELETE). Это быстро и гарантированно для всех клиентов, но код в базе сложнее версионировать, тестировать, отлаживать и масштабировать.

### Что есть в PostgreSQL

**Функция**:
```sql
CREATE FUNCTION order_total(p_order_id bigint) RETURNS numeric
LANGUAGE sql STABLE AS $$
  SELECT sum(price * qty) FROM order_items WHERE order_id = p_order_id
$$;
SELECT id, order_total(id) FROM orders;
```
Языки: SQL, PL/pgSQL, а также PL/Python и другие расширения. Категории волатильности (`IMMUTABLE`, `STABLE`, `VOLATILE`) влияют на оптимизацию и возможность использовать функцию в индексах.

**Процедура** (PostgreSQL 11+): `CREATE PROCEDURE ...`, вызов `CALL archive_old_orders();`. В отличие от функции может делать `COMMIT` и `ROLLBACK` внутри — удобно для пакетной обработки частями.

**Триггер**:
```sql
CREATE FUNCTION set_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END $$;

CREATE TRIGGER orders_updated_at BEFORE UPDATE ON orders
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```
`BEFORE`/`AFTER`, на каждую строку или на оператор. Типичное применение: аудит изменений, `updated_at`, денормализация, сложные ограничения целостности.

### Плюсы логики в базе

- **Близость к данным**: меньше сетевых кругов, массовая обработка без передачи данных в приложение.
- **Единые правила** для всех клиентов (несколько приложений, ручные запросы, ETL) — целостность гарантирует база.
- **Атомарность** сложных операций в одной транзакции.
- Права через `SECURITY DEFINER` — дать выполнить операцию без прав на таблицы (осторожно: требует аккуратного `search_path`).

### Минусы

- **Версионирование и деплой**: код живёт в базе, его нужно выкатывать миграциями, синхронно с приложением; откаты сложнее.
- **Тестирование и отладка** хуже, чем у кода приложения (есть pgTAP, но экосистема беднее).
- **Масштабирование**: база — самый дорогой и трудно масштабируемый компонент; вычисления в ней отнимают ресурсы у основной работы, а приложения масштабируются горизонтально легко.
- **Скрытое поведение**: триггеры срабатывают незаметно для разработчика приложения, каскады триггеров трудно понять; массовые операции замедляются.
- **Привязка к СУБД** (vendor lock-in) и специфичный язык, меньше разработчиков его знают.

### Практическая позиция

Бизнес-логику обычно держат **в приложении**, а в базе — то, что связано с **целостностью данных**: ограничения (`CHECK`, `FOREIGN KEY`, `UNIQUE`), простые триггеры (аудит, `updated_at`), функции для массовых операций над данными, которые неэффективно гонять по сети. Весь код базы — в Git и разворачивается миграциями (Flyway, Liquibase) с ревью, как и любой другой код.

## Выбор базы данных и базы данных в Kubernetes
id: choosing

> **Суть:** базу выбирают по **модели данных и паттернам доступа**: транзакционная работа с связанными данными — реляционная (PostgreSQL); аналитика по огромным объёмам — колоночная (ClickHouse); гибкие документы — MongoDB; огромный поток записи с распределением по многим узлам — Cassandra; кеш — Redis. По умолчанию разумный выбор — PostgreSQL, пока нет конкретной причины выбрать иное. Запускать базы в Kubernetes можно, но только с оператором, продуманным хранилищем и бэкапами — и это осознанное решение, а не значение по умолчанию.

### Вопросы перед выбором

- **Модель данных**: связанные сущности со связями (реляционная), документы, ключ-значение, графы, временные ряды.
- **Паттерн нагрузки**: **OLTP** (много коротких транзакций — заказы, пользователи) или **OLAP** (тяжёлые аналитические запросы по миллиардам строк).
- **Согласованность**: нужны ли строгие транзакции между сущностями или допустима итоговая согласованность.
- **Масштаб**: объём данных, запись и чтение в секунду, рост; нужно ли горизонтальное масштабирование записи.
- **Доступность и география**: несколько регионов, запись в нескольких местах.
- **Эксплуатация**: есть ли экспертиза в команде, управляемый сервис в облаке, стоимость.

### Сравнение

| БД | Модель | Сильные стороны | Ограничения | Когда |
|---|---|---|---|---|
| **PostgreSQL** | реляционная, ACID | транзакции, SQL, JOIN, расширения (JSONB, PostGIS, pgvector, TimescaleDB) | запись масштабируется вертикально (шардирование — Citus или в приложении) | **по умолчанию** для большинства OLTP |
| **MySQL** | реляционная | простота, распространённость | | веб-приложения, экосистема |
| **ClickHouse** | колоночная | агрегации по миллиардам строк за секунды, сжатие | неудобные точечные UPDATE/DELETE, нет полноценных транзакций | аналитика, логи, события, метрики |
| **MongoDB** | документы (JSON) | гибкая схема, вложенные документы, встроенное шардирование | JOIN и многодокументные транзакции дороже | разнородные документы, быстро меняющаяся схема |
| **Cassandra / ScyllaDB** | широкие колонки, распределённая | линейное масштабирование записи, нет единой точки отказа, мультирегион | запросы только по заранее спроектированным ключам, итоговая согласованность | огромный поток записи: IoT, события, история сообщений |
| **Redis** | ключ-значение в памяти | микросекундные задержки, структуры данных | объём ограничен памятью, долговечность ограничена | кеш, сессии, очереди, rate limiting, лидерборды |
| **Elasticsearch / OpenSearch** | поисковый индекс | полнотекстовый поиск, агрегации | не основное хранилище | поиск, логи |

Колоночное хранение (ClickHouse): данные каждой колонки лежат вместе — запрос «сумма по одной колонке за год» читает только эту колонку и отлично сжимает однотипные данные. Зато вставка и изменение одной строки затрагивает все колонки — поэтому вставляют пачками, а не по одной строке.

**CAP-теорема** (упрощённо): при сетевом разделении распределённая система выбирает между **согласованностью** (отказать в запросе) и **доступностью** (ответить, возможно, устаревшими данными). PostgreSQL с синхронной репликацией ближе к CP, Cassandra с настраиваемой согласованностью (`QUORUM`, `ONE`) — гибко между ними.

Частая архитектура — **несколько хранилищ**: PostgreSQL как источник истины, Redis для кеша, ClickHouse для аналитики (данные поступают через CDC или очереди), Elasticsearch для поиска.

### Базы данных в Kubernetes

Аргументы **за**:
- единая платформа, инструменты и GitOps для всего;
- **операторы** зрелые: CloudNativePG, Zalando, Crunchy (PostgreSQL), Percona (MySQL, MongoDB), Strimzi (Kafka), автоматизирующие failover, бэкапы, обновления;
- удобно для множества небольших баз, dev- и test-окружений, on-premise без управляемых сервисов.

Аргументы **против** и риски:
- состояние в среде, рассчитанной на эфемерность: выселение подов, обновления узлов, drain — требуют PDB, anti-affinity, аккуратных процедур (см. [ресурсы и eviction](#/theory/kubernetes/resources));
- **хранилище**: производительность и задержки сетевых дисков, поведение при отказе узла (RWO-диск привязан к зоне и узлу — см. [хранение](#/theory/kubernetes/storage)), локальные NVMe быстрее, но привязаны к узлу;
- нужна экспертиза и в базах, и в Kubernetes одновременно; отладка сложнее;
- соседство с другой нагрузкой (шумные соседи) — выделенные узлы;
- **управляемые сервисы** (RDS, Cloud SQL, Managed PostgreSQL) снимают много работы: бэкапы, PITR, обновления, отказоустойчивость.

Разумная позиция: продакшен-базы в облаке — **управляемый сервис**, если нет причин иначе (стоимость, требования к локализации, особые расширения); в Kubernetes — с **оператором**, на выделенных узлах, с быстрым хранилищем, бэкапами вне кластера и регулярно проверенным восстановлением. Dev и test — в Kubernetes без сомнений.
