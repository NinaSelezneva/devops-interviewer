# Ключевые концепции

**DevSecOps** — встраивание безопасности во все этапы жизненного цикла (**shift left**), автоматизация проверок и общая ответственность, а не «отдел безопасности проверит перед релизом».

### Слои защиты (defense in depth)
- **Код**: SAST, ревью, секрет-сканеры.
- **Зависимости**: SCA, SBOM, закрепление версий.
- **Артефакты**: сканирование образов, подпись, провенанс (SLSA).
- **Инфраструктура**: IaC-сканеры, политики (OPA/Kyverno), CIS Benchmarks.
- **Runtime**: least privilege, сетевые политики, детекция (Falco), WAF.
- **Данные**: шифрование at rest и in transit, управление ключами (KMS).
- **Идентичность**: SSO, MFA, короткоживущие креды, zero trust.

### Полезные фреймворки
OWASP Top 10, CIS Benchmarks, NIST SSDF, SLSA, MITRE ATT&CK (в т.ч. матрица для контейнеров), OWASP Kubernetes Top 10.

## Q: Как управлять секретами в инфраструктуре и приложениях?
level: senior
type: design
freq: 3
tags: секреты, vault

Требования: централизованное хранение, шифрование, аудит доступа, ротация, минимальные права, отсутствие секретов в Git/образах/логах.

Решения:
- **HashiCorp Vault / OpenBao**: KV-хранилище, **динамические секреты** (временные креды к БД и облаку, создаются по запросу и автоматически отзываются), PKI, transit-шифрование, аутентификация через Kubernetes ServiceAccount, OIDC, облачные роли. Минус — сложность эксплуатации (HA, unseal, бэкапы).
- **Облачные менеджеры**: AWS Secrets Manager/SSM Parameter Store, GCP Secret Manager, Azure Key Vault — проще, интеграция с IAM, автоматическая ротация.
- **Доставка в Kubernetes**:
  - **External Secrets Operator** — синхронизирует из Vault/облака в Secret;
  - **Secrets Store CSI Driver** — монтирует как файлы, не создавая Secret;
  - Vault Agent Injector (sidecar);
  - **Sealed Secrets / SOPS** — шифрованные секреты в Git для GitOps.

Важно про Kubernetes Secret: это **base64, а не шифрование**. Нужно включить шифрование etcd (EncryptionConfiguration, KMS-провайдер), ограничить RBAC на чтение секретов.

Лучшая стратегия — **избавляться от секретов** там, где можно: workload identity (IRSA, GKE Workload Identity), OIDC для CI, IAM-аутентификация в БД, mTLS вместо паролей.

## Q: Секрет (ключ доступа к облаку) утёк в публичный репозиторий. Ваши действия?
level: senior
type: scenario
freq: 2
tags: инцидент

Порядок важен: **сначала отозвать**, потом разбираться. Публичные репозитории сканируются ботами за минуты.

1. **Немедленно отозвать/ротировать** ключ (деактивировать access key, перевыпустить токен). Удаление коммита ничего не даёт — секрет уже скомпрометирован, остаётся в форках, кешах и истории.
2. **Оценить ущерб**: CloudTrail/аудит-логи по этому ключу — какие API вызывались, с каких IP, с момента утечки. Искать созданные ресурсы (майнинг-инстансы во всех регионах), новых IAM-пользователей/ключи (персистентность), доступ к данным.
3. **Локализовать**: удалить созданное злоумышленником, проверить другие секреты, к которым был доступ через этот ключ, — ротировать их тоже.
4. **Очистить историю** (git filter-repo / BFG) — для гигиены, не как защита; связаться с поддержкой хостинга для очистки кешей.
5. **Коммуникация**: уведомить службу безопасности, при утечке персональных данных — юристов (регуляторные сроки уведомления).
6. **Постмортем и профилактика**: pre-commit хуки (gitleaks), push protection, сканирование репозиториев, замена статических ключей на OIDC/роли, принцип наименьших привилегий (чтобы утечка давала минимум доступа), алерты на аномальную активность (GuardDuty).

## Q: Как обеспечить безопасность Kubernetes-кластера?
level: senior
type: practice
freq: 3
tags: kubernetes, безопасность

**Control plane и доступ**
- API-сервер не публичен (или ограничен по IP), аутентификация через OIDC/SSO, RBAC по принципу наименьших привилегий, отдельные кластеры или жёсткая изоляция для разных уровней доверия.
- Шифрование секретов в etcd, аудит-лог API-сервера.
- Регулярные обновления версии Kubernetes.

**Нагрузки**
- **Pod Security Admission** (уровень `restricted`): non-root, без privileged, без hostPath/hostNetwork, drop ALL capabilities, seccomp RuntimeDefault.
- **Policy engine** (Kyverno, OPA Gatekeeper): разрешённые реестры, проверка подписей образов, обязательные requests/limits и лейблы, запрет `latest`.
- `automountServiceAccountToken: false`, где токен не нужен.

**Сеть**
- **NetworkPolicy**: default deny ingress/egress, явные разрешения; контроль egress в интернет.
- mTLS между сервисами (service mesh).

**Цепочка поставок и runtime**
- Сканирование образов в CI и в реестре, admission-проверка подписи.
- Runtime-детекция: Falco/Tetragon (shell в контейнере, неожиданные процессы, доступ к чувствительным файлам).
- Ноды: минимальная ОС (Bottlerocket, Talos, Flatcar), IMDSv2 с hop limit 1 (под не должен получать креды ноды), CIS Benchmark (kube-bench).

**Проверка**: kube-bench, kubescape, Trivy operator, регулярный пентест.

## Q: Что такое безопасность цепочки поставок (supply chain)? SBOM, SLSA, подпись образов.
level: senior
type: theory
freq: 2
tags: supply-chain

Атаки на цепочку поставок компрометируют не ваш код, а то, **из чего и чем он собирается**: зависимости (event-stream, xz-utils backdoor в 2024), систему сборки (SolarWinds), реестр, CI (Codecov).

- **SBOM** (Software Bill of Materials) — перечень всех компонентов и версий в артефакте (форматы SPDX, CycloneDX; генерация Syft, Trivy). Позволяет за минуты ответить на вопрос «где у нас log4j?» при новой CVE.
- **Подпись артефактов** — **Sigstore/cosign**: keyless-подпись через OIDC-идентичность CI, запись в прозрачный журнал Rekor. Проверка при деплое admission-контроллером гарантирует, что образ собран вашим пайплайном и не подменён.
- **SLSA** (Supply-chain Levels for Software Artifacts) — фреймворк уровней зрелости: провенанс (аттестация «кто, где, из какого коммита и как собрал»), изолированная и защищённая сборка, неподделываемый провенанс.
- **Прочее**: lock-файлы и хеши зависимостей, приватный прокси-реестр, закрепление GitHub Actions по SHA, воспроизводимые сборки, Renovate для контролируемых обновлений, OpenSSF Scorecard для оценки зависимостей.

## Q: Что такое Zero Trust? Как вы его применяете в инфраструктуре?
level: senior
type: theory
freq: 1
tags: zero-trust

**Zero Trust** — модель «никогда не доверяй, всегда проверяй»: нахождение внутри сети не даёт доверия. Каждый запрос аутентифицируется, авторизуется и шифруется, исходя из идентичности, состояния устройства и контекста.

Практика:
- Отказ от «плоского» VPN с доступом ко всей сети → **identity-aware proxy** (Teleport, Cloudflare Access, Pomerium, Boundary) для SSH, Kubernetes, БД и внутренних веб-приложений с SSO, MFA и аудитом сессий.
- **Короткоживущие сертификаты** вместо статических SSH-ключей.
- Межсервисное взаимодействие — **mTLS** с идентичностью рабочей нагрузки (SPIFFE/SPIRE, service mesh) и авторизацией на уровне сервиса.
- Микросегментация сети (NetworkPolicy, security groups между сервисами).
- Just-in-time доступ к продакшену с одобрением, break-glass процедуры.
- Непрерывный мониторинг и аудит.

## Q: Как встроить проверки безопасности в CI/CD, не замедлив разработку?
level: senior
type: practice
freq: 2
tags: devsecops

- **Быстрые проверки — рано**: секрет-сканер в pre-commit и в CI, линтеры, SAST с инкрементальным анализом только изменённого кода — результаты в MR как комментарии.
- **Пороговые политики**: блокировать только критичные и исправимые находки (critical/high с доступным фиксом), остальное — в бэклог. Иначе команды будут игнорировать или обходить проверки.
- **Тяжёлые проверки — асинхронно**: DAST, полное сканирование, фаззинг — ночью или на staging.
- **Управление исключениями**: явный процесс с владельцем и сроком (`.trivyignore` с комментарием и датой), а не тихий отказ от проверки.
- **Автоматизация исправлений**: Renovate/Dependabot с автомержем патч-версий при зелёных тестах.
- **Безопасные шаблоны по умолчанию** (golden paths): базовые образы, Helm-чарты и Terraform-модули уже соответствуют политикам — разработчикам не нужно думать об этом.
- Метрики: время исправления уязвимостей (MTTR по severity), процент ложных срабатываний.
- Обучение и security champions в командах.

## Q: Как базово защитить Linux-сервер (hardening)?
level: middle
type: practice
freq: 3
tags: hardening, linux

**Доступ:**
- SSH только по ключам: `PasswordAuthentication no`, `PermitRootLogin no`, ограничить `AllowUsers`/`AllowGroups`;
- доступ к SSH только из VPN или через bastion, а не из всего интернета;
- **fail2ban** или аналог от перебора паролей;
- персональные учётки + sudo с минимальными правами, удаление неиспользуемых учёток, MFA для критичного доступа.

**Обновления:**
- регулярные патчи безопасности, автоматические для критичных (`unattended-upgrades`, `dnf-automatic`);
- перезагрузки для обновлений ядра (или live patching).

**Сеть:**
- файрвол с политикой «запрещено всё, что не разрешено» (`ufw`, `firewalld`, `nftables`, облачные Security Groups);
- закрыть лишние порты и удалить ненужные сервисы: `ss -tulpn` — что слушает и зачем;
- сервисы, которым не нужен внешний доступ (БД, Redis, Elasticsearch), слушают только внутренний интерфейс или localhost и защищены паролем.

**Система:**
- минимальная установка, только нужные пакеты;
- SELinux/AppArmor в режиме enforcing, а не отключены;
- сервисы под отдельными непривилегированными пользователями, systemd-sandboxing;
- права на файлы: конфиги с секретами — 600, аудит SUID-файлов;
- `noexec`, `nosuid`, `nodev` для `/tmp` и разделов с данными;
- параметры ядра (`sysctl`): `net.ipv4.conf.all.rp_filter=1`, отключить приём редиректов и source routing, `kernel.kptr_restrict`, `fs.protected_*`.

**Аудит и мониторинг:**
- централизованный сбор логов (аутентификация, sudo) — злоумышленник не сможет незаметно их подчистить;
- `auditd` для критичных событий, контроль целостности файлов (AIDE);
- синхронизация времени (chrony) — без неё логи нельзя сопоставить;
- сканирование уязвимостей и соответствия стандартам: **CIS Benchmarks**, **Lynis**, OpenSCAP.

**Данные:**
- шифрование дисков с чувствительными данными, TLS для всех сервисов;
- регулярные **проверенные** бэкапы.

**Автоматизация:** всё перечисленное оформить ролью Ansible или «золотым» образом (Packer), чтобы каждый сервер был защищён одинаково, а не настраивался вручную.
