# Ключевые концепции

Очереди и брокеры сообщений есть почти в любой микросервисной системе. DevOps-инженер отвечает за их **отказоустойчивость, мониторинг, производительность** и должен понимать гарантии доставки, чтобы разбирать инциденты вместе с разработчиками.

### Kafka в одной схеме
```
producer ──► topic "orders" (replication factor 3)
               ├─ partition 0: leader на broker 1, реплики на 2 и 3
               ├─ partition 1: leader на broker 2, реплики на 1 и 3
               └─ partition 2: leader на broker 3, реплики на 1 и 2
consumer group "billing":   consumer A ← p0, p1     consumer B ← p2
consumer group "analytics": читает те же сообщения независимо, со своими offset
```
- **Topic** делится на **партиции** — упорядоченные журналы только на добавление (append-only). Порядок гарантирован **только внутри партиции**.
- Сообщения с одинаковым **ключом** попадают в одну партицию (например, все события одного заказа).
- Сообщения **не удаляются после чтения** — хранятся по ретеншну (время или размер) или компактируются по ключу.
- Потребитель хранит своё положение — **offset**. Можно перечитать историю (replay).
- **KRaft** — встроенный консенсус контроллеров вместо ZooKeeper; с Kafka 4.0 ZooKeeper больше не поддерживается.

### RabbitMQ в одной схеме
```
producer ──► exchange (direct | topic | fanout | headers) ──binding──► queue ──► consumer (ack)
```
Сообщение удаляется после подтверждения (ack) потребителем. Гибкая маршрутизация, приоритеты, TTL, dead-letter exchanges.

### Когда что
| | Kafka | RabbitMQ |
|---|---|---|
| Модель | распределённый журнал | брокер с очередями |
| Хранение | по ретеншну, повторное чтение | до подтверждения |
| Пропускная способность | очень высокая | высокая, но ниже |
| Маршрутизация | по топикам и ключам | гибкая: exchanges, routing keys |
| Типичные задачи | события, стриминг, CDC, логи, аналитика | очереди задач, RPC, интеграции |

## Q: Как Kafka обеспечивает надёжность? Что такое replication factor, ISR и acks?
level: senior
type: theory
freq: 3
tags: kafka, репликация

Каждая партиция имеет **лидера** и **фолловеров** на других брокерах. Продюсеры пишут и потребители читают через лидера (чтение с ближайшей реплики тоже возможно, KIP-392). Фолловеры копируют данные у лидера.

- **Replication factor (RF)** — сколько копий у партиции. Для продакшена обычно **3**.
- **ISR (in-sync replicas)** — реплики, которые не отстают от лидера дольше `replica.lag.time.max.ms`. При падении лидера новым становится реплика из ISR, поэтому данные не теряются.
- **`acks`** у продюсера — когда считать запись успешной:
  - `acks=0` — не ждать подтверждения (быстро, возможна потеря);
  - `acks=1` — подтвердил лидер (потеря, если лидер упал до репликации);
  - **`acks=all`** — подтвердили все реплики из ISR. По умолчанию с Kafka 3.0.
- **`min.insync.replicas`** (на топике или брокере) — минимальное число реплик в ISR для приёма записи с `acks=all`. Классическая надёжная конфигурация: **RF=3, min.insync.replicas=2, acks=all** — выдерживает потерю одного брокера без потери данных и без остановки записи. Если в ISR осталась одна реплика, продюсеры получат `NotEnoughReplicas`: запись останавливается, но данные не теряются.
- **`unclean.leader.election.enable=false`** (по умолчанию) — не выбирать лидером отставшую реплику: доступность принесена в жертву сохранности данных.
- **Идемпотентный продюсер** (`enable.idempotence=true`, по умолчанию с 3.0) — ретраи продюсера не создают дубликатов в партиции.

**Rack awareness** (`broker.rack`): реплики партиции размещаются в разных стойках или зонах доступности, чтобы отказ зоны не уничтожил все копии.

**Что мониторить:** `UnderReplicatedPartitions` (> 0 — проблема), `OfflinePartitionsCount` (партиции без лидера — недоступны), `UnderMinIsrPartitionCount`, размер ISR, активный контроллер.

## Q: Как работают consumer groups? Что такое rebalance и почему он вреден?
level: senior
type: theory
freq: 3
tags: kafka, consumer

**Consumer group** — набор потребителей с одинаковым `group.id`, которые **делят партиции топика между собой**: каждая партиция в каждый момент читается **только одним** потребителем группы.
- Параллелизм группы **ограничен числом партиций**: при 6 партициях седьмой потребитель будет простаивать.
- Разные группы читают топик **независимо**, у каждой свои offset'ы (так одно событие получают и биллинг, и аналитика).
- Offset'ы хранятся в служебном топике `__consumer_offsets`. Коммит автоматический (`enable.auto.commit`) или ручной после обработки.

**Rebalance** — перераспределение партиций при изменении состава группы: потребитель добавился, ушёл, упал, перестал отправлять heartbeat или **не вызвал `poll()` дольше `max.poll.interval.ms`** (слишком долгая обработка батча).

Почему вреден:
- в классическом протоколе (eager) на время ребаланса **вся группа перестаёт читать** — растёт lag;
- частые ребалансы (флапающий потребитель, долгая обработка, rolling update десятков подов) превращаются в «шторм», группа почти не работает;
- возможна **повторная обработка**: сообщения, обработанные, но не закоммиченные до ребаланса, получит другой потребитель.

Как смягчить:
- **cooperative-sticky** назначение (`partition.assignment.strategy`) — переназначаются только затронутые партиции, остальные продолжают читаться;
- **static membership** (`group.instance.id`) — перезапуск пода с тем же ID в пределах `session.timeout.ms` не вызывает ребаланс; полезно при rolling update в Kubernetes;
- **новый протокол групп** (KIP-848, доступен в Kafka 4.0, `group.protocol=consumer`) — ребалансы выполняются инкрементально на стороне брокера;
- адекватные `max.poll.records` и `max.poll.interval.ms`: обработка батча должна укладываться во время;
- обработка сообщений **идемпотентна**, потому что повторы неизбежны.

## Q: Растёт consumer lag. Как будете разбираться?
level: senior
type: scenario
freq: 3
tags: kafka, траблшутинг, lag

**Consumer lag** — разница между последним offset в партиции и закоммиченным offset группы, то есть сколько сообщений ещё не обработано. Это главная метрика здоровья потребителей.

**Как посмотреть:**
```bash
kafka-consumer-groups.sh --bootstrap-server kafka:9092 --describe --group billing
# TOPIC  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG   CONSUMER-ID  HOST
```
В мониторинге: kafka-exporter / kminion / Burrow (`kafka_consumergroup_lag`), лучше алертить на **время отставания** (сколько секунд lag), а не на число сообщений.

**Диагностика по картине:**
1. **Lag растёт на всех партициях равномерно** → потребители не успевают за входящим потоком:
   - вырос входящий трафик (сравнить скорость записи в топик);
   - замедлилась обработка: медленная БД или внешний API, на который ходит потребитель (смотреть латентность обработки, трейсы), GC-паузы, нехватка CPU (throttling);
   - решение: масштабировать потребителей (**но не больше числа партиций**), ускорить обработку (батчи, параллельная обработка внутри потребителя), увеличить число партиций (с учётом смены распределения ключей).
2. **Lag растёт на одной или нескольких партициях** →
   - **перекос ключей** (hot partition): один «горячий» ключ получает основную часть трафика;
   - зависший потребитель, которому назначены эти партиции;
   - **«ядовитое» сообщение**: потребитель падает на нём, перезапускается и снова падает → нужна обработка ошибок и **dead letter topic**.
3. **Lag скачет, в логах частые rebalance** → потребители не укладываются в `max.poll.interval.ms`, флапают поды (OOM, liveness-проба), rolling update.
4. **Lag растёт, а потребители «простаивают»** → проблема на стороне брокеров: under-replicated партиции, перегрузка дисков или сети, троттлинг по квотам.
5. **Потребителей больше нет в группе** (`CONSUMER-ID` пустой) → сервис упал или не может подключиться (авторизация, DNS, сеть).

Для автоматического масштабирования по lag в Kubernetes используют **KEDA** (скейлер Kafka).

## Q: Как выбрать количество партиций? Чем грозит слишком много или слишком мало?
level: senior
type: design
freq: 2
tags: kafka, capacity

**Партиции — единица параллелизма:** одна партиция читается одним потребителем группы, и запись в партицию последовательная.

**Оценка:** `партиций ≥ max(целевая_пропускная_способность / пропускная_способность_одного_потребителя, то же для продюсера)` с запасом на рост, потому что **увеличить число партиций можно, а уменьшить — нет** (только пересоздать топик).

**Слишком мало:**
- нельзя масштабировать потребителей (лишние простаивают);
- горячие партиции, упор в производительность одного брокера и диска.

**Слишком много:**
- больше открытых файлов и памяти на брокерах, дольше выборы лидеров и восстановление после сбоя;
- больше накладных расходов у продюсеров (меньше батчи на партицию → хуже сжатие и пропускная способность);
- дольше ребалансы потребителей;
- KRaft сильно повысил практический предел партиций на кластер, но тысячи партиций на один топик без необходимости — всё равно антипаттерн.

**Важные нюансы:**
- **Увеличение числа партиций меняет распределение ключей** (`hash(key) % N`) → нарушается порядок для ключей, если в топике идёт поток событий по одному ключу. Для топиков, где важен порядок, количество партиций закладывают сразу с запасом.
- Порядок сообщений гарантирован только внутри партиции; если нужен порядок по заказу — ключом делают ID заказа.
- Типичные стартовые значения: десятки партиций для нагруженных топиков, кратные числу брокеров для равномерного распределения лидеров.

## Q: Что такое retention и log compaction в Kafka?
level: middle
type: theory
freq: 2
tags: kafka, хранение

Kafka хранит сообщения **независимо от того, прочитаны ли они**. Как долго — определяет политика очистки (`cleanup.policy`).

**`delete` (по умолчанию) — ретеншн:**
- `retention.ms` (по умолчанию 7 дней) — удалять данные старше заданного времени;
- `retention.bytes` — ограничение размера **на партицию**;
- удаление происходит **целыми сегментами** (`segment.bytes`, `segment.ms`): активный сегмент не удаляется, поэтому данные могут жить дольше заданного ретеншна.

**`compact` — компактирование:**
- для каждого **ключа** сохраняется **последнее значение**, старые версии удаляются фоновым процессом;
- сообщение с ключом и пустым значением (**tombstone**) означает удаление ключа;
- топик становится «таблицей текущего состояния»: последнее состояние каждого заказа, конфигурация, справочник, changelog для Kafka Streams. Служебные топики `__consumer_offsets` и топики Kafka Connect тоже компактируемые.

Можно сочетать: `cleanup.policy=compact,delete`.

**Практика DevOps:**
- считать **объём дисков**: входящий поток × ретеншн × replication factor + запас;
- **tiered storage** (Kafka 3.6+, KIP-405) — старые сегменты выгружаются в объектное хранилище (S3), на локальных дисках остаются только свежие данные;
- сжатие на продюсере (`compression.type=zstd` или `lz4`) экономит диск и сеть;
- повторная обработка данных (replay) возможна только в пределах ретеншна — это нужно учитывать в планах восстановления после ошибок в потребителях.

## Q: Какие гарантии доставки бывают? Как добиться exactly-once?
level: senior
type: theory
freq: 2
tags: kafka, гарантии, идемпотентность

- **At-most-once** — сообщение доставляется **не более одного раза**, возможна потеря. Пример: потребитель коммитит offset **до** обработки и падает.
- **At-least-once** — **не менее одного раза**, возможны дубли. Коммит offset **после** успешной обработки; при сбое между обработкой и коммитом сообщение обработается повторно. **Самый распространённый режим.**
- **Exactly-once** — ровно один раз.

**Exactly-once в Kafka** (EOS) работает в сценарии «прочитать из Kafka → обработать → записать в Kafka»:
- **идемпотентный продюсер** — нет дублей из-за ретраев;
- **транзакции** (`transactional.id`): запись результатов в несколько партиций и коммит offset'ов потребителя выполняются атомарно;
- потребители читают с `isolation.level=read_committed`;
- Kafka Streams включает это одним параметром (`processing.guarantee=exactly_once_v2`).

**Ограничение:** как только обработка затрагивает **внешнюю систему** (БД, HTTP API, отправка письма), гарантии Kafka на неё не распространяются. Поэтому на практике: **at-least-once + идемпотентная обработка**:
- **ключ идемпотентности** (ID события) и таблица обработанных событий или уникальный индекс — повтор не выполнит действие второй раз;
- операции вида «установить значение» вместо «прибавить»;
- **upsert** вместо insert;
- для записи в БД и отправки события одновременно — паттерн **transactional outbox**.

## Q: Что такое паттерн transactional outbox и dead letter queue?
level: senior
type: design
freq: 2
tags: паттерны, outbox, dlq

**Проблема двойной записи:** сервис должен сохранить заказ в БД **и** отправить событие `OrderCreated` в Kafka. Если сделать это двумя отдельными операциями, при сбое между ними получим расхождение: заказ есть, события нет (или наоборот). Распределённые транзакции (2PC) между БД и брокером — сложно и медленно.

**Transactional outbox:**
1. В **той же транзакции БД**, что и бизнес-изменение, сервис записывает событие в таблицу `outbox`.
2. Отдельный процесс (**relay**) читает таблицу outbox и публикует события в брокер, помечая отправленные. Варианты: периодический опрос таблицы или **CDC** — **Debezium** читает журнал БД (WAL в PostgreSQL) и публикует изменения таблицы outbox в Kafka.
3. Доставка — at-least-once, поэтому потребители должны быть идемпотентными.

**Dead letter queue (DLQ / dead letter topic):** сообщение, которое не удаётся обработать (невалидный формат, ошибка бизнес-логики, «ядовитое» сообщение), после N попыток перекладывается в отдельную очередь, а не блокирует обработку остальных.
- В **RabbitMQ** — встроенный механизм **dead letter exchange** (`x-dead-letter-exchange`): сообщение уходит туда при отказе (`nack` без requeue), истечении TTL или переполнении очереди.
- В **Kafka** встроенного DLQ нет: его реализуют в потребителе (публикация в топик `orders.DLT`), есть поддержка в Spring Kafka, Kafka Connect (`errors.deadletterqueue.topic.name`).
- **Обязательно**: мониторинг и алерт на размер DLQ, инструмент для просмотра и **повторной отправки** (replay) после исправления, сохранение причины ошибки в заголовках.
- Часто делают **промежуточные retry-топики** с задержкой (5 секунд, 1 минута, 10 минут) перед DLQ, чтобы временные сбои зависимостей обрабатывались без ручного вмешательства.

## Q: Как развернуть и эксплуатировать Kafka в Kubernetes? Что мониторить?
level: senior
type: practice
freq: 2
tags: kafka, kubernetes, strimzi

**Варианты:** managed-сервис (Amazon MSK, Confluent Cloud, Managed Kafka в Yandex Cloud и других облаках), на ВМ (Ansible), в Kubernetes с оператором — **Strimzi** (CNCF, самый популярный), Confluent for Kubernetes.

**Strimzi:** кластер описывается ресурсами `Kafka` и `KafkaNodePool` (брокеры и контроллеры KRaft), топики — `KafkaTopic`, пользователи и ACL — `KafkaUser`, коннекторы — `KafkaConnect` / `KafkaConnector`. Оператор управляет сертификатами (TLS между брокерами и клиентами), rolling update брокеров по одному с проверкой синхронизации реплик, Cruise Control для перебалансировки партиций.

**Особенности эксплуатации:**
- **хранилище**: быстрые диски (SSD), PVC с `WaitForFirstConsumer`, мониторинг заполнения — заполненный диск останавливает брокер;
- **распределение по зонам**: rack awareness (`topology.kubernetes.io/zone`), anti-affinity брокеров, PodDisruptionBudget;
- **сеть**: клиенты вне кластера должны достучаться до **каждого** брокера напрямую (advertised listeners) — LoadBalancer или NodePort на брокер, Ingress с TLS passthrough;
- **безопасность**: TLS, аутентификация (SCRAM, mTLS, OAuth), ACL на топики по принципу минимальных прав;
- **ресурсы**: память под page cache ОС важнее, чем большой heap JVM; Guaranteed QoS;
- **обновления** версий Kafka — постепенно, с проверкой совместимости клиентов.

**Мониторинг** (JMX exporter, Strimzi отдаёт метрики сам):
- состояние кластера: `UnderReplicatedPartitions`, `OfflinePartitionsCount`, `UnderMinIsrPartitionCount`, активный контроллер;
- производительность: входящий и исходящий трафик по брокерам, латентность запросов (Produce/Fetch), загрузка обработчиков запросов и сети (`RequestHandlerAvgIdlePercent`), дисковая латентность;
- ресурсы: диски, page cache, GC;
- клиенты: **consumer lag** по группам, ошибки продюсеров, частота ребалансов;
- дашборды: Strimzi Grafana dashboards, UI для просмотра топиков: AKHQ, Kafka UI (Provectus), Redpanda Console.

## Q: Как устроен RabbitMQ? Какие типы exchange бывают и как не потерять сообщения?
level: middle
type: theory
freq: 3
tags: rabbitmq

**Модель AMQP:** продюсер публикует сообщение в **exchange** с **routing key** → exchange по **bindings** раскладывает его в **очереди** → потребители получают сообщения из очередей и подтверждают обработку.

**Типы exchange:**
- **direct** — в очереди с binding key, точно равным routing key (`order.created`);
- **topic** — по шаблону: `order.*` (одно слово), `order.#` (любое количество слов) — гибкая подписка на категории событий;
- **fanout** — во все привязанные очереди, routing key игнорируется (широковещательная рассылка);
- **headers** — по заголовкам сообщения;
- **default exchange** — прямая отправка в очередь по её имени.

**Как не потерять сообщения — на каждом звене:**
1. **Продюсер → брокер**: **publisher confirms** — брокер подтверждает приём; без них сообщение может пропасть при сбое. Флаг `mandatory` — узнать, что сообщение не попало ни в одну очередь.
2. **Хранение**: **durable** очереди и **persistent** сообщения (`delivery_mode=2`) переживают перезапуск брокера. Для отказоустойчивости — **quorum queues** (репликация на основе Raft, нечётное число узлов). Классические зеркалируемые очереди устарели и удалены в RabbitMQ 4.0.
3. **Брокер → потребитель**: **ручные подтверждения** (`ack` после обработки, а не autoAck). Если потребитель упал, не подтвердив, сообщение вернётся в очередь и будет доставлено другому потребителю (то есть возможны дубли → идемпотентность).
4. **Ошибки обработки**: `nack`/`reject` без возврата в очередь → **dead letter exchange**, ограничение повторов (`x-delivery-limit` у quorum-очередей), иначе «ядовитое» сообщение будет крутиться бесконечно.

**Производительность и эксплуатация:**
- **prefetch** (`basic.qos`) — сколько неподтверждённых сообщений выдаётся потребителю: 1 — равномерно, но медленно; слишком много — один потребитель набирает всё, память растёт;
- **длинные очереди** — признак проблемы: брокер тратит память и диск. Срабатывают **memory и disk alarms** — брокер **блокирует всех продюсеров**;
- лимиты длины очереди (`x-max-length`) и TTL;
- мониторинг: длина очередей, скорость публикации и подтверждения, неподтверждённые сообщения, число потребителей, соединения и каналы (утечки каналов — частая проблема), алармы памяти и диска; встроенный плагин Prometheus;
- **RabbitMQ Streams** — журналоподобные очереди с повторным чтением, ответ на часть сценариев Kafka;
- в Kubernetes — RabbitMQ Cluster Operator.

## Q: Как использовать Redis как кеш, очередь и брокер? Какие у него режимы отказоустойчивости?

type: theory

**Redis** — хранилище данных в памяти: строки, хеши, списки, множества, отсортированные множества, потоки (streams). Однопоточная обработка команд (с потоками для ввода-вывода) — очень быстро, но тяжёлая команда (`KEYS *`, большой `SMEMBERS`) блокирует всех клиентов.

**Применения:**
- **кеш** (`SET key value EX 300`) — самое частое;
- сессии, rate limiting (`INCR` + `EXPIRE`), счётчики, рейтинги (sorted sets), распределённые блокировки (с оговорками);
- **очереди**: списки (`LPUSH` / `BRPOP`) — простые, но сообщение теряется, если потребитель упал после извлечения; **Redis Streams** (`XADD`, consumer groups, `XACK`) — с подтверждениями и группами потребителей, похоже на упрощённую Kafka;
- **Pub/Sub** — без хранения: сообщение получают только подключённые сейчас подписчики.

**Устойчивость данных (persistence):**
- **RDB** — периодические снимки на диск (быстрое восстановление, возможна потеря данных за интервал между снимками);
- **AOF** — журнал всех операций (`appendfsync everysec` — потеря не больше секунды);
- обычно включают оба; для чистого кеша — можно без persistence.

**Политика вытеснения** при достижении `maxmemory`: `allkeys-lru` / `allkeys-lfu` для кеша; `noeviction` (по умолчанию) — ошибки записи, когда память закончилась (правильно для очередей, где нельзя терять данные).

**Отказоустойчивость:**
- **репликация** master → replicas (асинхронная — при failover возможна потеря последних записей);
- **Redis Sentinel** — мониторинг и автоматический failover, клиенты узнают адрес мастера у Sentinel;
- **Redis Cluster** — шардирование: 16384 слота распределены между мастерами, у каждого — реплики; клиент должен поддерживать кластерный режим, операции с несколькими ключами — только в пределах одного слота (hash tags `{user:1}`);
- managed-сервисы в облаках.

**Лицензии:** в 2024 году Redis сменил лицензию, сообщество создало форк **Valkey** (Linux Foundation), который многие облака используют в managed-сервисах. В 2025 Redis 8 снова стал доступен и под открытой лицензией AGPL.

**Эксплуатация:** мониторинг памяти и фрагментации, hit ratio кеша, вытеснений, медленных команд (`SLOWLOG`), количества подключений, лага репликации; запрет опасных команд (`rename-command`, ACL); **никогда не открывать Redis в интернет** без пароля и TLS.
