# Ключевые концепции

Сетевые вопросы — второй по частоте блок после Linux. Senior должен уверенно объяснить путь пакета от клиента до приложения и уметь локализовать сетевую проблему.

### Модели OSI и TCP/IP
| OSI | Уровень | Примеры |
|---|---|---|
| 7 | Прикладной | HTTP, DNS, gRPC |
| 6–5 | Представления / сеансовый | TLS (условно) |
| 4 | Транспортный | TCP, UDP, QUIC (поверх UDP) |
| 3 | Сетевой | IP, ICMP, маршрутизация |
| 2 | Канальный | Ethernet, ARP, VLAN, MAC |
| 1 | Физический | кабель, радио |

### Что нужно знать
- TCP: handshake, состояния (`SYN_SENT`, `ESTABLISHED`, `TIME_WAIT`, `CLOSE_WAIT`), окна, ретрансмиты, Nagle.
- Адресация: CIDR, приватные диапазоны (10/8, 172.16/12, 192.168/16), NAT/SNAT/DNAT, маршрутизация.
- DNS: рекурсия, записи, TTL, кеширование, `/etc/resolv.conf`, `ndots` в Kubernetes.
- HTTP/1.1, HTTP/2, HTTP/3, коды ответов, keep-alive.
- TLS 1.2/1.3, сертификаты, цепочки доверия, SNI, mTLS.
- Балансировка L4 vs L7, health checks, sticky sessions.
- Linux-сеть: `ip`, `ss`, `iptables/nftables`, conntrack, `tcpdump`, `dig`, `curl -v`, `mtr`.

## Q: Что происходит, когда вы вводите URL в браузере и нажимаете Enter?
level: middle
type: theory
freq: 3
tags: dns, http, tls

Классический вопрос, где можно показать глубину. Основные шаги:

1. **Разбор URL** и проверка HSTS-списка (принудительный HTTPS).
2. **DNS-резолв**: кеш браузера → кеш ОС (`/etc/hosts`, systemd-resolved) → рекурсивный резолвер → корневые серверы → TLD (`.com`) → авторитативный сервер домена. Ответ кешируется на TTL.
3. **TCP-соединение**: 3-way handshake SYN → SYN-ACK → ACK (для HTTP/3 — QUIC поверх UDP, handshake совмещён с TLS). Перед этим — ARP для MAC-адреса шлюза, маршрутизация, NAT на роутере.
4. **TLS handshake**: ClientHello (с SNI и поддерживаемыми шифрами) → ServerHello + сертификат → проверка цепочки до доверенного корня, срока, имени → обмен ключами (ECDHE) → симметричное шифрование. TLS 1.3 — 1 RTT, возможен 0-RTT.
5. **HTTP-запрос** `GET /` с заголовками (Host, Cookie, Accept-Encoding).
6. **На стороне сервера**: CDN/WAF → L4/L7 балансировщик → reverse proxy (nginx/Ingress) → приложение → БД/кеш.
7. **Ответ**: статус, заголовки (Cache-Control, Set-Cookie), тело. Браузер парсит HTML, загружает ресурсы (часто параллельно по HTTP/2), рендерит страницу.

На senior-уровне хорошо упомянуть, где на каждом этапе может сломаться и как это диагностировать (`dig`, `curl -v --resolve`, `openssl s_client`).

**Вариант вопроса: «что происходит при `curl ya.ru`?»** Отличия от браузера:
- нет схемы → curl использует **HTTP** (порт 80), а не HTTPS; HSTS-кеша у curl по умолчанию нет;
- резолв через `getaddrinfo()` (nsswitch → `/etc/hosts` → DNS), подключение к IPv6 или IPv4 (Happy Eyeballs);
- сервер, скорее всего, ответит **301/302 редиректом** на `https://ya.ru/`, но curl **не следует редиректам** без флага `-L` и просто выведет тело ответа с редиректом;
- нет рендеринга, JavaScript, загрузки ресурсов страницы, cookies (без `-b/-c`);
- `curl -v` покажет каждый этап: резолв, `Connected to ...`, TLS handshake, заголовки запроса (`>`) и ответа (`<`); `curl -w '%{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer}\n'` — тайминги каждого этапа для диагностики.

## Q: Чем отличаются TCP и UDP? Опишите установку и закрытие TCP-соединения.
level: middle
type: theory
freq: 3
tags: tcp, udp

| | TCP | UDP |
|---|---|---|
| Соединение | есть (handshake) | нет |
| Надёжность | подтверждения, ретрансмиты, порядок | нет гарантий |
| Контроль перегрузки | есть (окна, cubic/BBR) | нет |
| Накладные расходы | выше | ниже |
| Применение | HTTP/1-2, БД, SSH | DNS, VoIP, видео, QUIC/HTTP3 |

**Установка**: SYN → SYN-ACK → ACK. Клиент выбирает начальный sequence number, сервер подтверждает его и отправляет свой.

**Закрытие** (4 сегмента): FIN → ACK, затем FIN → ACK. Сторона, закрывшая первой, переходит в **TIME_WAIT** на 2×MSL (в Linux 60 секунд), чтобы поздние пакеты старого соединения не попали в новое и чтобы корректно повторить последний ACK.

Проблемы:
- Много **TIME_WAIT** на клиенте (например, прокси, открывающий новое соединение на каждый запрос) → исчерпание эфемерных портов. Лечение: keep-alive/пулы соединений, `net.ipv4.tcp_tw_reuse`, расширение `ip_local_port_range`.
- Много **CLOSE_WAIT** → баг в приложении: удалённая сторона закрыла соединение, а приложение не вызывает `close()`.

## Q: Как работает DNS? Какие типы записей вы знаете?
level: middle
type: theory
freq: 3
tags: dns

DNS — распределённая иерархическая база. Клиент (stub resolver) спрашивает **рекурсивный резолвер**, тот итеративно идёт: корень → TLD → авторитативный сервер зоны. Ответы кешируются на **TTL**.

Записи:
- **A / AAAA** — имя → IPv4 / IPv6;
- **CNAME** — алиас на другое имя (нельзя на apex зоны и вместе с другими записями; облака решают через ALIAS/ANAME);
- **MX** — почтовые серверы; **TXT** — SPF, DKIM, верификация домена;
- **NS** — авторитативные серверы зоны; **SOA** — параметры зоны;
- **PTR** — обратная зона (IP → имя);
- **SRV** — сервис + порт (используется в k8s, Consul).

Практика и подводные камни:
- Порядок резолва в Linux задаёт `/etc/nsswitch.conf` (`hosts: files dns`), поэтому `/etc/hosts` срабатывает раньше DNS.
- Перед миграцией **заранее снижать TTL**.
- Отрицательное кеширование (NXDOMAIN кешируется по SOA minimum).
- Kubernetes: `ndots:5` в `resolv.conf` → короткое внешнее имя сначала перебирается по всем search-доменам, что даёт лишние запросы и задержки. Решение — FQDN с точкой на конце или уменьшить `ndots`, NodeLocal DNSCache.
- DNS по умолчанию работает по UDP/53, но переходит на TCP для больших ответов (и для AXFR).

Инструменты: `dig +trace example.com`, `dig @8.8.8.8`, `host`, `resolvectl`.

## Q: В чём разница между HTTP/1.1, HTTP/2 и HTTP/3?
level: senior
type: theory
freq: 2
tags: http

- **HTTP/1.1**: текстовый протокол, keep-alive, но один запрос за раз на соединение → **head-of-line blocking** на уровне приложения. Браузеры открывают 6 соединений на хост; отсюда старые оптимизации (спрайты, шардинг доменов).
- **HTTP/2**: бинарный фрейминг, **мультиплексирование** множества потоков в одном TCP-соединении, сжатие заголовков HPACK, приоритеты, server push (фактически устарел). Проблема: HOL-блокировка переехала на уровень TCP — потеря одного пакета тормозит все потоки. Основа **gRPC**.
- **HTTP/3**: поверх **QUIC** (UDP). Независимые потоки без HOL-блокировки на транспорте, TLS 1.3 встроен, быстрый handshake (1-RTT, 0-RTT), **connection migration** (смена IP у мобильного клиента без разрыва). Сжатие заголовков QPACK.

Для DevOps важно: gRPC через L4-балансировщик распределяется плохо (одно долгоживущее соединение → весь трафик на один под) — нужен L7-балансинг (Envoy, service mesh) или клиентская балансировка. HTTP/3 требует открытого UDP/443.

## Q: Как работает TLS? Что такое mTLS?
level: senior
type: theory
freq: 3
tags: tls, безопасность

**TLS** обеспечивает конфиденциальность (шифрование), целостность и аутентификацию сервера.

Handshake TLS 1.3 (упрощённо):
1. ClientHello: версии, наборы шифров, **key share** (ECDHE), SNI (имя хоста).
2. ServerHello + key share → обе стороны вычисляют общий секрет; дальше всё зашифровано.
3. Сервер отправляет сертификат и подпись (CertificateVerify), Finished.
4. Клиент проверяет цепочку сертификатов до доверенного корневого CA, срок действия, соответствие имени (SAN), отзыв (OCSP).

**Асимметричная криптография** используется для обмена ключами и аутентификации, **симметричная** (AES-GCM, ChaCha20) — для данных. ECDHE даёт **perfect forward secrecy**.

**mTLS** — сервер тоже запрашивает сертификат клиента и проверяет его. Применение: межсервисная аутентификация в service mesh (Istio, Linkerd автоматически выдают и ротируют сертификаты), доступ к API, zero trust.

Частые проблемы: неполная цепочка (нет intermediate), истёкший сертификат (нужен мониторинг сроков и автоматизация — cert-manager, ACME), несоответствие SNI. Отладка: `openssl s_client -connect host:443 -servername host -showcerts`.

## Q: Чем балансировка L4 отличается от L7?
level: senior
type: theory
freq: 3
tags: балансировка

**L4** (транспортный уровень) — балансирует TCP/UDP-соединения по IP и порту, не заглядывая в содержимое. Быстро, дёшево, поддерживает любые протоколы, может сохранять IP клиента. Примеры: AWS NLB, IPVS, HAProxy в режиме tcp, MetalLB.

**L7** (прикладной уровень) — понимает HTTP/gRPC: маршрутизация по хосту, пути, заголовкам, cookie; терминирует TLS; ретраи, rate limiting, WAF, канареечные деплои по весам, балансировка отдельных запросов (важно для HTTP/2 и gRPC). Дороже по ресурсам, добавляет латентность. Примеры: AWS ALB, nginx, Envoy, Traefik, Ingress-контроллеры.

Алгоритмы: round-robin, least connections, weighted, consistent hashing (для кешей/sticky), EWMA/P2C (Envoy).

Важные детали: **health checks** (активные и пассивные/outlier detection), передача IP клиента (`X-Forwarded-For`, PROXY protocol), connection draining при выводе бэкенда, таймауты на каждом уровне.

## Q: Пользователи получают 502 и 504 от nginx. Чем они отличаются и как искать причину?
level: senior
type: scenario
freq: 3
tags: http, nginx, траблшутинг

- **502 Bad Gateway** — прокси получил **некорректный ответ** или вообще не смог получить ответ от апстрима: апстрим не слушает порт (connection refused), упал во время запроса, сбросил соединение, превышен размер заголовков ответа, рассинхрон keep-alive (апстрим закрыл соединение раньше, чем прокси попытался его переиспользовать).
- **504 Gateway Timeout** — апстрим не ответил за `proxy_read_timeout` (по умолчанию 60с): медленный запрос, зависшие воркеры, медленная БД, исчерпан пул соединений.
- **503** — сервис недоступен: нет живых бэкендов, rate limiting, в k8s — нет ready-эндпоинтов.

Диагностика:
1. `error.log` nginx — там точная причина (`connect() failed (111: Connection refused)`, `upstream prematurely closed connection`, `upstream timed out`).
2. Корреляция с деплоями: 502 во время rolling update — поды убиваются до того, как их вывели из балансировки → нужен `preStop` sleep и graceful shutdown.
3. Состояние апстрима: живы ли процессы, загрузка воркеров, логи приложения, метрики латентности.
4. Таймауты keep-alive: таймаут простоя у апстрима должен быть **больше**, чем у прокси (классика с Node.js `keepAliveTimeout` за ALB).
5. Проверить напрямую: `curl -v http://upstream:port/health` с хоста прокси.

## Q: Как вы будете диагностировать, что сервис A не может достучаться до сервиса B?
level: senior
type: scenario
freq: 3
tags: траблшутинг, сеть

Идти **снизу вверх по стеку**:

1. **DNS**: `dig B` / `getent hosts B` — резолвится ли имя, в правильный ли адрес.
2. **Маршрут и L3**: `ip route get <IP>`, `ping` (ICMP может быть запрещён), `mtr`/`traceroute` — где теряются пакеты.
3. **L4-порт**: `nc -zv B 443`, `curl -v telnet://B:443`. Результат информативен:
   - *Connection refused* — хост доступен, но порт никто не слушает (или REJECT в firewall);
   - *Timeout* — пакеты дропаются: security group, NACL, firewall, NetworkPolicy, отсутствует маршрут;
   - *No route to host* — проблема маршрутизации или ICMP-reject.
4. **На стороне B**: `ss -tlnp` — слушает ли сервис и на каком адресе (`127.0.0.1` vs `0.0.0.0` — частая ошибка).
5. **Firewall**: `iptables -L -n -v`/`nft list ruleset`, облачные SG/NACL, k8s NetworkPolicy.
6. **TLS/L7**: `openssl s_client`, `curl -v` — сертификат, SNI, коды ответа, авторизация.
7. **Захват трафика**: `tcpdump -i any host B and port 443 -nn` на обеих сторонах — уходит ли SYN, приходит ли SYN-ACK.

Также проверить: MTU (большие пакеты теряются в туннелях/VPN — `ping -M do -s 1472`), conntrack table full (`dmesg: nf_conntrack: table full`), асимметричную маршрутизацию.

## Q: Объясните CIDR и разбейте сеть 10.0.0.0/16 на подсети для VPC.
level: middle
type: practice
freq: 2
tags: ip, cidr

**CIDR** — запись адреса с длиной префикса: `/16` означает, что первые 16 бит — сеть, оставшиеся 16 — хосты → 65 536 адресов. `/24` — 256 адресов (в AWS из каждой подсети резервируется 5).

Формула: адресов в подсети = 2^(32 − префикс).

Пример разбиения `10.0.0.0/16` на 3 AZ:
| Подсеть | CIDR | Адресов |
|---|---|---|
| public-a/b/c | 10.0.0.0/24, 10.0.1.0/24, 10.0.2.0/24 | 256 |
| private-a/b/c (приложения, поды) | 10.0.32.0/19, 10.0.64.0/19, 10.0.96.0/19 | 8192 |
| db-a/b/c | 10.0.10.0/24, 10.0.11.0/24, 10.0.12.0/24 | 256 |

Senior-моменты: оставлять резерв для роста; **не пересекать** диапазоны между VPC, офисом и on-prem (иначе невозможен peering/VPN); для EKS с VPC CNI каждый под получает IP из подсети — нужны крупные подсети или secondary CIDR / prefix delegation; учитывать диапазоны Service/Pod CIDR в Kubernetes.

## Q: Что такое NAT и conntrack? Какие проблемы с ними бывают?
level: senior
type: theory
freq: 2
tags: nat, iptables

**NAT** — подмена адресов в пакетах. **SNAT/masquerade** — исходящий трафик из приватной сети выходит под одним публичным IP (домашний роутер, NAT Gateway в облаке). **DNAT** — входящий трафик на публичный адрес перенаправляется во внутреннюю сеть (port forwarding, Kubernetes Service через kube-proxy в режиме iptables).

Чтобы ответные пакеты вернулись правильно, ядро ведёт таблицу **conntrack** — состояние каждого соединения.

Проблемы:
- **Переполнение conntrack** (`nf_conntrack: table full, dropping packet`) при большом числе коротких соединений → случайные таймауты. Мониторить `nf_conntrack_count` vs `nf_conntrack_max`.
- **Исчерпание портов SNAT** — к одному назначению через один NAT-IP максимум ~64к соединений; в AWS NAT Gateway — ошибки `ErrorPortAllocation`.
- **Race condition в conntrack с UDP** — известная проблема с DNS в Kubernetes (5-секундные задержки), решается NodeLocal DNSCache или `single-request-reopen`.
- Стоимость: трафик через облачный NAT Gateway платный — использовать VPC endpoints для S3/ECR.

## Q: Имя не резолвится. Как диагностировать проблему с DNS на Linux-хосте?
level: senior
type: scenario
freq: 3
tags: dns, траблшутинг

Важно понимать, **в каком порядке** система ищет имя, и что разные утилиты идут разными путями.

**Порядок резолва в glibc:**
1. `/etc/nsswitch.conf` — строка `hosts: files dns` (или `files resolve [!UNAVAIL=return] myhostname dns`) задаёт источники и их порядок: сначала `/etc/hosts`, потом DNS.
2. `/etc/hosts` — статические записи.
3. `/etc/resolv.conf` — список `nameserver` (максимум 3), опрашиваются **по порядку**: следующий только при таймауте предыдущего (`options timeout:2 attempts:2`), либо по кругу с `options rotate`. Также `search` и `ndots`.
4. Часто там `nameserver 127.0.0.53` — локальный **systemd-resolved**, который уже сам ходит к upstream-серверам (смотреть `resolvectl status`, серверы задаются для каждого интерфейса отдельно, через DHCP или netplan/NetworkManager).

**Почему `dig` работает, а приложение — нет (и наоборот):** `dig`/`nslookup`/`host` обращаются к DNS-серверу **напрямую**, игнорируя nsswitch и `/etc/hosts`. Приложения используют `getaddrinfo()` → nsswitch. Поэтому проверять обоими способами:
```bash
getent hosts api.example.com      # как увидит приложение (nsswitch)
getent ahosts api.example.com     # с IPv4 и IPv6
dig api.example.com               # прямой запрос к серверу из resolv.conf
dig @8.8.8.8 api.example.com      # в обход локального резолвера
dig +trace api.example.com        # от корня до авторитативного сервера
resolvectl query api.example.com  # через systemd-resolved
```

**Пошаговая диагностика:**
1. Какой ответ: `NXDOMAIN` (имени нет), `SERVFAIL` (сбой на сервере, часто DNSSEC или недоступен авторитативный), таймаут (нет связи с DNS-сервером), или имя резолвится, но в неверный адрес.
2. Проверить `/etc/hosts` — нет ли там устаревшей записи, перекрывающей DNS.
3. Проверить `/etc/resolv.conf`: правильные ли серверы, не перезаписан ли он DHCP-клиентом/NetworkManager, корректны ли `search`-домены (короткие имена).
4. Доступность DNS-сервера: `nc -vzu <ns> 53`, firewall для UDP **и TCP** 53 (большие ответы идут по TCP).
5. Сравнить ответы разных серверов: проблема у конкретного резолвера (устаревший кеш) или у авторитативного сервера (`dig NS example.com`, затем `dig @ns1.example.com`).
6. Кеширование: TTL, отрицательный кеш, локальные кеши (`resolvectl flush-caches`, nscd, кеш в JVM — `networkaddress.cache.ttl`).
7. Split-horizon DNS: внутреннее имя резолвится только внутренним сервером/через VPN.
8. В Kubernetes: `ndots:5` и search-домены, работоспособность CoreDNS (`kubectl -n kube-system logs -l k8s-app=kube-dns`), NetworkPolicy к kube-dns, conntrack-гонки с UDP.

## Q: Как работает DHCP?
level: middle
type: theory
freq: 2
tags: dhcp

**DHCP** (Dynamic Host Configuration Protocol) автоматически выдаёт клиенту IP-адрес и сетевые параметры: маску, шлюз (option 3), DNS-серверы (option 6), домен поиска, NTP, MTU и др. Работает поверх **UDP**: сервер слушает порт **67**, клиент — **68**. Прикладной уровень (L7), хотя обслуживает настройку L3.

**Получение адреса — процесс DORA:**
1. **Discover** — клиент без адреса шлёт **широковещательный** запрос (src 0.0.0.0 → dst 255.255.255.255) со своим MAC-адресом.
2. **Offer** — один или несколько серверов предлагают адрес и параметры.
3. **Request** — клиент выбирает одно предложение и широковещательно запрашивает его (чтобы остальные серверы узнали, что их предложение отклонено).
4. **Acknowledge** — сервер подтверждает аренду (**lease**) на определённое время.

Перед использованием клиент может проверить адрес на конфликт через ARP.

**Продление аренды:**
- в момент **T1** (50% срока) клиент unicast-запросом продлевает аренду у своего сервера;
- в момент **T2** (87.5%) — широковещательно у любого сервера;
- по истечении аренды адрес нужно освободить и начать заново. **Release** — добровольный отказ от адреса.

**DHCP relay** (`ip helper-address`): широковещательные пакеты не проходят через маршрутизаторы, поэтому для обслуживания нескольких VLAN одним сервером роутер пересылает запросы на сервер unicast-ом (option 82 — информация о порте/коммутаторе).

**Практика DevOps:**
- Резервирование адреса за MAC (static lease).
- В облаках DHCP предоставляет сама платформа (AWS VPC DHCP options set — DNS-серверы и домен).
- Клиенты в Linux: `dhclient`, `systemd-networkd`, NetworkManager; DHCP-клиент может **перезаписывать `/etc/resolv.conf`** — частая причина «внезапно сломавшегося» DNS.
- Безопасность: поддельный DHCP-сервер (rogue DHCP) может выдать свой шлюз и DNS → MITM; защита — **DHCP snooping** на коммутаторах.
- Диагностика: `journalctl -u systemd-networkd`, `tcpdump -n -i eth0 port 67 or port 68`.

## Q: Чем сокет отличается от порта?
level: middle
type: theory
freq: 2
tags: tcp, сокеты

- **Порт** — 16-битное число (0–65535) в заголовке TCP/UDP, идентифицирующее приложение на хосте. Это **часть адреса**, а не объект. Диапазоны: 0–1023 — системные (нужны root или `CAP_NET_BIND_SERVICE`), 1024–49151 — зарегистрированные, эфемерные для исходящих соединений — в Linux `net.ipv4.ip_local_port_range` (по умолчанию 32768–60999).
- **Сокет** — **объект ОС** (файловый дескриптор), конечная точка сетевого взаимодействия, через который процесс читает и пишет данные. Создаётся системным вызовом `socket()`, далее `bind()`, `listen()`/`accept()` на сервере или `connect()` на клиенте.

Ключевое: TCP-соединение однозначно определяется **четвёркой** (а с протоколом — пятёркой): `src IP, src port, dst IP, dst port (+ протокол)`. Поэтому:
- на **одном порту** 443 сервер держит **один слушающий сокет** и **тысячи сокетов соединений** — у каждого свой адрес и порт клиента;
- один и тот же номер порта может одновременно использоваться TCP и UDP;
- ограничение «~64 тысячи соединений» относится к исходящим соединениям **с одного IP на один и тот же dst IP:port**, а не к серверу.

Другие виды сокетов:
- **Unix domain sockets** (`/var/run/docker.sock`, `/run/postgresql/.s.PGSQL.5432`) — межпроцессное взаимодействие на одном хосте через файл в ФС, без сетевого стека, быстрее TCP через loopback; доступ контролируется правами файла.
- raw-сокеты (ping, tcpdump), netlink (взаимодействие с ядром).

Посмотреть: `ss -tlnp` (слушающие TCP), `ss -tanp` (все соединения с состояниями), `ss -xlp` (Unix-сокеты), `ls -l /proc/PID/fd` (сокеты как дескрипторы).

## Q: Чем симметричное шифрование отличается от асимметричного? Где используется каждое?
level: middle
type: theory
freq: 3
tags: криптография, tls

**Симметричное шифрование** — **один общий ключ** для шифрования и расшифровки.
- Алгоритмы: **AES** (AES-128/256 в режиме GCM), **ChaCha20-Poly1305**; устаревшие — DES, 3DES, RC4.
- Плюсы: очень быстрое (AES ускорен аппаратно — инструкции AES-NI), подходит для больших объёмов данных.
- Минус: **проблема распределения ключа**. Как безопасно передать общий ключ собеседнику, если канал ещё не защищён?

**Асимметричное шифрование** — **пара ключей**: открытый (public) можно раздавать всем, закрытый (private) хранится только у владельца.
- Зашифрованное **открытым** ключом расшифровывается только **закрытым** (конфиденциальность).
- Подписанное **закрытым** ключом проверяется **открытым** (**цифровая подпись**: подлинность и целостность).
- Алгоритмы: **RSA**, **ECDSA**/**Ed25519** (подписи), **(EC)DH / X25519** (согласование общего ключа).
- Минусы: в сотни и тысячи раз медленнее симметричного, ограничение на размер данных.

**На практике их комбинируют (гибридная схема):** асимметричная криптография нужна, чтобы проверить подлинность и договориться о ключе, а симметричная шифрует сами данные.
- **TLS/HTTPS**: сертификат сервера (открытый ключ, подписанный CA) и подпись handshake → обмен ECDHE → общий **сессионный** симметричный ключ → данные шифруются AES-GCM/ChaCha20.
- **SSH**: ключи хоста и пользователя (Ed25519/RSA) для аутентификации, обмен ключами Diffie–Hellman, затем симметричный шифр сессии.
- **PGP/GPG, SOPS, age**: данные шифруются случайным симметричным ключом, а он — открытыми ключами получателей.
- Подписи артефактов (cosign), коммитов (GPG/SSH signing), JWT (RS256 — асимметричная подпись, HS256 — симметричный HMAC).

**Не путать с хешированием**: SHA-256 — односторонняя функция без ключа (целостность, отпечатки). Пароли хранят медленными хешами с солью (bcrypt, scrypt, Argon2), а не шифруют.

## Q: Как снять и проанализировать дамп сетевого трафика?
level: senior
type: practice
freq: 2
tags: tcpdump, траблшутинг

**tcpdump** — основной инструмент на серверах:
```bash
tcpdump -i any -nn host 10.0.0.5 and port 5432          # -nn: не резолвить имена и порты
tcpdump -i eth0 -nn 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'   # только SYN и RST
tcpdump -i any -nn -s 0 -w /tmp/cap.pcap port 443 -C 100 -W 5  # запись в файл с ротацией
tcpdump -A -nn port 80                                   # показать содержимое (HTTP в открытом виде)
tcpdump -i any -nn udp port 53                           # DNS-запросы и ответы
```
Фильтры BPF: `host`, `net 10.0.0.0/24`, `port`, `src`/`dst`, `tcp`/`udp`/`icmp`, `and`/`or`/`not`. Фильтровать нужно сразу, чтобы не захлебнуться трафиком и не перегрузить диск.

**Анализ** — в **Wireshark** (локально, открыв `.pcap`) или **tshark** на сервере:
- *Statistics → Conversations* и *Follow TCP Stream* — увидеть диалог целиком;
- фильтры `tcp.analysis.retransmission`, `tcp.analysis.zero_window`, `tcp.flags.reset==1`, `dns.flags.rcode != 0`, `http.response.code >= 500`;
- расшифровка TLS при наличии `SSLKEYLOGFILE` от клиента.

**Что ищем:**
- SYN уходит, SYN-ACK не возвращается → firewall, security group, маршрутизация;
- сразу RST → порт закрыт или соединение отвергнуто;
- ретрансмиты и дубли ACK → потери в сети, перегрузка;
- zero window → получатель не успевает читать (тормозит приложение);
- большие паузы между запросом и ответом → медленный сервер, а не сеть;
- проблемы MTU: большие пакеты пропадают, ICMP «fragmentation needed».

**Где снимать:** с обеих сторон соединения, чтобы понять, где теряются пакеты.
- В Kubernetes: `kubectl debug` с образом `nicolaka/netshoot`, `nsenter -t <PID> -n tcpdump` на ноде, плагин `kubectl sniff`.
- В облаке: VPC Traffic Mirroring, Flow Logs (только метаданные).

**Осторожно:** дамп может содержать персональные данные и секреты, поэтому нужно ограничивать захват (`-s` длина пакета, фильтры), хранить его безопасно и удалять после анализа.

## Q: Что такое VLAN и VXLAN? Чем они отличаются?
level: senior
type: theory
freq: 2
tags: vlan, vxlan, overlay

**VLAN** (IEEE 802.1Q) — логическое разделение **одной физической L2-сети** на изолированные широковещательные домены.
- В Ethernet-кадр добавляется 4-байтовый тег с **VLAN ID** (12 бит → до **4094** VLAN).
- Порты коммутатора: **access** (один VLAN, без тега, для конечных устройств) и **trunk** (несколько VLAN с тегами, между коммутаторами и до гипервизоров).
- Трафик между VLAN идёт только через маршрутизатор или L3-коммутатор, а значит, проходит через firewall.
- Применение: разделить сети пользователей, серверов, управления (IPMI/iLO), хранилищ; изолировать арендаторов.
- В Linux: `ip link add link eth0 name eth0.100 type vlan id 100`.

**VXLAN** (RFC 7348) — **оверлей**: L2-кадры инкапсулируются в **UDP** (порт **4789**) и передаются поверх обычной **L3 IP-сети**.
- Идентификатор сети **VNI** — 24 бита → до **16 миллионов** сегментов (против 4094 у VLAN).
- Позволяет растянуть L2-сегмент между стойками, ЦОДами, хостами через маршрутизируемую сеть.
- Концы туннеля — **VTEP** (на гипервизоре, коммутаторе или ноде Kubernetes). Как VTEP узнают друг о друге: multicast, статические списки или **EVPN** (BGP) в современных фабриках.
- Накладные расходы: +50 байт на пакет → нужно увеличить MTU в underlay (jumbo frames) или уменьшить MTU внутри оверлея (1450 вместо 1500). Типичный источник «зависающих» больших запросов.

| | VLAN | VXLAN |
|---|---|---|
| Уровень | L2-тег в Ethernet | L2 поверх UDP/IP (L3) |
| Количество сетей | 4094 | ~16 млн |
| Границы | один L2-домен (коммутаторы) | любая IP-сеть, между ЦОДами |
| Где используется | офисы, ЦОД, гипервизоры | облака, SDN, Kubernetes CNI (Flannel, Calico, Cilium в VXLAN-режиме), VMware NSX, OpenStack |

## Q: Как построить VPN? Какие технологии и схемы бывают?
level: senior
type: design
freq: 2
tags: vpn, ipsec, wireguard

**Сначала уточнить задачу.** Есть два основных сценария:
- **Site-to-site** — связать сети целиком: офис ↔ ЦОД, on-prem ↔ облачная VPC, облако ↔ облако. Маршрутизаторы или шлюзы держат постоянный туннель, пользователи ничего не настраивают.
- **Remote access** — подключение сотрудников к внутренней сети с ноутбуков.

**Технологии:**
| | IPsec | WireGuard | OpenVPN |
|---|---|---|---|
| Уровень | L3, в ядре | L3, в ядре Linux | userspace, TLS |
| Транспорт | ESP + IKEv2 (UDP 500/4500) | UDP (один порт) | UDP или TCP (можно 443) |
| Плюсы | стандарт, поддерживается всеми роутерами и облаками | очень прост, быстр, ~4000 строк кода, современная криптография | гибкий, проходит через строгие firewall |
| Минусы | сложная настройка, много параметров для согласования | нет встроенного управления пользователями и выдачи адресов | медленнее, сложнее PKI |

**Пример site-to-site (офис ↔ AWS):** AWS Site-to-Site VPN — два IPsec-туннеля к разным конечным точкам для отказоустойчивости, маршрутизация через **BGP** (динамически) или статическая, Virtual Private Gateway / Transit Gateway. Для высоких скоростей и стабильной задержки — Direct Connect / Cloud Interconnect.

**Пример WireGuard между двумя площадками:**
```ini
# /etc/wireguard/wg0.conf на шлюзе A
[Interface]
Address = 10.99.0.1/30
PrivateKey = <ключ A>
ListenPort = 51820

[Peer]
PublicKey = <ключ B>
Endpoint = b.example.com:51820
AllowedIPs = 10.99.0.2/32, 192.168.20.0/24   # сети за шлюзом B
PersistentKeepalive = 25
```
Затем включить `net.ipv4.ip_forward=1`, разрешить трафик в firewall и прописать маршруты в сети B на обеих сторонах (или анонсировать их через BGP).

**Ключевые вопросы проектирования:**
- **Непересекающиеся адресные пространства** на площадках, иначе нужен NAT, а это боль.
- **Отказоустойчивость**: два туннеля, два шлюза, динамическая маршрутизация (BGP), мониторинг состояния туннелей.
- **MTU/MSS**: инкапсуляция уменьшает MTU → `MSS clamping` на шлюзах.
- **Split tunnel vs full tunnel** для пользователей: только корпоративные сети или весь трафик.
- **Аутентификация**: сертификаты/ключи, для пользователей — SSO и MFA, быстрый отзыв доступа.
- **Сегментация**: VPN не должен давать доступ ко всей сети. Нужны правила по ролям.

**Современная альтернатива** классическому remote-access VPN — Zero Trust и mesh-VPN: Tailscale/Headscale, Netbird (на основе WireGuard, с SSO и ACL), identity-aware proxy (Teleport, Cloudflare Access) для доступа к конкретным сервисам вместо сети целиком.
