# Ключевые концепции

Сетевые вопросы — второй по частоте блок после Linux. Senior должен уверенно объяснить путь пакета от клиента до приложения и уметь локализовать сетевую проблему.

### Модели OSI и TCP/IP
| OSI | Уровень | Примеры |
|---|---|---|
| 7 | Прикладной | HTTP, DNS, gRPC |
| 6–5 | Представления / сеансовый | TLS (условно) |
| 4 | Транспортный | TCP, UDP, QUIC (поверх UDP) |
| 3 | Сетевой | IP, ICMP, маршрутизация |
| 2 | Канальный | Ethernet, ARP, VLAN, MAC |
| 1 | Физический | кабель, радио |

### Что нужно знать
- TCP: handshake, состояния (`SYN_SENT`, `ESTABLISHED`, `TIME_WAIT`, `CLOSE_WAIT`), окна, ретрансмиты, Nagle.
- Адресация: CIDR, приватные диапазоны (10/8, 172.16/12, 192.168/16), NAT/SNAT/DNAT, маршрутизация.
- DNS: рекурсия, записи, TTL, кеширование, `/etc/resolv.conf`, `ndots` в Kubernetes.
- HTTP/1.1, HTTP/2, HTTP/3, коды ответов, keep-alive.
- TLS 1.2/1.3, сертификаты, цепочки доверия, SNI, mTLS.
- Балансировка L4 vs L7, health checks, sticky sessions.
- Linux-сеть: `ip`, `ss`, `iptables/nftables`, conntrack, `tcpdump`, `dig`, `curl -v`, `mtr`.

## Q: Что происходит, когда вы вводите URL в браузере и нажимаете Enter?
level: middle
type: theory
freq: 3
tags: dns, http, tls

Классический вопрос, где можно показать глубину. Основные шаги:

1. **Разбор URL** и проверка HSTS-списка (принудительный HTTPS).
2. **DNS-резолв**: кеш браузера → кеш ОС (`/etc/hosts`, systemd-resolved) → рекурсивный резолвер → корневые серверы → TLD (`.com`) → авторитативный сервер домена. Ответ кешируется на TTL.
3. **TCP-соединение**: 3-way handshake SYN → SYN-ACK → ACK (для HTTP/3 — QUIC поверх UDP, handshake совмещён с TLS). Перед этим — ARP для MAC-адреса шлюза, маршрутизация, NAT на роутере.
4. **TLS handshake**: ClientHello (с SNI и поддерживаемыми шифрами) → ServerHello + сертификат → проверка цепочки до доверенного корня, срока, имени → обмен ключами (ECDHE) → симметричное шифрование. TLS 1.3 — 1 RTT, возможен 0-RTT.
5. **HTTP-запрос** `GET /` с заголовками (Host, Cookie, Accept-Encoding).
6. **На стороне сервера**: CDN/WAF → L4/L7 балансировщик → reverse proxy (nginx/Ingress) → приложение → БД/кеш.
7. **Ответ**: статус, заголовки (Cache-Control, Set-Cookie), тело. Браузер парсит HTML, загружает ресурсы (часто параллельно по HTTP/2), рендерит страницу.

На senior-уровне хорошо упомянуть, где на каждом этапе может сломаться и как это диагностировать (`dig`, `curl -v --resolve`, `openssl s_client`).

**Вариант вопроса: «что происходит при `curl ya.ru`?»** Отличия от браузера:
- нет схемы → curl использует **HTTP** (порт 80), а не HTTPS; HSTS-кеша у curl по умолчанию нет;
- резолв через `getaddrinfo()` (nsswitch → `/etc/hosts` → DNS), подключение к IPv6 или IPv4 (Happy Eyeballs);
- сервер, скорее всего, ответит **301/302 редиректом** на `https://ya.ru/`, но curl **не следует редиректам** без флага `-L` и просто выведет тело ответа с редиректом;
- нет рендеринга, JavaScript, загрузки ресурсов страницы, cookies (без `-b/-c`);
- `curl -v` покажет каждый этап: резолв, `Connected to ...`, TLS handshake, заголовки запроса (`>`) и ответа (`<`); `curl -w '%{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer}\n'` — тайминги каждого этапа для диагностики.

## Q: Чем отличаются TCP и UDP? Опишите установку и закрытие TCP-соединения.
level: middle
type: theory
freq: 3
tags: tcp, udp

| | TCP | UDP |
|---|---|---|
| Соединение | есть (handshake) | нет |
| Надёжность | подтверждения, ретрансмиты, порядок | нет гарантий |
| Контроль перегрузки | есть (окна, cubic/BBR) | нет |
| Накладные расходы | выше | ниже |
| Применение | HTTP/1-2, БД, SSH | DNS, VoIP, видео, QUIC/HTTP3 |

**Установка**: SYN → SYN-ACK → ACK. Клиент выбирает начальный sequence number, сервер подтверждает его и отправляет свой.

**Закрытие** (4 сегмента): FIN → ACK, затем FIN → ACK. Сторона, закрывшая первой, переходит в **TIME_WAIT** на 2×MSL (в Linux 60 секунд), чтобы поздние пакеты старого соединения не попали в новое и чтобы корректно повторить последний ACK.

Проблемы:
- Много **TIME_WAIT** на клиенте (например, прокси, открывающий новое соединение на каждый запрос) → исчерпание эфемерных портов. Лечение: keep-alive/пулы соединений, `net.ipv4.tcp_tw_reuse`, расширение `ip_local_port_range`.
- Много **CLOSE_WAIT** → баг в приложении: удалённая сторона закрыла соединение, а приложение не вызывает `close()`.

## Q: Как работает DNS? Какие типы записей вы знаете?
level: middle
type: theory
freq: 3
tags: dns

DNS — распределённая иерархическая база. Клиент (stub resolver) спрашивает **рекурсивный резолвер**, тот итеративно идёт: корень → TLD → авторитативный сервер зоны. Ответы кешируются на **TTL**.

Записи:
- **A / AAAA** — имя → IPv4 / IPv6;
- **CNAME** — алиас на другое имя (нельзя на apex зоны и вместе с другими записями; облака решают через ALIAS/ANAME);
- **MX** — почтовые серверы; **TXT** — SPF, DKIM, верификация домена;
- **NS** — авторитативные серверы зоны; **SOA** — параметры зоны;
- **PTR** — обратная зона (IP → имя);
- **SRV** — сервис + порт (используется в k8s, Consul).

Практика и подводные камни:
- Порядок резолва в Linux задаёт `/etc/nsswitch.conf` (`hosts: files dns`), поэтому `/etc/hosts` срабатывает раньше DNS.
- Перед миграцией **заранее снижать TTL**.
- Отрицательное кеширование (NXDOMAIN кешируется по SOA minimum).
- Kubernetes: `ndots:5` в `resolv.conf` → короткое внешнее имя сначала перебирается по всем search-доменам, что даёт лишние запросы и задержки. Решение — FQDN с точкой на конце или уменьшить `ndots`, NodeLocal DNSCache.
- DNS по умолчанию работает по UDP/53, но переходит на TCP для больших ответов (и для AXFR).

Инструменты: `dig +trace example.com`, `dig @8.8.8.8`, `host`, `resolvectl`.

## Q: В чём разница между HTTP/1.1, HTTP/2 и HTTP/3?
level: senior
type: theory
freq: 2
tags: http

- **HTTP/1.1**: текстовый протокол, keep-alive, но один запрос за раз на соединение → **head-of-line blocking** на уровне приложения. Браузеры открывают 6 соединений на хост; отсюда старые оптимизации (спрайты, шардинг доменов).
- **HTTP/2**: бинарный фрейминг, **мультиплексирование** множества потоков в одном TCP-соединении, сжатие заголовков HPACK, приоритеты, server push (фактически устарел). Проблема: HOL-блокировка переехала на уровень TCP — потеря одного пакета тормозит все потоки. Основа **gRPC**.
- **HTTP/3**: поверх **QUIC** (UDP). Независимые потоки без HOL-блокировки на транспорте, TLS 1.3 встроен, быстрый handshake (1-RTT, 0-RTT), **connection migration** (смена IP у мобильного клиента без разрыва). Сжатие заголовков QPACK.

Для DevOps важно: gRPC через L4-балансировщик распределяется плохо (одно долгоживущее соединение → весь трафик на один под) — нужен L7-балансинг (Envoy, service mesh) или клиентская балансировка. HTTP/3 требует открытого UDP/443.

## Q: Как работает TLS? Что такое mTLS?
level: senior
type: theory
freq: 3
tags: tls, безопасность

**TLS** обеспечивает конфиденциальность (шифрование), целостность и аутентификацию сервера.

Handshake TLS 1.3 (упрощённо):
1. ClientHello: версии, наборы шифров, **key share** (ECDHE), SNI (имя хоста).
2. ServerHello + key share → обе стороны вычисляют общий секрет; дальше всё зашифровано.
3. Сервер отправляет сертификат и подпись (CertificateVerify), Finished.
4. Клиент проверяет цепочку сертификатов до доверенного корневого CA, срок действия, соответствие имени (SAN), отзыв (OCSP).

**Асимметричная криптография** используется для обмена ключами и аутентификации, **симметричная** (AES-GCM, ChaCha20) — для данных. ECDHE даёт **perfect forward secrecy**.

**mTLS** — сервер тоже запрашивает сертификат клиента и проверяет его. Применение: межсервисная аутентификация в service mesh (Istio, Linkerd автоматически выдают и ротируют сертификаты), доступ к API, zero trust.

Частые проблемы: неполная цепочка (нет intermediate), истёкший сертификат (нужен мониторинг сроков и автоматизация — cert-manager, ACME), несоответствие SNI. Отладка: `openssl s_client -connect host:443 -servername host -showcerts`.

## Q: Чем балансировка L4 отличается от L7?
level: senior
type: theory
freq: 3
tags: балансировка

**L4** (транспортный уровень) — балансирует TCP/UDP-соединения по IP и порту, не заглядывая в содержимое. Быстро, дёшево, поддерживает любые протоколы, может сохранять IP клиента. Примеры: AWS NLB, IPVS, HAProxy в режиме tcp, MetalLB.

**L7** (прикладной уровень) — понимает HTTP/gRPC: маршрутизация по хосту, пути, заголовкам, cookie; терминирует TLS; ретраи, rate limiting, WAF, канареечные деплои по весам, балансировка отдельных запросов (важно для HTTP/2 и gRPC). Дороже по ресурсам, добавляет латентность. Примеры: AWS ALB, nginx, Envoy, Traefik, Ingress-контроллеры.

Алгоритмы: round-robin, least connections, weighted, consistent hashing (для кешей/sticky), EWMA/P2C (Envoy).

Важные детали: **health checks** (активные и пассивные/outlier detection), передача IP клиента (`X-Forwarded-For`, PROXY protocol), connection draining при выводе бэкенда, таймауты на каждом уровне.

## Q: Пользователи получают 502 и 504 от nginx. Чем они отличаются и как искать причину?
level: senior
type: scenario
freq: 3
tags: http, nginx, траблшутинг

- **502 Bad Gateway** — прокси получил **некорректный ответ** или вообще не смог получить ответ от апстрима: апстрим не слушает порт (connection refused), упал во время запроса, сбросил соединение, превышен размер заголовков ответа, рассинхрон keep-alive (апстрим закрыл соединение раньше, чем прокси попытался его переиспользовать).
- **504 Gateway Timeout** — апстрим не ответил за `proxy_read_timeout` (по умолчанию 60с): медленный запрос, зависшие воркеры, медленная БД, исчерпан пул соединений.
- **503** — сервис недоступен: нет живых бэкендов, rate limiting, в k8s — нет ready-эндпоинтов.

Диагностика:
1. `error.log` nginx — там точная причина (`connect() failed (111: Connection refused)`, `upstream prematurely closed connection`, `upstream timed out`).
2. Корреляция с деплоями: 502 во время rolling update — поды убиваются до того, как их вывели из балансировки → нужен `preStop` sleep и graceful shutdown.
3. Состояние апстрима: живы ли процессы, загрузка воркеров, логи приложения, метрики латентности.
4. Таймауты keep-alive: таймаут простоя у апстрима должен быть **больше**, чем у прокси (классика с Node.js `keepAliveTimeout` за ALB).
5. Проверить напрямую: `curl -v http://upstream:port/health` с хоста прокси.

## Q: Как вы будете диагностировать, что сервис A не может достучаться до сервиса B?
level: senior
type: scenario
freq: 3
tags: траблшутинг, сеть

Идти **снизу вверх по стеку**:

1. **DNS**: `dig B` / `getent hosts B` — резолвится ли имя, в правильный ли адрес.
2. **Маршрут и L3**: `ip route get <IP>`, `ping` (ICMP может быть запрещён), `mtr`/`traceroute` — где теряются пакеты.
3. **L4-порт**: `nc -zv B 443`, `curl -v telnet://B:443`. Результат информативен:
   - *Connection refused* — хост доступен, но порт никто не слушает (или REJECT в firewall);
   - *Timeout* — пакеты дропаются: security group, NACL, firewall, NetworkPolicy, отсутствует маршрут;
   - *No route to host* — проблема маршрутизации или ICMP-reject.
4. **На стороне B**: `ss -tlnp` — слушает ли сервис и на каком адресе (`127.0.0.1` vs `0.0.0.0` — частая ошибка).
5. **Firewall**: `iptables -L -n -v`/`nft list ruleset`, облачные SG/NACL, k8s NetworkPolicy.
6. **TLS/L7**: `openssl s_client`, `curl -v` — сертификат, SNI, коды ответа, авторизация.
7. **Захват трафика**: `tcpdump -i any host B and port 443 -nn` на обеих сторонах — уходит ли SYN, приходит ли SYN-ACK.

Также проверить: MTU (большие пакеты теряются в туннелях/VPN — `ping -M do -s 1472`), conntrack table full (`dmesg: nf_conntrack: table full`), асимметричную маршрутизацию.

## Q: Объясните CIDR и разбейте сеть 10.0.0.0/16 на подсети для VPC.
level: middle
type: practice
freq: 2
tags: ip, cidr

**CIDR** — запись адреса с длиной префикса: `/16` означает, что первые 16 бит — сеть, оставшиеся 16 — хосты → 65 536 адресов. `/24` — 256 адресов (в AWS из каждой подсети резервируется 5).

Формула: адресов в подсети = 2^(32 − префикс).

Пример разбиения `10.0.0.0/16` на 3 AZ:
| Подсеть | CIDR | Адресов |
|---|---|---|
| public-a/b/c | 10.0.0.0/24, 10.0.1.0/24, 10.0.2.0/24 | 256 |
| private-a/b/c (приложения, поды) | 10.0.32.0/19, 10.0.64.0/19, 10.0.96.0/19 | 8192 |
| db-a/b/c | 10.0.10.0/24, 10.0.11.0/24, 10.0.12.0/24 | 256 |

Senior-моменты: оставлять резерв для роста; **не пересекать** диапазоны между VPC, офисом и on-prem (иначе невозможен peering/VPN); для EKS с VPC CNI каждый под получает IP из подсети — нужны крупные подсети или secondary CIDR / prefix delegation; учитывать диапазоны Service/Pod CIDR в Kubernetes.

## Q: Что такое NAT и conntrack? Какие проблемы с ними бывают?
level: senior
type: theory
freq: 2
tags: nat, iptables

**NAT** — подмена адресов в пакетах. **SNAT/masquerade** — исходящий трафик из приватной сети выходит под одним публичным IP (домашний роутер, NAT Gateway в облаке). **DNAT** — входящий трафик на публичный адрес перенаправляется во внутреннюю сеть (port forwarding, Kubernetes Service через kube-proxy в режиме iptables).

Чтобы ответные пакеты вернулись правильно, ядро ведёт таблицу **conntrack** — состояние каждого соединения.

Проблемы:
- **Переполнение conntrack** (`nf_conntrack: table full, dropping packet`) при большом числе коротких соединений → случайные таймауты. Мониторить `nf_conntrack_count` vs `nf_conntrack_max`.
- **Исчерпание портов SNAT** — к одному назначению через один NAT-IP максимум ~64к соединений; в AWS NAT Gateway — ошибки `ErrorPortAllocation`.
- **Race condition в conntrack с UDP** — известная проблема с DNS в Kubernetes (5-секундные задержки), решается NodeLocal DNSCache или `single-request-reopen`.
- Стоимость: трафик через облачный NAT Gateway платный — использовать VPC endpoints для S3/ECR.

## Q: Имя не резолвится. Как диагностировать проблему с DNS на Linux-хосте?
level: senior
type: scenario
freq: 3
tags: dns, траблшутинг

Важно понимать, **в каком порядке** система ищет имя, и что разные утилиты идут разными путями.

**Порядок резолва в glibc:**
1. `/etc/nsswitch.conf` — строка `hosts: files dns` (или `files resolve [!UNAVAIL=return] myhostname dns`) задаёт источники и их порядок: сначала `/etc/hosts`, потом DNS.
2. `/etc/hosts` — статические записи.
3. `/etc/resolv.conf` — список `nameserver` (максимум 3), опрашиваются **по порядку**: следующий только при таймауте предыдущего (`options timeout:2 attempts:2`), либо по кругу с `options rotate`. Также `search` и `ndots`.
4. Часто там `nameserver 127.0.0.53` — локальный **systemd-resolved**, который уже сам ходит к upstream-серверам (смотреть `resolvectl status`, серверы задаются для каждого интерфейса отдельно, через DHCP или netplan/NetworkManager).

**Почему `dig` работает, а приложение — нет (и наоборот):** `dig`/`nslookup`/`host` обращаются к DNS-серверу **напрямую**, игнорируя nsswitch и `/etc/hosts`. Приложения используют `getaddrinfo()` → nsswitch. Поэтому проверять обоими способами:
```bash
getent hosts api.example.com      # как увидит приложение (nsswitch)
getent ahosts api.example.com     # с IPv4 и IPv6
dig api.example.com               # прямой запрос к серверу из resolv.conf
dig @8.8.8.8 api.example.com      # в обход локального резолвера
dig +trace api.example.com        # от корня до авторитативного сервера
resolvectl query api.example.com  # через systemd-resolved
```

**Пошаговая диагностика:**
1. Какой ответ: `NXDOMAIN` (имени нет), `SERVFAIL` (сбой на сервере, часто DNSSEC или недоступен авторитативный), таймаут (нет связи с DNS-сервером), или имя резолвится, но в неверный адрес.
2. Проверить `/etc/hosts` — нет ли там устаревшей записи, перекрывающей DNS.
3. Проверить `/etc/resolv.conf`: правильные ли серверы, не перезаписан ли он DHCP-клиентом/NetworkManager, корректны ли `search`-домены (короткие имена).
4. Доступность DNS-сервера: `nc -vzu <ns> 53`, firewall для UDP **и TCP** 53 (большие ответы идут по TCP).
5. Сравнить ответы разных серверов: проблема у конкретного резолвера (устаревший кеш) или у авторитативного сервера (`dig NS example.com`, затем `dig @ns1.example.com`).
6. Кеширование: TTL, отрицательный кеш, локальные кеши (`resolvectl flush-caches`, nscd, кеш в JVM — `networkaddress.cache.ttl`).
7. Split-horizon DNS: внутреннее имя резолвится только внутренним сервером/через VPN.
8. В Kubernetes: `ndots:5` и search-домены, работоспособность CoreDNS (`kubectl -n kube-system logs -l k8s-app=kube-dns`), NetworkPolicy к kube-dns, conntrack-гонки с UDP.

## Q: Как работает DHCP?
level: middle
type: theory
freq: 2
tags: dhcp

**DHCP** (Dynamic Host Configuration Protocol) автоматически выдаёт клиенту IP-адрес и сетевые параметры: маску, шлюз (option 3), DNS-серверы (option 6), домен поиска, NTP, MTU и др. Работает поверх **UDP**: сервер слушает порт **67**, клиент — **68**. Прикладной уровень (L7), хотя обслуживает настройку L3.

**Получение адреса — процесс DORA:**
1. **Discover** — клиент без адреса шлёт **широковещательный** запрос (src 0.0.0.0 → dst 255.255.255.255) со своим MAC-адресом.
2. **Offer** — один или несколько серверов предлагают адрес и параметры.
3. **Request** — клиент выбирает одно предложение и широковещательно запрашивает его (чтобы остальные серверы узнали, что их предложение отклонено).
4. **Acknowledge** — сервер подтверждает аренду (**lease**) на определённое время.

Перед использованием клиент может проверить адрес на конфликт через ARP.

**Продление аренды:**
- в момент **T1** (50% срока) клиент unicast-запросом продлевает аренду у своего сервера;
- в момент **T2** (87.5%) — широковещательно у любого сервера;
- по истечении аренды адрес нужно освободить и начать заново. **Release** — добровольный отказ от адреса.

**DHCP relay** (`ip helper-address`): широковещательные пакеты не проходят через маршрутизаторы, поэтому для обслуживания нескольких VLAN одним сервером роутер пересылает запросы на сервер unicast-ом (option 82 — информация о порте/коммутаторе).

**Практика DevOps:**
- Резервирование адреса за MAC (static lease).
- В облаках DHCP предоставляет сама платформа (AWS VPC DHCP options set — DNS-серверы и домен).
- Клиенты в Linux: `dhclient`, `systemd-networkd`, NetworkManager; DHCP-клиент может **перезаписывать `/etc/resolv.conf`** — частая причина «внезапно сломавшегося» DNS.
- Безопасность: поддельный DHCP-сервер (rogue DHCP) может выдать свой шлюз и DNS → MITM; защита — **DHCP snooping** на коммутаторах.
- Диагностика: `journalctl -u systemd-networkd`, `tcpdump -n -i eth0 port 67 or port 68`.

## Q: Чем сокет отличается от порта?
level: middle
type: theory
freq: 2
tags: tcp, сокеты

- **Порт** — 16-битное число (0–65535) в заголовке TCP/UDP, идентифицирующее приложение на хосте. Это **часть адреса**, а не объект. Диапазоны: 0–1023 — системные (нужны root или `CAP_NET_BIND_SERVICE`), 1024–49151 — зарегистрированные, эфемерные для исходящих соединений — в Linux `net.ipv4.ip_local_port_range` (по умолчанию 32768–60999).
- **Сокет** — **объект ОС** (файловый дескриптор), конечная точка сетевого взаимодействия, через который процесс читает и пишет данные. Создаётся системным вызовом `socket()`, далее `bind()`, `listen()`/`accept()` на сервере или `connect()` на клиенте.

Ключевое: TCP-соединение однозначно определяется **четвёркой** (а с протоколом — пятёркой): `src IP, src port, dst IP, dst port (+ протокол)`. Поэтому:
- на **одном порту** 443 сервер держит **один слушающий сокет** и **тысячи сокетов соединений** — у каждого свой адрес и порт клиента;
- один и тот же номер порта может одновременно использоваться TCP и UDP;
- ограничение «~64 тысячи соединений» относится к исходящим соединениям **с одного IP на один и тот же dst IP:port**, а не к серверу.

Другие виды сокетов:
- **Unix domain sockets** (`/var/run/docker.sock`, `/run/postgresql/.s.PGSQL.5432`) — межпроцессное взаимодействие на одном хосте через файл в ФС, без сетевого стека, быстрее TCP через loopback; доступ контролируется правами файла.
- raw-сокеты (ping, tcpdump), netlink (взаимодействие с ядром).

Посмотреть: `ss -tlnp` (слушающие TCP), `ss -tanp` (все соединения с состояниями), `ss -xlp` (Unix-сокеты), `ls -l /proc/PID/fd` (сокеты как дескрипторы).

## Q: Чем симметричное шифрование отличается от асимметричного? Где используется каждое?
level: middle
type: theory
freq: 3
tags: криптография, tls

**Симметричное шифрование** — **один общий ключ** для шифрования и расшифровки.
- Алгоритмы: **AES** (AES-128/256 в режиме GCM), **ChaCha20-Poly1305**; устаревшие — DES, 3DES, RC4.
- Плюсы: очень быстрое (AES ускорен аппаратно — инструкции AES-NI), подходит для больших объёмов данных.
- Минус: **проблема распределения ключа**. Как безопасно передать общий ключ собеседнику, если канал ещё не защищён?

**Асимметричное шифрование** — **пара ключей**: открытый (public) можно раздавать всем, закрытый (private) хранится только у владельца.
- Зашифрованное **открытым** ключом расшифровывается только **закрытым** (конфиденциальность).
- Подписанное **закрытым** ключом проверяется **открытым** (**цифровая подпись**: подлинность и целостность).
- Алгоритмы: **RSA**, **ECDSA**/**Ed25519** (подписи), **(EC)DH / X25519** (согласование общего ключа).
- Минусы: в сотни и тысячи раз медленнее симметричного, ограничение на размер данных.

**На практике их комбинируют (гибридная схема):** асимметричная криптография нужна, чтобы проверить подлинность и договориться о ключе, а симметричная шифрует сами данные.
- **TLS/HTTPS**: сертификат сервера (открытый ключ, подписанный CA) и подпись handshake → обмен ECDHE → общий **сессионный** симметричный ключ → данные шифруются AES-GCM/ChaCha20.
- **SSH**: ключи хоста и пользователя (Ed25519/RSA) для аутентификации, обмен ключами Diffie–Hellman, затем симметричный шифр сессии.
- **PGP/GPG, SOPS, age**: данные шифруются случайным симметричным ключом, а он — открытыми ключами получателей.
- Подписи артефактов (cosign), коммитов (GPG/SSH signing), JWT (RS256 — асимметричная подпись, HS256 — симметричный HMAC).

**Не путать с хешированием**: SHA-256 — односторонняя функция без ключа (целостность, отпечатки). Пароли хранят медленными хешами с солью (bcrypt, scrypt, Argon2), а не шифруют.

## Q: Как снять и проанализировать дамп сетевого трафика?
level: senior
type: practice
freq: 2
tags: tcpdump, траблшутинг

**tcpdump** — основной инструмент на серверах:
```bash
tcpdump -i any -nn host 10.0.0.5 and port 5432          # -nn: не резолвить имена и порты
tcpdump -i eth0 -nn 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'   # только SYN и RST
tcpdump -i any -nn -s 0 -w /tmp/cap.pcap port 443 -C 100 -W 5  # запись в файл с ротацией
tcpdump -A -nn port 80                                   # показать содержимое (HTTP в открытом виде)
tcpdump -i any -nn udp port 53                           # DNS-запросы и ответы
```
Фильтры BPF: `host`, `net 10.0.0.0/24`, `port`, `src`/`dst`, `tcp`/`udp`/`icmp`, `and`/`or`/`not`. Фильтровать нужно сразу, чтобы не захлебнуться трафиком и не перегрузить диск.

**Анализ** — в **Wireshark** (локально, открыв `.pcap`) или **tshark** на сервере:
- *Statistics → Conversations* и *Follow TCP Stream* — увидеть диалог целиком;
- фильтры `tcp.analysis.retransmission`, `tcp.analysis.zero_window`, `tcp.flags.reset==1`, `dns.flags.rcode != 0`, `http.response.code >= 500`;
- расшифровка TLS при наличии `SSLKEYLOGFILE` от клиента.

**Что ищем:**
- SYN уходит, SYN-ACK не возвращается → firewall, security group, маршрутизация;
- сразу RST → порт закрыт или соединение отвергнуто;
- ретрансмиты и дубли ACK → потери в сети, перегрузка;
- zero window → получатель не успевает читать (тормозит приложение);
- большие паузы между запросом и ответом → медленный сервер, а не сеть;
- проблемы MTU: большие пакеты пропадают, ICMP «fragmentation needed».

**Где снимать:** с обеих сторон соединения, чтобы понять, где теряются пакеты.
- В Kubernetes: `kubectl debug` с образом `nicolaka/netshoot`, `nsenter -t <PID> -n tcpdump` на ноде, плагин `kubectl sniff`.
- В облаке: VPC Traffic Mirroring, Flow Logs (только метаданные).

**Осторожно:** дамп может содержать персональные данные и секреты, поэтому нужно ограничивать захват (`-s` длина пакета, фильтры), хранить его безопасно и удалять после анализа.

## Q: Что такое VLAN и VXLAN? Чем они отличаются?
level: senior
type: theory
freq: 2
tags: vlan, vxlan, overlay

**VLAN** (IEEE 802.1Q) — логическое разделение **одной физической L2-сети** на изолированные широковещательные домены.
- В Ethernet-кадр добавляется 4-байтовый тег с **VLAN ID** (12 бит → до **4094** VLAN).
- Порты коммутатора: **access** (один VLAN, без тега, для конечных устройств) и **trunk** (несколько VLAN с тегами, между коммутаторами и до гипервизоров).
- Трафик между VLAN идёт только через маршрутизатор или L3-коммутатор, а значит, проходит через firewall.
- Применение: разделить сети пользователей, серверов, управления (IPMI/iLO), хранилищ; изолировать арендаторов.
- В Linux: `ip link add link eth0 name eth0.100 type vlan id 100`.

**VXLAN** (RFC 7348) — **оверлей**: L2-кадры инкапсулируются в **UDP** (порт **4789**) и передаются поверх обычной **L3 IP-сети**.
- Идентификатор сети **VNI** — 24 бита → до **16 миллионов** сегментов (против 4094 у VLAN).
- Позволяет растянуть L2-сегмент между стойками, ЦОДами, хостами через маршрутизируемую сеть.
- Концы туннеля — **VTEP** (на гипервизоре, коммутаторе или ноде Kubernetes). Как VTEP узнают друг о друге: multicast, статические списки или **EVPN** (BGP) в современных фабриках.
- Накладные расходы: +50 байт на пакет → нужно увеличить MTU в underlay (jumbo frames) или уменьшить MTU внутри оверлея (1450 вместо 1500). Типичный источник «зависающих» больших запросов.

| | VLAN | VXLAN |
|---|---|---|
| Уровень | L2-тег в Ethernet | L2 поверх UDP/IP (L3) |
| Количество сетей | 4094 | ~16 млн |
| Границы | один L2-домен (коммутаторы) | любая IP-сеть, между ЦОДами |
| Где используется | офисы, ЦОД, гипервизоры | облака, SDN, Kubernetes CNI (Flannel, Calico, Cilium в VXLAN-режиме), VMware NSX, OpenStack |

## Q: Как построить VPN? Какие технологии и схемы бывают?
level: senior
type: design
freq: 2
tags: vpn, ipsec, wireguard

**Сначала уточнить задачу.** Есть два основных сценария:
- **Site-to-site** — связать сети целиком: офис ↔ ЦОД, on-prem ↔ облачная VPC, облако ↔ облако. Маршрутизаторы или шлюзы держат постоянный туннель, пользователи ничего не настраивают.
- **Remote access** — подключение сотрудников к внутренней сети с ноутбуков.

**Технологии:**
| | IPsec | WireGuard | OpenVPN |
|---|---|---|---|
| Уровень | L3, в ядре | L3, в ядре Linux | userspace, TLS |
| Транспорт | ESP + IKEv2 (UDP 500/4500) | UDP (один порт) | UDP или TCP (можно 443) |
| Плюсы | стандарт, поддерживается всеми роутерами и облаками | очень прост, быстр, ~4000 строк кода, современная криптография | гибкий, проходит через строгие firewall |
| Минусы | сложная настройка, много параметров для согласования | нет встроенного управления пользователями и выдачи адресов | медленнее, сложнее PKI |

**Пример site-to-site (офис ↔ AWS):** AWS Site-to-Site VPN — два IPsec-туннеля к разным конечным точкам для отказоустойчивости, маршрутизация через **BGP** (динамически) или статическая, Virtual Private Gateway / Transit Gateway. Для высоких скоростей и стабильной задержки — Direct Connect / Cloud Interconnect.

**Пример WireGuard между двумя площадками:**
```ini
# /etc/wireguard/wg0.conf на шлюзе A
[Interface]
Address = 10.99.0.1/30
PrivateKey = <ключ A>
ListenPort = 51820

[Peer]
PublicKey = <ключ B>
Endpoint = b.example.com:51820
AllowedIPs = 10.99.0.2/32, 192.168.20.0/24   # сети за шлюзом B
PersistentKeepalive = 25
```
Затем включить `net.ipv4.ip_forward=1`, разрешить трафик в firewall и прописать маршруты в сети B на обеих сторонах (или анонсировать их через BGP).

**Ключевые вопросы проектирования:**
- **Непересекающиеся адресные пространства** на площадках, иначе нужен NAT, а это боль.
- **Отказоустойчивость**: два туннеля, два шлюза, динамическая маршрутизация (BGP), мониторинг состояния туннелей.
- **MTU/MSS**: инкапсуляция уменьшает MTU → `MSS clamping` на шлюзах.
- **Split tunnel vs full tunnel** для пользователей: только корпоративные сети или весь трафик.
- **Аутентификация**: сертификаты/ключи, для пользователей — SSO и MFA, быстрый отзыв доступа.
- **Сегментация**: VPN не должен давать доступ ко всей сети. Нужны правила по ролям.

**Современная альтернатива** классическому remote-access VPN — Zero Trust и mesh-VPN: Tailscale/Headscale, Netbird (на основе WireGuard, с SSO и ACL), identity-aware proxy (Teleport, Cloudflare Access) для доступа к конкретным сервисам вместо сети целиком.

## Q: Расскажите про модель OSI. На каком уровне работают коммутатор, маршрутизатор, балансировщик?
level: middle
type: theory
freq: 3
tags: osi, основы

**OSI** — эталонная 7-уровневая модель сетевого взаимодействия. На практике используется более простой стек **TCP/IP** (4 уровня), но уровни OSI — общий язык («проблема на L3», «балансировщик L7»).

| № | Уровень | Единица данных | Что делает | Протоколы и устройства |
|---|---|---|---|---|
| 7 | Прикладной | данные | взаимодействие приложений | HTTP, DNS, SMTP, SSH, DHCP |
| 6 | Представления | данные | кодирование, шифрование, сжатие | TLS (условно), JPEG, кодировки |
| 5 | Сеансовый | данные | установка и поддержание сеанса | RPC, (условно) TLS-сессии |
| 4 | Транспортный | сегмент / датаграмма | доставка между приложениями, порты, надёжность | TCP, UDP |
| 3 | Сетевой | пакет | адресация и маршрутизация между сетями | IP, ICMP, маршрутизатор |
| 2 | Канальный | кадр | доставка в пределах сегмента, MAC-адреса | Ethernet, ARP, VLAN, коммутатор |
| 1 | Физический | биты | сигнал в среде передачи | кабель, оптика, радио, хаб |

Мнемоника (англ., снизу вверх): *Please Do Not Throw Sausage Pizza Away*.

**Устройства:**
- **хаб** — L1, повторяет сигнал на все порты;
- **коммутатор (switch)** — L2, пересылает кадры по MAC-таблице; L3-коммутатор умеет и маршрутизировать;
- **маршрутизатор (router)** — L3, пересылает пакеты между сетями по таблице маршрутов;
- **файрвол** — L3/L4 (IP, порты, состояние соединения), NGFW и WAF — до L7;
- **балансировщик** — L4 (NLB, IPVS) или L7 (ALB, nginx).

**Инкапсуляция:** при отправке каждый уровень добавляет свой заголовок (HTTP → TCP-сегмент → IP-пакет → Ethernet-кадр), при приёме заголовки снимаются в обратном порядке.

**Практическое применение — диагностика снизу вверх:** есть ли линк (L1/L2: `ip link`, ARP), есть ли маршрут и связность (L3: `ping`, `ip route`), открыт ли порт (L4: `nc -zv`), отвечает ли приложение (L7: `curl -v`).

## Q: Какие HTTP-методы и коды ответов вы знаете? Какие заголовки важны?
level: middle
type: theory
freq: 3
tags: http

**Методы:**
| Метод | Назначение | Безопасный | Идемпотентный |
|---|---|---|---|
| GET | получить ресурс | да | да |
| HEAD | только заголовки | да | да |
| POST | создать или выполнить действие | нет | **нет** |
| PUT | заменить ресурс целиком | нет | да |
| PATCH | частично изменить | нет | не гарантируется |
| DELETE | удалить | нет | да |
| OPTIONS | возможности сервера, CORS preflight | да | да |

Идемпотентность важна для **ретраев**: повторять GET/PUT/DELETE безопасно, POST — нет (двойной платёж).

**Коды ответов:**
- **1xx** — информационные (101 Switching Protocols — переход на WebSocket);
- **2xx** — успех: 200 OK, 201 Created, 204 No Content;
- **3xx** — перенаправление: 301 (постоянное), 302/307 (временное), 304 Not Modified (кеш), 308;
- **4xx** — ошибка клиента: 400 Bad Request, **401** Unauthorized (не аутентифицирован), **403** Forbidden (нет прав), 404 Not Found, 405 Method Not Allowed, 408 Request Timeout, 409 Conflict, 413 Payload Too Large (`client_max_body_size` в nginx), 429 Too Many Requests (rate limit);
- **5xx** — ошибка сервера: 500 Internal Server Error, **502** Bad Gateway, **503** Service Unavailable, **504** Gateway Timeout.

**Важные заголовки:**
- запрос: `Host` (виртуальные хосты), `User-Agent`, `Authorization`, `Cookie`, `Accept`, `Content-Type`, `X-Forwarded-For` / `X-Forwarded-Proto` (исходный IP и схема за прокси), `X-Request-ID`;
- ответ: `Content-Type`, `Content-Length`, `Set-Cookie`, `Location` (для редиректов), `Cache-Control`, `ETag`, `Strict-Transport-Security` (HSTS), `Retry-After`;
- CORS: `Access-Control-Allow-Origin` и др. — браузер не даст JS-коду с одного домена читать ответы другого домена без разрешения сервера.

Проверить вручную: `curl -I https://example.com` (только заголовки), `curl -v`, вкладка Network в DevTools браузера.

## Q: Как настроить nginx как reverse proxy? Как nginx выбирает location?
level: middle
type: practice
freq: 3
tags: nginx, reverse-proxy

```nginx
upstream api_backend {
    server 10.0.1.10:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.11:8080;
    keepalive 32;                       # пул соединений к апстримам
}

server {
    listen 80;
    server_name shop.example.com;
    return 301 https://$host$request_uri;          # редирект на HTTPS
}

server {
    listen 443 ssl;
    http2 on;
    server_name shop.example.com;

    ssl_certificate     /etc/letsencrypt/live/shop.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/shop.example.com/privkey.pem;

    client_max_body_size 20m;

    location /static/ {
        root /var/www/shop;                         # файл: /var/www/shop/static/...
        expires 7d;
    }

    location /api/ {
        proxy_pass http://api_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 30s;
    }

    location / {
        try_files $uri $uri/ /index.html;           # SPA
    }
}
```

**Порядок выбора location:**
1. `location = /path` — **точное совпадение**, применяется сразу.
2. Среди **префиксных** location выбирается **самый длинный** совпадающий. Если у него модификатор `^~`, регулярные выражения не проверяются.
3. **Регулярные выражения** `~` (с учётом регистра) и `~*` (без) проверяются **по порядку в конфиге**, побеждает первое совпавшее.
4. Если ни одно регулярное выражение не подошло, используется самый длинный префикс из шага 2.

**Частые ловушки:**
- `proxy_pass http://backend/;` **со слешем на конце** заменяет совпавшую часть пути: `/api/users` → `/users`. Без слеша путь передаётся как есть.
- `root` vs `alias`: `root` дописывает весь URI к пути, `alias` заменяет часть URI из location.
- Не передан `Host`/`X-Forwarded-*` → приложение генерирует неверные ссылки или видит IP прокси вместо клиента.

**Эксплуатация:** проверка конфигурации `nginx -t`, применение без разрыва соединений `nginx -s reload` (или `systemctl reload nginx`), логи `/var/log/nginx/access.log` и `error.log`, переоткрытие логов после ротации — сигнал `USR1`.

## Q: Как работает аутентификация по SSH-ключу? Как настроить ~/.ssh/config и jump host?
level: middle
type: practice
freq: 3
tags: ssh

**Аутентификация по ключу:**
1. Генерируем пару: `ssh-keygen -t ed25519 -C "alice@laptop"` → `~/.ssh/id_ed25519` (закрытый, никому не передавать) и `id_ed25519.pub` (открытый).
2. Открытый ключ кладём на сервер в `~/.ssh/authorized_keys` (`ssh-copy-id user@host`).
3. При подключении сервер проверяет, что клиент владеет закрытым ключом: клиент **подписывает** данные сессии своим закрытым ключом, сервер проверяет подпись открытым. Сам закрытый ключ по сети не передаётся.
4. Перед этим клиент проверяет **ключ хоста** сервера по `~/.ssh/known_hosts` (защита от MITM). Предупреждение `REMOTE HOST IDENTIFICATION HAS CHANGED` означает, что сервер переустановили или кто-то подменяет соединение.

**Права**, без которых sshd отвергнет ключ: `~/.ssh` — 700, `authorized_keys` — 600, закрытый ключ — 600 (иначе клиент ругается `Permissions 0644 are too open`), домашний каталог не должен быть доступен на запись другим.

**~/.ssh/config:**
```
Host bastion
    HostName 203.0.113.10
    User alice
    IdentityFile ~/.ssh/id_ed25519

Host prod-*
    User deploy
    ProxyJump bastion          # подключение через jump host
    ServerAliveInterval 30

Host prod-db
    HostName 10.0.3.15
```
Теперь `ssh prod-db` автоматически пойдёт через bastion. Разово то же самое: `ssh -J alice@bastion deploy@10.0.3.15`.

**ssh-agent** хранит расшифрованные ключи в памяти (`ssh-add`). `ForwardAgent yes` пробрасывает агент на удалённый хост — удобно, но **небезопасно** на чужих серверах (root там может использовать ваш агент). Вместо этого лучше `ProxyJump`.

**Защита sshd** (`/etc/ssh/sshd_config`): `PasswordAuthentication no`, `PermitRootLogin no`, `AllowUsers`/`AllowGroups`, fail2ban, доступ только через bastion или VPN. Крупные компании переходят на **SSH-сертификаты** (короткоживущие, выдаются CA: Vault, Teleport) вместо раскладывания ключей.

## Q: Что такое SSH-туннели? Чем отличаются -L, -R и -D?
level: middle
type: practice
freq: 2
tags: ssh, туннели

SSH умеет пробрасывать TCP-соединения через зашифрованный канал.

**Локальный проброс `-L`** — открыть порт **у себя**, который ведёт к адресу, доступному **с сервера**:
```bash
ssh -L 5433:db.internal:5432 bastion
# теперь psql -h localhost -p 5433 подключается к db.internal:5432 через bastion
```
Типичный случай: доступ к БД, админке или Kubernetes API во внутренней сети.

**Удалённый проброс `-R`** — открыть порт **на сервере**, который ведёт к адресу, доступному **у вас**:
```bash
ssh -R 8080:localhost:3000 public-server
# public-server:8080 → ваш localhost:3000 (показать локальный сервис снаружи)
```
Чтобы порт слушал не только на loopback сервера, нужна опция `GatewayPorts` в sshd.

**Динамический проброс `-D`** — локальный **SOCKS-прокси**, весь трафик которого выходит с сервера:
```bash
ssh -D 1080 bastion      # в браузере указать SOCKS5 localhost:1080
```

Полезные флаги: `-N` (не запускать команду, только туннель), `-f` (в фон), `-o ExitOnForwardFailure=yes`. Для постоянных туннелей — `autossh` или systemd-сервис.

**С точки зрения безопасности:** туннели позволяют обойти сетевую сегментацию, поэтому на bastion их часто ограничивают (`AllowTcpForwarding no` или `PermitOpen`). Для регулярного доступа лучше VPN или identity-aware proxy. Аналог в Kubernetes — `kubectl port-forward`.

## Q: Как настроить ограничение частоты запросов (rate limiting) в nginx?
level: middle
type: practice
freq: 2
tags: nginx, rate-limiting

nginx использует алгоритм **leaky bucket** (протекающее ведро): запросы обрабатываются с заданной скоростью, всплески можно буферизовать.

```nginx
http {
    # зона: ключ — IP клиента, 10 МБ памяти (~160 тыс. IP), 10 запросов в секунду
    limit_req_zone $binary_remote_addr zone=api_per_ip:10m rate=10r/s;
    # ограничение одновременных соединений
    limit_conn_zone $binary_remote_addr zone=conn_per_ip:10m;
    limit_req_status 429;          # по умолчанию 503 — правильнее 429 Too Many Requests
    limit_conn_status 429;

    server {
        location /api/ {
            limit_req zone=api_per_ip burst=20 nodelay;
            limit_conn conn_per_ip 20;
            proxy_pass http://api_backend;
        }
        location /login {
            limit_req zone=api_per_ip burst=5;    # строже — защита от перебора паролей
            proxy_pass http://api_backend;
        }
    }
}
```

**Параметры:**
- `rate` — средняя разрешённая скорость (`r/s` или `r/m`);
- `burst` — сколько запросов сверх скорости можно поставить в очередь;
- **`nodelay`** — запросы из burst обрабатываются **сразу**, без искусственной задержки (иначе nginx «растягивает» их по времени, увеличивая латентность). Без `burst` любой всплеск даже из 2 одновременных запросов будет отклонён;
- `limit_req_dry_run on` — режим проверки: только логировать, ничего не блокировать (удобно для подбора лимитов).

**Подводные камни:**
- **Ключ по IP** за другим прокси или балансировщиком: все запросы выглядят как один IP → лимит сработает на всех сразу. Нужен корректный реальный IP (`real_ip_header`, `set_real_ip_from`).
- Много пользователей за одним корпоративным NAT — лимит по IP их ограничит. Лучше ключ по API-ключу или токену пользователя (`$http_authorization` / переменная из `map`).
- Лимиты в nginx считаются **на каждом экземпляре** отдельно: при 3 репликах фактический лимит в 3 раза выше. Глобальный лимит — в API gateway с общим хранилищем (Redis) или во внешней системе.
- Белые списки для внутренних сервисов и мониторинга через `geo` + `map` (пустой ключ не ограничивается).

В Kubernetes ingress-nginx настраивается аннотациями (`nginx.ingress.kubernetes.io/limit-rps`), в Gateway API и Envoy — через политики rate limit.

## Q: Как настроить кеширование ответов в nginx?
level: middle
type: practice
freq: 2
tags: nginx, кеширование

**Кеширование проксируемых ответов** снимает нагрузку с бэкенда:
```nginx
http {
    proxy_cache_path /var/cache/nginx/api levels=1:2 keys_zone=api_cache:50m
                     max_size=5g inactive=60m use_temp_path=off;

    server {
        location /api/catalog/ {
            proxy_cache api_cache;
            proxy_cache_key "$scheme$request_method$host$request_uri";
            proxy_cache_valid 200 301 10m;          # сколько хранить успешные ответы
            proxy_cache_valid 404 1m;
            proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
            proxy_cache_background_update on;       # обновлять в фоне, отдавая устаревшее
            proxy_cache_lock on;                    # один запрос к бэкенду на один ключ
            proxy_cache_bypass $http_authorization; # не брать из кеша для авторизованных
            proxy_no_cache $http_authorization;     # и не сохранять их ответы
            add_header X-Cache-Status $upstream_cache_status;   # HIT / MISS / STALE / BYPASS
            proxy_pass http://api_backend;
        }
    }
}
```

**Ключевые директивы:**
- `proxy_cache_path` — где хранить, имя и размер зоны для ключей (`keys_zone`), предел размера на диске, удаление неиспользуемого (`inactive`);
- `proxy_cache_valid` — время жизни по кодам ответа (если бэкенд не прислал `Cache-Control`/`Expires`; заголовки бэкенда имеют приоритет);
- **`proxy_cache_use_stale`** — отдавать устаревший кеш, если бэкенд недоступен или отвечает ошибкой: сайт продолжает работать во время аварии бэкенда;
- **`proxy_cache_lock`** — защита от **cache stampede**: при промахе только один запрос идёт к бэкенду, остальные ждут;
- `X-Cache-Status` в заголовке ответа — для отладки и метрик hit ratio.

**Опасности:**
- **Кеширование персональных данных**: ответ одного пользователя отдаётся другому. Не кешировать ответы с `Authorization`, `Set-Cookie`, приватные страницы; учитывать нужные заголовки и cookie в ключе.
- Инвалидация: в открытой версии nginx нет `proxy_cache_purge` (есть в NGINX Plus и сторонних модулях) — обычно используют короткие TTL или версионированные URL.

**Статика** обычно не кешируется в nginx, а отдаётся с правильными заголовками для браузера и CDN: `expires 30d; add_header Cache-Control "public, immutable";` для файлов с хешем в имени (`app.3f9a1c.js`), и `no-cache` для `index.html`.

**Микрокеширование** — кеш на 1–5 секунд для «горячих» публичных страниц: при тысячах RPS бэкенд получает один запрос в секунду на страницу.

## Q: Какие методы балансировки и проверки здоровья апстримов есть в nginx?
level: middle
type: theory
freq: 2
tags: nginx, балансировка

```nginx
upstream api {
    least_conn;                                   # метод балансировки
    server 10.0.1.10:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.1.11:8080 weight=1;
    server 10.0.1.12:8080 backup;                 # только если основные недоступны
    server 10.0.1.13:8080 down;                   # временно выведен
    keepalive 64;                                 # пул соединений к апстримам
}
```

**Методы балансировки:**
- **round-robin** (по умолчанию) — по очереди, с учётом `weight`;
- **`least_conn`** — на сервер с наименьшим числом активных соединений: лучше для запросов разной длительности;
- **`ip_hash`** — по IP клиента (липкие сессии), неравномерно, если много клиентов за NAT;
- **`hash $key consistent`** — по произвольному ключу с консистентным хешированием: при добавлении или удалении сервера перераспределяется только часть ключей (полезно для кешей);
- `random two least_conn` — «power of two choices»;
- `least_time` — только в NGINX Plus.

**Проверки здоровья:**
- **Пассивные** (open source nginx): если к серверу `max_fails` раз подряд не удалось обратиться в течение `fail_timeout`, он исключается на `fail_timeout`. Ошибкой считается то, что указано в **`proxy_next_upstream`** (по умолчанию `error timeout`), тогда же запрос **повторяется на следующем сервере**.
- **Активные** проверки (`health_check` с периодическими запросами к `/health`) — только в NGINX Plus. В open source — сторонний модуль, внешний механизм или балансировщик другого уровня (HAProxy, Envoy, облачный LB, Kubernetes readiness).

**Внимание к повторам:** `proxy_next_upstream` по умолчанию **не повторяет** неидемпотентные запросы (POST) после того, как запрос уже был отправлен апстриму (`non_idempotent` выключен) — и это правильно, чтобы не создать заказ дважды. Ограничивать повторы `proxy_next_upstream_tries` и `proxy_next_upstream_timeout`.

**Важно для апстримов в DNS:** nginx резолвит имена в `upstream` **один раз при старте**. Если IP сервисов меняются (облачные балансировщики, контейнеры), нужен `resolver` + переменная в `proxy_pass` или параметр `resolve` у `server` (доступен в open source nginx с версии 1.27.3).

## Q: Как настроить nginx под высокую нагрузку? Какие параметры важны?
level: senior
type: practice
freq: 2
tags: nginx, производительность

**Процессы и соединения:**
```nginx
worker_processes auto;            # по числу ядер
worker_rlimit_nofile 65535;       # лимит файловых дескрипторов на воркер
events {
    worker_connections 16384;     # соединений на воркер (клиентские + к апстримам)
    multi_accept on;
}
```
Максимум одновременных клиентов ≈ `worker_processes × worker_connections`, но при проксировании каждый клиент занимает **два** соединения (к клиенту и к апстриму). Лимит дескрипторов ОС должен быть выше (`LimitNOFILE` в systemd).

**Соединения с клиентами и апстримами:**
- `keepalive_timeout 30s; keepalive_requests 1000;` — переиспользование соединений клиентами;
- **keepalive к апстримам**: `keepalive 64;` в `upstream` + `proxy_http_version 1.1; proxy_set_header Connection "";` — без этого на каждый запрос открывается новое TCP-соединение к бэкенду → TIME_WAIT, исчерпание портов, лишняя латентность;
- таймауты: `proxy_connect_timeout`, `proxy_read_timeout`, `proxy_send_timeout`, `client_body_timeout`, `send_timeout`.

**Буферизация и передача:**
- `sendfile on; tcp_nopush on; tcp_nodelay on;` — эффективная отдача файлов;
- `proxy_buffering on` (по умолчанию) — nginx быстро забирает ответ у бэкенда и сам отдаёт его медленным клиентам, освобождая бэкенд. Для стриминга (SSE, LLM-ответы) — `proxy_buffering off`;
- `proxy_buffers`, `proxy_buffer_size` — для больших заголовков (ошибка `upstream sent too big header` → 502).

**Сжатие и TLS:**
- `gzip` (или brotli через модуль) для текстовых типов, `gzip_comp_level 4–6`;
- TLS: `ssl_protocols TLSv1.2 TLSv1.3`, `ssl_session_cache shared:SSL:50m; ssl_session_timeout 1d;` (повторное использование сессий снижает нагрузку на CPU), OCSP stapling, HTTP/2 (`http2 on`), HTTP/3 (`listen 443 quic`).

**Логи:** буферизация `access_log ... buffer=64k flush=5s;`, отключение логов для health-check'ов и статики, JSON-формат с временем апстрима (`$upstream_response_time`, `$request_time`).

**ОС (sysctl):** `net.core.somaxconn` и `backlog` в `listen`, `net.ipv4.ip_local_port_range`, `net.ipv4.tcp_tw_reuse=1`, буферы сокетов, conntrack-таблица.

**Измерять:** нагрузочное тестирование (wrk, k6), метрики `stub_status` / nginx-prometheus-exporter (активные соединения, запросы в секунду), латентность из логов. Узкое место чаще оказывается в бэкенде или в TLS-рукопожатиях, а не в самом nginx.

## Q: Что означают коды 499 и 413 в логах nginx?
level: middle
type: scenario
freq: 2
tags: nginx, коды-ответа

**499 Client Closed Request** — нестандартный код nginx: **клиент закрыл соединение**, не дождавшись ответа. Ответ клиенту не отправлен, в лог записан 499.
Причины:
- бэкенд отвечает **слишком медленно**, и у клиента сработал свой таймаут: браузер, мобильное приложение, **балансировщик перед nginx** (например, у облачного LB таймаут 60 с, а запрос выполняется дольше) или другой сервис с таймаутом HTTP-клиента в 5 секунд;
- пользователь закрыл вкладку или ушёл со страницы;
- health-check балансировщика с маленьким таймаутом.
Как разбираться: смотреть `$request_time` и `$upstream_response_time` для запросов с 499 — если они близки к какому-то круглому числу (5 с, 30 с, 60 с), это таймаут клиента или промежуточного прокси. Лечить медленный бэкенд, а не повышать таймауты. Опция `proxy_ignore_client_abort on` позволяет довести запрос до бэкенда, даже если клиент ушёл (полезно для операций, которые нельзя прерывать).

**413 Request Entity Too Large** — тело запроса больше **`client_max_body_size`** (по умолчанию **1 МБ**). Типично при загрузке файлов и больших JSON. Решение: увеличить лимит в нужном `location` (а не глобально), учитывая все прокси по пути — Ingress-контроллер (`nginx.ingress.kubernetes.io/proxy-body-size`), облачный балансировщик, само приложение.

**Другие частые коды в логах nginx:**
- **502** — апстрим недоступен или ответил некорректно (смотреть `error.log`);
- **504** — апстрим не ответил за `proxy_read_timeout`;
- **400** с `client sent invalid header` или слишком большие заголовки (`large_client_header_buffers`) — часто из-за огромных cookie;
- **444** — специальный код nginx: закрыть соединение без ответа (используется для отсечения нежелательных запросов: `return 444;`).

## Q: Как работает ARP? Что такое gratuitous ARP и где он используется?
level: middle
type: theory
freq: 2
tags: arp, l2

**ARP** (Address Resolution Protocol) сопоставляет **IP-адрес → MAC-адрес** в пределах одного L2-сегмента. Нужен потому, что Ethernet-кадр адресуется MAC-адресом, а приложения знают только IP.

**Как работает:**
1. Хосту нужно отправить пакет на 10.0.0.20 в своей подсети (или на шлюз по умолчанию, если адрес в другой сети — тогда ищется **MAC шлюза**).
2. Проверяется **ARP-кеш** (`ip neigh`). Если записи нет — **широковещательный** ARP-запрос: «у кого 10.0.0.20? Ответьте 10.0.0.10».
3. Владелец адреса отвечает **unicast**-ом своим MAC-адресом.
4. Ответ кешируется на время (состояния `REACHABLE`, `STALE`, `FAILED`).

**Gratuitous ARP** — хост сам, без запроса, объявляет: «IP 10.0.0.100 теперь у MAC такого-то». Применение:
- **переезд виртуального IP** при отказоустойчивости (**keepalived/VRRP**, Pacemaker, Patroni с vip-manager, **MetalLB в L2-режиме**): новый владелец VIP рассылает gratuitous ARP, и коммутаторы и соседи обновляют свои таблицы;
- обнаружение конфликтов IP-адресов при поднятии интерфейса.

**Проблемы и диагностика:**
- **конфликт IP** (два хоста с одним адресом) — соединения то работают, то нет; `arping -D -I eth0 10.0.0.20` для проверки;
- **устаревший ARP-кеш** после переезда IP, если gratuitous ARP заблокирован или проигнорирован (некоторые облака и коммутаторы) → VIP «не переезжает». Поэтому в облаках вместо VIP на основе ARP используют API облака (перенос secondary IP, маршрута) или балансировщик;
- **ARP spoofing** — атака «человек посередине» в локальной сети (подделка ответов); защита — Dynamic ARP Inspection на коммутаторах, сегментация.
- переполнение таблицы соседей на больших L2-сетях (Kubernetes-ноды с множеством подов): `net.ipv4.neigh.default.gc_thresh1/2/3`.

Команды: `ip neigh show`, `ip neigh flush dev eth0`, `arping`, `tcpdump -n -i eth0 arp`.

В IPv6 вместо ARP используется **NDP** (Neighbor Discovery Protocol) на основе ICMPv6.

## Q: Что нужно знать DevOps-инженеру об IPv6?
level: middle
type: theory
freq: 2
tags: ipv6

**Зачем:** адреса IPv4 исчерпаны — облака берут плату за публичные IPv4, мобильные операторы и крупные сервисы работают по IPv6, большие Kubernetes-кластеры упираются в размер приватных IPv4-диапазонов.

**Основы:**
- адрес 128 бит, запись восемью группами по 16 бит в шестнадцатеричном виде: `2001:0db8:0000:0000:0000:0000:0000:0001` = `2001:db8::1` (`::` заменяет одну последовательность нулей);
- типичный размер подсети — **/64**; провайдер или облако выдаёт /48 или /56 на сеть;
- **нет NAT** в классическом смысле: у каждого устройства глобально маршрутизируемый адрес → **файрвол обязателен**, «приватность через NAT» больше не работает;
- типы адресов: глобальные (`2000::/3`), **link-local** (`fe80::/10`, есть на каждом интерфейсе, используются для служебного обмена), ULA (`fc00::/7`, аналог приватных), loopback `::1`, «все интерфейсы» `::`;
- **NDP** вместо ARP, автоконфигурация адресов (**SLAAC**) по анонсам маршрутизатора или DHCPv6;
- **ICMPv6 нельзя блокировать целиком**: через него работают NDP и Path MTU Discovery (фрагментацию выполняет только отправитель).

**Практика:**
- **dual-stack** — интерфейсы с IPv4 и IPv6 одновременно; переходный период длится годами;
- DNS: записи **AAAA**; клиенты при наличии обоих адресов используют **Happy Eyeballs** (пробуют IPv6 и IPv4 параллельно);
- адрес с портом в URL записывается в квадратных скобках: `http://[2001:db8::1]:8080/`;
- приложения должны слушать `::` (или и `0.0.0.0`, и `::`), иначе по IPv6 сервис недоступен;
- частые проблемы: правила файрвола и security groups только для IPv4 (сервис открыт по IPv6!), логирование и парсинг IP-адресов в коде и регулярках, лимиты и белые списки по IP, мониторинг только IPv4;
- **Kubernetes** поддерживает dual-stack (поды и сервисы с адресами обоих семейств) и IPv6-only кластеры.

Команды: `ip -6 addr`, `ip -6 route`, `ping -6`, `curl -6`, `ss -6 -tln`, `dig AAAA example.com`.

## Q: Что такое BGP и зачем он DevOps-инженеру?
level: senior
type: theory
freq: 1
tags: bgp, маршрутизация

**BGP** (Border Gateway Protocol) — протокол обмена маршрутами между **автономными системами** (AS) — сетями провайдеров, облаков и крупных компаний. По сути, это протокол, на котором держится маршрутизация интернета: каждая AS анонсирует соседям, какие префиксы (IP-диапазоны) через неё доступны, и выбирает лучшие пути по атрибутам (длина пути AS_PATH, local preference, MED).

- **eBGP** — между разными AS; **iBGP** — внутри одной AS.
- Работает поверх TCP (порт 179), сессии между соседями (peers) настраиваются явно.

**Где DevOps-инженер встречает BGP:**
- **Kubernetes-сети**: **Calico** анонсирует маршруты к подсетям подов на ноды и на сетевое оборудование ЦОД (без оверлея); **MetalLB** и **Cilium** в BGP-режиме анонсируют IP-адреса сервисов `LoadBalancer` на маршрутизаторы — так bare-metal кластер получает «облачные» балансировщики;
- **гибридное облако**: AWS Direct Connect, Site-to-Site VPN, Azure ExpressRoute, GCP Cloud Router используют BGP для динамического обмена маршрутами между ЦОД и облаком — при падении одного туннеля трафик автоматически уходит в другой;
- **anycast**: один IP-адрес анонсируется из нескольких точек мира (CDN, публичные DNS-резолверы, защита от DDoS) — пользователь попадает в ближайшую;
- **ECMP** — несколько равноценных маршрутов для балансировки трафика между серверами на уровне сети;
- **EVPN** (BGP для VXLAN-фабрик) в современных ЦОД.

**Инциденты из-за BGP:** утечки и ошибочные анонсы маршрутов (route leak, hijack) периодически делают недоступными крупные сервисы; известный пример — сбой Facebook в 2021 году, когда ошибочная настройка привела к отзыву их BGP-анонсов, и сервисы вместе с DNS исчезли из интернета. Защита — RPKI (криптографическая проверка, кто вправе анонсировать префикс), фильтры анонсов.

На собеседовании обычно достаточно понимать назначение и эти сценарии; глубокая настройка — задача сетевых инженеров.

## Q: Как работает CDN? Что кешировать на CDN и как инвалидировать кеш?
level: middle
type: theory
freq: 2
tags: cdn, кеширование

**CDN** (Content Delivery Network) — распределённая сеть серверов (**edge**, точек присутствия — PoP) по всему миру. Пользователь получает контент с ближайшего узла, а не с вашего сервера (**origin**).

**Как пользователь попадает на ближайший узел:** через **DNS** (CNAME вашего домена на CDN, CDN отвечает IP ближайшего узла по геолокации резолвера) или **anycast** (один IP анонсируется из всех точек).

**Что даёт:**
- меньше задержка (контент рядом с пользователем, TLS-рукопожатие завершается на ближайшем узле);
- разгрузка origin и экономия исходящего трафика;
- защита: поглощение DDoS, WAF, скрытие IP origin, rate limiting, защита от ботов;
- оптимизация: сжатие, HTTP/2 и HTTP/3, конвертация изображений.

**Что кешировать:**
- **статика**: JS, CSS, изображения, шрифты, видео — с долгим сроком жизни и **хешем в имени файла** (`app.3f9a1c.js`): при изменении меняется имя, и инвалидация не нужна;
- публичные страницы и ответы API — с коротким TTL (секунды–минуты), если это допустимо;
- **не кешировать** персональные ответы: всё, что зависит от cookie сессии или `Authorization`, — иначе пользователь увидит чужие данные (классический инцидент при неверной настройке CDN).

**Управление кешированием:** заголовки ответа origin — `Cache-Control: public, max-age=31536000, immutable`, `s-maxage` (только для общих кешей, то есть CDN), `no-store`, `private`; `Vary` (кеш различается по заголовку, например `Accept-Encoding`); правила на стороне CDN (по путям, игнорирование query string или cookie в ключе кеша).

**Инвалидация:**
- **purge** по URL, префиксу или тегам (surrogate keys / cache tags) через API CDN — вызывается из CI после деплоя;
- **версионирование URL** — предпочтительный способ для статики;
- `stale-while-revalidate` и `stale-if-error` — отдавать устаревший контент, пока обновляется кеш или если origin недоступен.

**Метрики:** **cache hit ratio**, трафик на origin, ошибки 5xx на edge и на origin, латентность.

**Провайдеры:** Cloudflare, Akamai, Fastly, Amazon CloudFront, Google Cloud CDN, Azure Front Door; в России — CDN Яндекса (Cloud CDN), NGENIX, CDNvideo, CDN операторов связи.

## Q: Как проксировать WebSocket и долгоживущие соединения через nginx и балансировщики?
level: middle
type: practice
freq: 2
tags: websocket, nginx, балансировка

**WebSocket** начинается как обычный HTTP-запрос с заголовками `Upgrade: websocket` и `Connection: Upgrade`. Сервер отвечает `101 Switching Protocols`, и дальше по тому же TCP-соединению идёт двусторонний обмен сообщениями.

**Проблема:** `Upgrade` и `Connection` — **hop-by-hop** заголовки, прокси по умолчанию их **не передаёт**. Без настройки соединение не установится (ошибка 400 или ответ обычным HTTP).

**nginx:**
```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
server {
    location /ws/ {
        proxy_pass http://ws_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;     # иначе соединение без трафика закроется через 60 с
        proxy_send_timeout 3600s;
    }
}
```

**Таймауты простоя на каждом звене:** nginx (`proxy_read_timeout`), облачный балансировщик (у AWS ALB idle timeout по умолчанию 60 с), Ingress-контроллер (аннотации `proxy-read-timeout`), NAT и файрволы. Решение — **heartbeat (ping/pong)** от приложения чаще, чем самый короткий таймаут по пути, плюс увеличенные таймауты.

**Масштабирование и деплой:**
- **балансировка** долгоживущих соединений неравномерна: новые поды почти не получают нагрузку, пока старые держат соединения. Помогают алгоритм least connections и периодическое переподключение клиентов;
- **деплой**: при остановке пода все его соединения рвутся → клиент обязан уметь **переподключаться с экспоненциальной задержкой и jitter** (иначе тысячи клиентов одновременно переподключатся на оставшиеся поды); сервер при SIGTERM закрывает соединения постепенно, `terminationGracePeriodSeconds` с запасом;
- **состояние между экземплярами**: если сообщение для пользователя может прийти на любой под, нужна общая шина (Redis Pub/Sub, NATS, Kafka); иногда используют sticky sessions;
- лимиты дескрипторов и памяти: каждое соединение — открытый сокет.

**Альтернативы WebSocket:** **Server-Sent Events** (SSE — однонаправленный поток от сервера по обычному HTTP; на nginx нужно `proxy_buffering off`), long polling, gRPC streaming (нужен HTTP/2 до бэкенда).
