# Ключевые концепции

С 2024–2026 годов вопросы про ИИ стали обычной частью собеседований DevOps. Для этого не нужно быть ML-инженером. Обычно проверяют три вещи.

### 1. ИИ как инструмент инженера
Ассистенты в IDE и терминале (GitHub Copilot, Claude Code, Cursor, Codex CLI, JetBrains AI), чат-модели. Применение: генерация и ревью IaC и пайплайнов, объяснение логов и ошибок, написание скриптов, документации и постмортемов. Ждут **осознанного** использования: проверка результата, никаких секретов в промптах, понимание ограничений.

### 2. Инфраструктура для ИИ (MLOps / LLMOps)
DevOps-инженера всё чаще просят **развернуть и эксплуатировать** модели:
```
пользователи / приложения
        │
  LLM Gateway ── авторизация, лимиты, бюджеты, маскирование PII, логи, фолбэки
   │        │
внешние API          self-hosted модели в Kubernetes на GPU
(Claude, GPT,        (vLLM / TGI / Triton / SGLang; модели Llama, Qwen,
 Gemini, YandexGPT,   Mistral, DeepSeek, Gemma)
 GigaChat)
        │
  RAG: векторная БД (pgvector, Qdrant, Milvus) + конвейер индексации документов
        │
  Наблюдаемость: токены, латентность, стоимость, трейсы промптов, оценка качества (evals)
```

### 3. ИИ в эксплуатации (AIOps)
Обнаружение аномалий в метриках, корреляция и дедупликация алертов, суммаризация инцидентов, агенты для траблшутинга с доступом к инструментам через **MCP** (Model Context Protocol).

### Словарь
| Термин | Смысл |
|---|---|
| **Токен** | единица текста для модели (часть слова). Цена и лимиты считаются в токенах |
| **Контекстное окно** | сколько токенов (промпт + ответ) модель обрабатывает за раз |
| **Инференс** | выполнение готовой модели (ответ на запрос), в отличие от обучения |
| **Эмбеддинг** | вектор чисел, отражающий смысл текста; основа семантического поиска |
| **RAG** | Retrieval-Augmented Generation: найти релевантные документы и подставить их в промпт |
| **Fine-tuning** | дообучение модели на своих данных (LoRA и др.) |
| **Квантизация** | хранение весов в меньшей точности (INT8, INT4), чтобы модель занимала меньше памяти |
| **Агент** | LLM, которая в цикле планирует действия и вызывает инструменты (API, команды) |
| **MCP** | открытый протокол подключения инструментов и источников данных к LLM-приложениям |
| **TTFT** | time to first token — задержка до первого токена ответа |

> Российский контекст: персональные данные по 152-ФЗ и коммерческая тайна часто не могут уходить во внешние API, поэтому популярны self-hosted open-weight модели и отечественные сервисы (YandexGPT в Yandex Cloud, GigaChat от Сбера).

## Q: Как вы используете ИИ-ассистентов в работе DevOps? Какие риски и как их контролировать?
level: middle
type: practice
freq: 3
tags: ассистенты, copilot, практика

Этот вопрос всё чаще задают даже на собеседованиях, не связанных с ИИ. Ждут конкретики и зрелого отношения к инструменту: без «ИИ всё делает за меня» и без «не пользуюсь принципиально».

**Где ИИ реально помогает:**
- **Черновики кода**: Terraform-модули, Helm-чарты, Dockerfile, `.gitlab-ci.yml`, Ansible-роли, bash/Python-скрипты, регулярные выражения, PromQL и SQL-запросы.
- **Разбор незнакомого**: объяснить стектрейс, лог, чужой код, legacy-конфигурацию, опции утилиты.
- **Траблшутинг**: гипотезы по симптомам, план диагностики. Агентные инструменты в терминале (Claude Code, Codex CLI, Gemini CLI) могут сами выполнить команды диагностики и предложить исправление.
- **Ревью**: проверка MR на очевидные ошибки, безопасность, соответствие стандартам (в том числе как бот в CI).
- **Документация**: README, runbook'и, черновики постмортемов, описание MR.
- **Миграции**: перевод с одного формата на другой (Jenkinsfile → GitLab CI, docker-compose → манифесты Kubernetes).

**Риски:**
- **Галлюцинации**: несуществующие параметры, устаревшие версии API, выдуманные флаги CLI. Выглядят правдоподобно.
- **Небезопасные значения по умолчанию**: `0.0.0.0/0` в security group, `privileged: true`, отключённая проверка TLS, права `*` в IAM.
- **Утечка данных**: секреты, клиентские данные и внутренняя архитектура в промптах, отправленных во внешний сервис.
- **Лицензии и авторство** сгенерированного кода.
- **Деградация навыков**: инженер не понимает, что именно применил в прод.
- **Агенты с доступом к инфраструктуре** могут выполнить разрушительную команду.

**Как контролировать:**
- Ответственность за результат на инженере: сгенерированное проходит **тот же процесс**, что и написанное вручную — ревью, линтеры, `terraform plan`, тесты, staging.
- Корпоративные инструменты с договором о неиспользовании данных для обучения (enterprise-версии или доступ через собственный LLM-шлюз), запрет отправки секретов, сканеры секретов.
- Агентам — минимальные права: read-only доступ, работа в dev-окружении, подтверждение человеком перед изменениями, запрет на прод.
- Проверка по официальной документации для критичных параметров.

**Пример хорошего ответа:** «Использую Claude Code / Copilot для черновиков Terraform и скриптов, всегда смотрю plan и прогоняю tflint/checkov. Для разбора инцидентов прошу ассистента составить гипотезы по логам, но проверяю их сам. Секреты и клиентские данные во внешние модели не отправляю — у нас есть внутренний шлюз».

## Q: Объясните основные понятия LLM: токены, контекстное окно, температура, эмбеддинги, RAG, fine-tuning.
level: middle
type: theory
freq: 2
tags: llm, основы

- **Токен** — фрагмент текста, с которым работает модель (часть слова, слово, знак). В английском 1 токен ≈ 4 символа, в русском токенов обычно больше на тот же текст. **Оплата и лимиты** API считаются в токенах, отдельно входные и выходные (выходные дороже).
- **Контекстное окно** — максимум токенов в одном запросе (системный промпт + история диалога + документы + ответ). Сейчас это от десятков тысяч до миллиона токенов. Большой контекст стоит денег и увеличивает задержку.
- **Температура** — степень случайности генерации: 0 — максимально детерминированно (для кода, извлечения данных), выше — разнообразнее (для творческих задач). Даже при 0 ответы не всегда полностью воспроизводимы.
- **Системный промпт** — инструкции, задающие роль и правила поведения модели.
- **Эмбеддинг** — вектор (сотни–тысячи чисел), представляющий смысл текста. Близкие по смыслу тексты дают близкие векторы (косинусное расстояние). Используется для семантического поиска, кластеризации, рекомендаций. Генерируется отдельными embedding-моделями.
- **RAG** (Retrieval-Augmented Generation) — перед ответом найти в базе знаний релевантные фрагменты (по эмбеддингам и/или ключевым словам) и подставить их в промпт. Даёт актуальные и внутренние знания без дообучения, позволяет ссылаться на источники и разграничивать доступ.
- **Fine-tuning** — дообучение модели на своих примерах (обычно эффективными методами вроде **LoRA**). Меняет **стиль, формат, поведение**, но плохо подходит для добавления часто меняющихся фактов — для них RAG.
- **Инференс vs обучение**: DevOps чаще эксплуатирует **инференс** (обслуживание запросов). Обучение больших моделей — отдельная дисциплина с огромными GPU-кластерами.
- **Open-weight vs проприетарные модели**: веса открытых моделей (Llama, Qwen, Mistral, DeepSeek, Gemma) можно скачать и запустить у себя; проприетарные (Claude, GPT, Gemini, YandexGPT, GigaChat) доступны через API.
- **Tool use / function calling** — модель возвращает структурированный вызов функции, приложение его выполняет и отдаёт результат обратно. Основа агентов.

Порядок выбора подхода для задачи: **промпт-инжиниринг → RAG → fine-tuning**. Каждый следующий шаг дороже и сложнее в поддержке.

## Q: Как внедрить LLM в компании: внешнее API или своя модель? Какие критерии выбора?
level: senior
type: design
freq: 3
tags: внедрение, архитектура, enterprise

**Варианты:**

1. **Внешнее API провайдера** (Anthropic, OpenAI, Google) напрямую или через облако (Amazon Bedrock, Google Vertex AI, Azure OpenAI): данные остаются в выбранном регионе облака, работают корпоративные договоры, IAM и VPC endpoints. В России — YandexGPT (Yandex Cloud), GigaChat (Сбер).
   - Плюсы: лучшее качество моделей, ноль инфраструктуры, быстрый старт, оплата за использование.
   - Минусы: данные уходят за периметр, зависимость от провайдера, лимиты запросов, стоимость при больших объёмах, возможная недоступность из-за санкций или регуляторики.
2. **Self-hosted open-weight модели** на своих GPU (on-prem или в облаке).
   - Плюсы: данные не покидают контур, полный контроль, предсказуемая стоимость при высокой постоянной нагрузке, возможность дообучения.
   - Минусы: дорогие и дефицитные GPU, качество открытых моделей обычно ниже лучших проприетарных, нужна экспертиза (сервинг, обновления, безопасность), простаивающие GPU стоят денег.
3. **Гибрид** (самый частый в энтерпрайзе): маршрутизация через единый шлюз — чувствительные данные и массовые простые задачи идут на свои модели, сложные задачи без чувствительных данных — во внешнее API.

**Критерии выбора:**
- **Данные**: классификация (персональные данные по 152-ФЗ / GDPR, коммерческая тайна, исходный код), требования ИБ и юристов.
- **Качество** на ваших задачах — проверять своими **оценками (evals)** на реальных примерах, а не по рейтингам.
- **Стоимость**: прогноз объёма токенов, сравнение «API за токены» против «GPU за часы» с учётом загрузки GPU и стоимости команды.
- **Латентность и доступность**: SLA провайдера, лимиты, резервный провайдер.
- **Экспертиза команды** и время до результата.

**Обязательные элементы платформы независимо от варианта:**
- **LLM-шлюз**: единая точка доступа, учёт по командам, лимиты, маскирование PII, логирование, фолбэки;
- управление доступом через корпоративный SSO;
- политика использования ИИ для сотрудников;
- наблюдаемость и оценка качества;
- каталог разрешённых моделей и сценариев;
- пилот на 1–2 сценариях с измеримым эффектом, затем масштабирование.

## Q: Что такое LLM-шлюз (AI gateway) и зачем он нужен?
level: senior
type: practice
freq: 2
tags: gateway, litellm, enterprise

**LLM-шлюз** — прокси между приложениями и моделями: единый API (обычно OpenAI-совместимый) для всех провайдеров и собственных моделей. Это аналог API gateway, только для ИИ.

**Функции:**
- **Единая точка доступа**: приложения не хранят ключи провайдеров, получают свои ключи шлюза; смена модели или провайдера без изменения кода.
- **Аутентификация и авторизация**: какие команды и сервисы к каким моделям имеют доступ, интеграция с SSO.
- **Лимиты и бюджеты**: rate limit, квоты токенов и денег на команду или проект, алерты на превышение.
- **Надёжность**: ретраи, **фолбэк** на другую модель или провайдера при ошибках и лимитах, балансировка между ключами и регионами, таймауты.
- **Маршрутизация**: дешёвая модель для простых запросов, мощная — для сложных; чувствительные данные — только на self-hosted модели.
- **Безопасность (guardrails)**: маскирование персональных данных и секретов **до** отправки во внешнее API, фильтрация вредоносных промптов и ответов.
- **Кеширование**: точное и семантическое, плюс использование prompt caching провайдеров.
- **Наблюдаемость и аудит**: логи запросов (с учётом требований к хранению PII), токены, стоимость, латентность по командам и моделям, экспорт в Prometheus и OpenTelemetry.

**Инструменты:** LiteLLM (open source, популярен для self-hosted), Portkey, Kong AI Gateway, Envoy AI Gateway, Apache APISIX / Higress AI-плагины, облачные решения (Amazon Bedrock, Azure API Management с AI-политиками, Cloudflare AI Gateway).

**Эксплуатация как обычного критичного сервиса:** HA (несколько реплик за балансировщиком), хранилище состояния для лимитов (Redis, PostgreSQL), секреты провайдеров в Vault, мониторинг и алерты, конфигурация в Git.

## Q: Как развернуть LLM в Kubernetes на GPU?
level: senior
type: practice
freq: 3
tags: gpu, kubernetes, vllm

**1. GPU-ноды:**
- Отдельный пул нод с GPU (taint `nvidia.com/gpu=present:NoSchedule`, чтобы туда не попадали обычные поды).
- **NVIDIA GPU Operator** — автоматически ставит драйвер, container toolkit, **device plugin**, мониторинг (DCGM exporter), node feature discovery. В managed-кластерах часть этого делает провайдер.
- Device plugin объявляет ресурс `nvidia.com/gpu`, который запрашивается как обычный ресурс (только целыми числами, в limits).
- **Разделение GPU**: **MIG** (аппаратное деление A100/H100 на изолированные части), **time-slicing** (поочерёдный доступ без изоляции памяти), MPS. Для небольших моделей и dev-окружений это сильно экономит деньги.

**2. Сервер инференса** — не самописный Flask, а специализированный движок:
- **vLLM** — стандарт де-факто: PagedAttention, continuous batching, OpenAI-совместимый API, tensor parallelism;
- **SGLang**, **TGI** (Hugging Face), **NVIDIA Triton / TensorRT-LLM** (максимальная производительность на NVIDIA);
- **Ollama / llama.cpp** — для разработки, CPU и небольших нагрузок.

```yaml
containers:
- name: vllm
  image: vllm/vllm-openai:<версия>
  args: ["--model", "Qwen/Qwen2.5-7B-Instruct", "--max-model-len", "16384",
         "--gpu-memory-utilization", "0.90"]
  ports: [{ containerPort: 8000 }]
  resources:
    limits: { nvidia.com/gpu: 1, memory: 32Gi }
  readinessProbe: { httpGet: { path: /health, port: 8000 }, initialDelaySeconds: 60 }
  volumeMounts:
  - { name: models, mountPath: /root/.cache/huggingface }
  - { name: shm, mountPath: /dev/shm }        # нужно для tensor parallelism
tolerations: [{ key: nvidia.com/gpu, operator: Exists, effect: NoSchedule }]
volumes:
- { name: models, persistentVolumeClaim: { claimName: model-cache } }
- { name: shm, emptyDir: { medium: Memory, sizeLimit: 8Gi } }
```

**3. Платформенный слой** (по мере роста): **KServe** (InferenceService, масштабирование, канареечные выкатки моделей), **KubeAI**, **llm-d**, **Ray Serve**, NVIDIA NIM.

**Особенности эксплуатации:**
- **Веса моделей** — десятки и сотни гигабайт: не класть в образ; хранить в S3 или на PVC, кешировать на нодах, использовать внутреннее зеркало Hugging Face. **Холодный старт** пода занимает минуты — учитывать в пробах (startupProbe) и автомасштабировании.
- **Автомасштабирование** не по CPU, а по длине очереди и числу запросов в обработке (метрики vLLM `num_requests_waiting`) через KEDA или HPA с custom metrics. Масштабирование GPU-нод — Cluster Autoscaler / Karpenter, но GPU могут быть недоступны в нужной зоне.
- **Мониторинг**: DCGM exporter (утилизация GPU, память, температура, ECC-ошибки), метрики движка (TTFT, токены/с, очередь, KV-cache usage).
- **Стоимость**: GPU — самая дорогая часть кластера; простаивающие GPU нужно находить и устранять (scale to zero для редко используемых моделей, разделение GPU, spot для batch-задач).

## Q: Как оценить, сколько GPU-памяти нужно для модели? Что такое квантизация и KV-кеш?
level: senior
type: theory
freq: 2
tags: gpu, capacity, квантизация

**Память под веса** ≈ количество параметров × байт на параметр:
| Точность | Байт на параметр | Модель 7–8B | Модель 70B |
|---|---|---|---|
| FP16 / BF16 | 2 | ~16 ГБ | ~140 ГБ |
| FP8 / INT8 | 1 | ~8 ГБ | ~70 ГБ |
| INT4 (AWQ, GPTQ, GGUF Q4) | ~0.5 | ~4–5 ГБ | ~35–40 ГБ |

**Плюс KV-кеш** — память для хранения промежуточных результатов (ключей и значений attention) по всем токенам **всех одновременно обслуживаемых запросов**. Растёт с длиной контекста и количеством параллельных запросов и может занимать **больше, чем сами веса**. Именно поэтому важны:
- **PagedAttention** (vLLM) — выделение KV-кеша страницами без фрагментации;
- ограничение максимальной длины контекста (`--max-model-len`);
- квантизация KV-кеша.

Плюс накладные расходы движка и CUDA (несколько ГБ). Практическое правило: для модели 7–8B в FP16 нужен GPU на 24 ГБ и больше, а для комфортной работы с параллельными запросами — 40–80 ГБ.

**Квантизация** — хранение весов в пониженной точности. Модель в 2–4 раза меньше и быстрее, ценой небольшой потери качества (у 4-битных квантизаций обычно приемлемой, но проверять на своих задачах). Форматы: AWQ, GPTQ, FP8 — для GPU-движков; **GGUF** — для llama.cpp и Ollama (в том числе на CPU).

**Модель не помещается в один GPU** — **tensor parallelism**: веса делятся между несколькими GPU одной ноды (`--tensor-parallel-size 4`), нужна быстрая связь между GPU (NVLink). Для совсем больших моделей — pipeline parallelism между нодами.

**Ключевые метрики производительности:**
- **TTFT** (time to first token) — важно для интерактивных чатов;
- **TPOT / ITL** (время на каждый следующий токен) — скорость «печати» ответа;
- **throughput** — токенов в секунду суммарно по всем запросам, определяет стоимость;
- компромисс: больше параллельных запросов (batch) → выше throughput, но хуже латентность одного запроса.

Мощность подбирают **нагрузочным тестированием** на реалистичных промптах: инструменты бенчмарка vLLM, GuideLLM, k6 с OpenAI-совместимым API.

## Q: Спроектируйте RAG-систему для поиска по внутренней документации компании.
level: senior
type: design
freq: 2
tags: rag, векторные-бд, архитектура

**Требования для уточнения:** источники (Confluence, Git, Jira, файловые хранилища), объём документов, частота обновления, **права доступа** к документам, языки, требования к данным (можно ли во внешнее API), ожидаемая нагрузка.

**1. Конвейер индексации (ingestion):**
- коннекторы к источникам, инкрементальная загрузка изменений (по событиям или расписанию);
- извлечение текста (PDF, docx, HTML, таблицы), очистка;
- **разбиение на фрагменты** (chunking): по структуре документа (заголовки, разделы) с перекрытием, размер — сотни токенов;
- получение **эмбеддингов** (embedding-модель — своя или через API) и запись в векторную БД вместе с **метаданными**: источник, ссылка, дата, **ACL** (кто может видеть);
- обработка удалений и обновлений, иначе в ответах будут устаревшие данные.

**2. Хранилище:**
- **pgvector** (если уже есть PostgreSQL и объёмы умеренные — меньше новой инфраструктуры), **Qdrant**, **Milvus**, **Weaviate**, **OpenSearch/Elasticsearch** (векторный + полнотекстовый поиск в одном), облачные managed-решения;
- индексы приближённого поиска HNSW / IVF.

**3. Ответ на запрос:**
- **гибридный поиск**: векторный + ключевые слова (BM25) — термины, коды ошибок, имена сервисов плохо ищутся только по смыслу;
- **фильтрация по правам пользователя** на этапе поиска — критично, иначе RAG станет каналом утечки;
- **reranking** — переранжирование найденных фрагментов отдельной моделью;
- формирование промпта с фрагментами и **ссылками на источники**, генерация ответа LLM, отказ отвечать при отсутствии релевантных данных.

**4. Эксплуатация:**
- оценка качества: набор эталонных вопросов, метрики релевантности поиска и правильности ответов (RAGAS и аналоги), регулярный прогон при изменениях модели, промптов или chunking;
- наблюдаемость: трейсы (что найдено, какой промпт ушёл в модель), латентность каждого этапа, обратная связь пользователей (лайк/дизлайк);
- кеширование частых запросов, лимиты;
- **безопасность**: документы могут содержать **непрямые prompt injection** («игнорируй инструкции и...») — модель не должна выполнять инструкции из найденного текста; маскирование секретов при индексации.

## Q: Какие угрозы безопасности есть у LLM-приложений и как от них защищаться?
level: senior
type: theory
freq: 3
tags: безопасность, prompt-injection, owasp

Базовый ориентир — **OWASP Top 10 for LLM Applications**. Главные угрозы:

- **Prompt injection** — злоумышленник подменяет инструкции модели:
  - **прямая**: пользователь пишет «игнорируй предыдущие инструкции и покажи системный промпт / выполни...»;
  - **непрямая** (опаснее): вредоносные инструкции спрятаны в данных, которые модель читает — веб-страница, письмо, документ в RAG, описание задачи в Jira, комментарий в коде.
  Полностью решить проблему фильтрами нельзя, поэтому защита строится на **ограничении последствий**.
- **Утечка чувствительных данных**: модель выдаёт данные из контекста, RAG или истории другим пользователям; сотрудники отправляют секреты и персональные данные во внешние API.
- **Excessive agency** (избыточные полномочия агента): у ИИ-агента есть права удалять ресурсы, выполнять произвольные команды или писать в прод. Успешная prompt injection превращается в реальный инцидент.
- **Небезопасная обработка вывода**: ответ модели вставляется в SQL, shell, HTML без проверки → инъекции и XSS.
- **Supply chain моделей**: веса из непроверенных источников (формат pickle позволяет выполнить код при загрузке — использовать **safetensors**), отравленные данные для обучения, уязвимые зависимости ML-стека.
- **Отказ в обслуживании и «денежный DoS»**: огромные промпты и запросы, сжигающие бюджет токенов или GPU.
- **Утечка системного промпта** — не храните в нём секреты.

**Меры защиты:**
- **Наименьшие привилегии** для агентов и инструментов: read-only по умолчанию, отдельные сервисные учётки с узкими правами, отсутствие доступа к проду.
- **Human-in-the-loop**: подтверждение человеком любых изменяющих действий.
- **Изоляция** выполнения кода (sandbox, отдельные контейнеры без сети и секретов).
- **Guardrails** на входе и выходе: классификаторы вредоносных промптов, Llama Guard, NeMo Guardrails, маскирование PII и секретов (Presidio), DLP в шлюзе.
- Обработка вывода модели как **недоверенного ввода**: валидация, экранирование, структурированный вывод по схеме.
- Разграничение доступа к данным в RAG по правам пользователя.
- Лимиты токенов и запросов, бюджеты.
- Логирование и аудит всех запросов и действий агентов, red teaming перед запуском.

## Q: Что такое AI-агенты и MCP? Как безопасно дать агенту доступ к инфраструктуре?
level: senior
type: theory
freq: 2
tags: агенты, mcp

**AI-агент** — LLM, которая работает в цикле: получает задачу → планирует → **вызывает инструменты** (выполнить команду, запрос к API, прочитать файл) → анализирует результат → решает, что делать дальше, пока задача не решена. Примеры: агентные ассистенты для кода (Claude Code, Codex, Cursor agent), агенты для траблшутинга Kubernetes, ChatOps-боты, автоматический разбор алертов.

**MCP (Model Context Protocol)** — открытый протокол (предложен Anthropic в 2024 году, сейчас поддерживается большинством ИИ-инструментов) для подключения к LLM-приложениям **инструментов и источников данных** единым способом:
- **MCP-сервер** предоставляет инструменты (tools), ресурсы и шаблоны промптов: например, сервер для Kubernetes, GitLab, Jira, Confluence, PostgreSQL, Prometheus, Grafana;
- **MCP-клиент** (ассистент, IDE, агент) подключается к серверам и даёт модели вызывать их инструменты;
- транспорт — stdio (локально) или HTTP (удалённые серверы с OAuth-авторизацией).

Аналогия: MCP для ИИ — как USB для периферии или LSP для редакторов кода. Один сервер для GitLab работает с любым совместимым клиентом.

**Роль DevOps-инженера:** разворачивать и эксплуатировать внутренние MCP-серверы, управлять их доступом, учётными данными и аудитом, строить агентные сценарии (разбор алерта: собрать логи, метрики, события → гипотеза → предложение исправления в MR).

**Как безопасно дать агенту доступ к инфраструктуре:**
1. **Read-only по умолчанию**: чтение логов, метрик, `kubectl get/describe` — без права изменений.
2. **Отдельная идентичность** агента с минимальными правами (свой ServiceAccount, роль IAM), короткоживущие токены, никаких личных учётных данных инженера.
3. **Изменения — через существующий процесс**: агент создаёт MR / план, а применяет его человек или конвейер с ревью, а не агент напрямую в прод.
4. **Подтверждение человеком** для любого изменяющего действия, списки разрешённых команд.
5. **Изоляция окружений**: сначала dev и staging, агентам — запрет на прод или только чтение.
6. **Аудит**: логирование всех вызовов инструментов и их результатов, возможность разобрать действия агента как инцидент.
7. **Защита от prompt injection**: данные из логов, тикетов и веб-страниц считаются недоверенными; доверенные MCP-серверы — только из проверенного каталога, с закреплёнными версиями.
8. **Лимиты**: таймауты, ограничение числа шагов и стоимости, kill switch.

## Q: Чем MLOps отличается от DevOps? Какие инструменты используются?
level: middle
type: theory
freq: 2
tags: mlops, ml

**MLOps** — применение практик DevOps к жизненному циклу моделей машинного обучения. Отличие в том, что результат зависит не только от **кода**, но и от **данных** и **модели**, и все три нужно версионировать и воспроизводить.

**Жизненный цикл ML:**
```
данные → подготовка и признаки → обучение и эксперименты → оценка → реестр моделей
      → развёртывание (инференс) → мониторинг качества и дрейфа → переобучение
```

**Что добавляется по сравнению с DevOps:**
- **Версионирование данных и моделей**: DVC, lakeFS, **MLflow Model Registry**, Weights & Biases.
- **Отслеживание экспериментов**: параметры, метрики, артефакты (MLflow, W&B).
- **Feature store** — единое хранилище признаков для обучения и онлайн-инференса (Feast).
- **Конвейеры обучения** (pipelines): Kubeflow Pipelines, Airflow, Argo Workflows, Prefect, Metaflow.
- **CI/CD для моделей (CT — continuous training)**: автоматическое переобучение и проверка модели перед выкаткой (качество не хуже текущей), канареечный и shadow-деплой моделей.
- **Сервинг**: KServe, Seldon, BentoML, Triton, Ray Serve, для LLM — vLLM.
- **Мониторинг ML-специфики**: **дрейф данных** (входные данные стали отличаться от обучающих), деградация качества предсказаний, а не только латентность и ошибки (Evidently, WhyLabs).
- **Инфраструктура**: GPU, распределённое обучение (Ray, Kubeflow Training Operator), большие хранилища данных.

**LLMOps** — частный случай для больших языковых моделей: обычно не обучаем модель с нуля, а **выбираем и адаптируем** готовую. В фокусе управление промптами (версионирование, A/B), RAG, оценка качества ответов (evals), guardrails, стоимость токенов, LLM-шлюз.

**Роль DevOps-инженера в ML-команде:** платформа (Kubernetes с GPU, хранилища, реестры), CI/CD для кода и моделей, инфраструктура обучения и инференса, наблюдаемость, безопасность и стоимость. Сами модели обучают ML-инженеры и data scientists.

## Q: Как организовать наблюдаемость LLM-приложений? Какие метрики важны?
level: senior
type: practice
freq: 2
tags: observability, llm, langfuse

Помимо обычных метрик сервиса (RED) у LLM-приложений есть свои особенности: ответы недетерминированы, ошибки бывают «тихими» (уверенный неправильный ответ), стоимость зависит от каждого запроса.

**Метрики:**
- **Латентность**: TTFT (первый токен), полное время ответа, время каждого этапа (поиск в RAG, reranking, вызовы инструментов, генерация).
- **Токены**: входные и выходные на запрос, по моделям, командам, сценариям; попадания в кеш.
- **Стоимость**: деньги в разрезе команд, фич и пользователей, прогноз до конца месяца, аномалии.
- **Ошибки**: ошибки провайдера, превышение лимитов (429), таймауты, срабатывания фолбэков, отказы guardrails, невалидный структурированный вывод.
- **Для self-hosted**: утилизация и память GPU, очередь запросов, KV-cache usage, throughput.
- **Качество**: оценки пользователей (лайк/дизлайк), доля «не знаю» в ответах, результаты автоматических оценок.

**Трейсинг** — главный инструмент отладки: трейс содержит весь путь запроса — промпт, найденные документы, вызовы инструментов, ответы модели, токены и время каждого шага. Стандарт — **OpenTelemetry semantic conventions for GenAI**. Инструменты: **Langfuse** (open source, self-hosted), Arize Phoenix, Helicone, LangSmith, OpenLLMetry; трейсы можно отправлять и в обычные бэкенды (Tempo, Jaeger), а также получать из LLM-шлюза.

**Оценка качества (evals)** — аналог тестов:
- эталонный набор вопросов с ожидаемыми ответами, прогон в CI при изменении промпта, модели или RAG-настроек (регрессия качества = красный пайплайн);
- **LLM-as-a-judge** — оценка ответов другой моделью по критериям, с выборочной проверкой человеком;
- онлайн-оценка части продакшен-трафика.

**Особенности хранения:** промпты и ответы могут содержать персональные данные и секреты. Нужны маскирование, ограниченный ретеншн, контроль доступа к логам и трейсам, соответствие 152-ФЗ / GDPR.

## Q: Как контролировать и снижать стоимость использования LLM?
level: senior
type: scenario
freq: 2
tags: стоимость, finops, llm

**1. Видимость:** учёт токенов и денег по командам, сервисам и фичам через LLM-шлюз, бюджеты и алерты, дашборды стоимости. Без этого затраты незаметно растут.

**2. Подходящая модель для задачи:**
- **маршрутизация**: простые задачи (классификация, извлечение данных, короткие ответы) — маленькая и дешёвая модель, сложные рассуждения — большая; разница в цене между ними может быть в десятки раз;
- проверять на evals, хватает ли более дешёвой модели.

**3. Меньше токенов:**
- короткие и точные системные промпты, ограничение истории диалога (суммаризация старых сообщений);
- в RAG — меньше, но более релевантных фрагментов (reranking);
- ограничение длины ответа (`max_tokens`), структурированный вывод вместо многословного текста.

**4. Кеширование:**
- **prompt caching** у провайдеров — повторяющийся префикс (системный промпт, документы) оплачивается со значительной скидкой;
- кеш ответов на одинаковые запросы, семантический кеш (с осторожностью: риск вернуть неподходящий ответ).

**5. Режимы оплаты:** **batch API** для задач, не требующих мгновенного ответа (обработка документов, ночная разметка), обычно заметно дешевле; резервирование ёмкости при стабильном объёме.

**6. Self-hosted:**
- считать **точку окупаемости**: собственные GPU выгодны при высокой и стабильной загрузке; простаивающий GPU — чистые потери;
- максимизировать загрузку: continuous batching, квантизация, разделение GPU (MIG) для небольших моделей, scale to zero для редко используемых моделей, spot-инстансы для batch-задач;
- правильный размер модели: дистиллированная или дообученная маленькая модель часто справляется с узкой задачей не хуже большой.

**7. Защита от злоупотреблений:** лимиты на пользователя и ключ, ограничение размера входа, обнаружение аномального потребления (зацикленный агент может сжечь бюджет за час).

## Q: Что такое AIOps? Как ИИ применяется в эксплуатации и мониторинге?
level: middle
type: theory
freq: 2
tags: aiops, мониторинг, инциденты

**AIOps** — применение машинного обучения и LLM для автоматизации эксплуатации: обработки огромного потока метрик, логов, алертов и инцидентов, с которым люди уже не справляются вручную.

**Классические ML-задачи:**
- **Обнаружение аномалий** в метриках с учётом сезонности (трафик ночью и днём, выходные) вместо статических порогов;
- **корреляция и дедупликация алертов**: сотня алертов от одной первопричины объединяется в один инцидент;
- **прогнозирование**: заполнение дисков, исчерпание ёмкости, capacity planning;
- **поиск первопричины**: что изменилось перед инцидентом (деплои, конфигурации), какие сервисы затронуты по графу зависимостей;
- кластеризация логов по шаблонам, выявление новых типов ошибок.

**Возможности LLM:**
- **суммаризация инцидента** для дежурного и стейкхолдеров: что происходит, что уже проверено;
- **агент-помощник дежурного**: по алерту сам собирает логи, метрики, события Kubernetes и последние деплои, предлагает гипотезы и подходящий runbook;
- **черновики постмортемов** из хронологии в чате инцидента;
- **запросы на естественном языке**: «покажи p99 латентности сервиса оплаты за сутки» → PromQL/LogQL/SQL;
- автоматизация типовых действий по runbook (с подтверждением человека).

**Инструменты:** встроенные возможности платформ мониторинга (Datadog, Dynatrace, New Relic, Grafana, Elastic), incident.io, PagerDuty, собственные агенты на базе LLM + MCP-серверов для Prometheus, Loki, Kubernetes и тикет-системы.

**Ограничения и здравый смысл:**
- мусор на входе → мусор на выходе: без качественной телеметрии, единых меток и связи сигналов (trace_id) ИИ не поможет;
- ИИ даёт **гипотезы**, а не истину: решения о действиях в проде остаются за людьми;
- ложные срабатывания детекторов аномалий тоже вызывают усталость от алертов;
- сначала наведите порядок в базовом мониторинге и алертинге (SLO, RED/USE, runbook'и), потом добавляйте ИИ.
