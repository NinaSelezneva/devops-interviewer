# Ключевые концепции

**Мониторинг** отвечает на известные вопросы («жив ли сервис, сколько ошибок?»). **Observability** — свойство системы, позволяющее по внешним сигналам ответить на **новые, заранее неизвестные** вопросы («почему медленно только у пользователей из этого региона на iOS?»).

### Три (четыре) сигнала
- **Метрики** — числовые временные ряды, дёшево хранить, агрегаты, алерты. Prometheus, VictoriaMetrics, Mimir.
- **Логи** — дискретные события с контекстом. Loki, ELK/OpenSearch, ClickHouse.
- **Трейсы** — путь запроса через сервисы (spans). Jaeger, Tempo, Zipkin.
- **Профили** — continuous profiling (Pyroscope, Parca).

Связь между ними: exemplars (метрика → трейс), trace_id в логах. Стандарт сбора — **OpenTelemetry**.

### Методологии
- **USE** (для ресурсов): Utilization, Saturation, Errors.
- **RED** (для сервисов): Rate, Errors, Duration.
- **Четыре золотых сигнала** (Google SRE): Latency, Traffic, Errors, Saturation.

### SLI / SLO / SLA
- **SLI** — измеряемый показатель: доля успешных запросов, доля запросов быстрее 300 мс.
- **SLO** — цель для SLI: 99.9% за 30 дней.
- **SLA** — договорное обязательство с последствиями (обычно мягче SLO).
- **Error budget** = 100% − SLO — сколько ненадёжности можно «потратить» на релизы и эксперименты.

## Q: Как устроен Prometheus? Pull vs Push модель.
level: middle
type: theory
freq: 3
tags: prometheus

Компоненты:
- **Prometheus server**: обнаружение целей (service discovery: Kubernetes, Consul, файлы), **scrape** эндпоинтов `/metrics` по HTTP с интервалом, хранение в локальной TSDB (блоки по 2 часа, WAL), вычисление recording и alerting rules, PromQL.
- **Exporters**: node_exporter, blackbox_exporter (пробы HTTP/TCP/ICMP), postgres_exporter, kube-state-metrics.
- **Alertmanager**: группировка, дедупликация, подавление (inhibition), тишина (silences), маршрутизация в Slack/PagerDuty/Telegram.
- **Pushgateway** — для короткоживущих batch-задач (не для обычных сервисов).

**Pull-модель** плюсы: Prometheus сам знает, какие цели должны существовать (`up == 0` — цель недоступна), легко отлаживать (открыл `/metrics` в браузере), нагрузку контролирует сервер. Минусы: цели должны быть доступны по сети, сложнее за NAT/в эфемерных задачах.

**Push** (StatsD, OTLP, Graphite, remote_write агентов) удобнее для короткоживущих задач и сложных сетевых топологий.

Ограничения Prometheus: один узел, локальное хранение, нет встроенного HA и долгосрочного хранения → **Thanos, Cortex/Mimir, VictoriaMetrics** (remote_write, глобальный запрос, дедупликация HA-пар, хранение в объектном хранилище).

## Q: Какие типы метрик есть в Prometheus? Объясните rate и histogram_quantile.
level: senior
type: practice
freq: 3
tags: promql

Типы:
- **Counter** — только растёт (сбрасывается при рестарте): число запросов, ошибок. Смотреть всегда через `rate()`/`increase()`.
- **Gauge** — может расти и падать: память, температура, длина очереди.
- **Histogram** — распределение по корзинам (`_bucket{le="0.1"}`), плюс `_sum` и `_count`. Квантили считаются на сервере и **агрегируются** между инстансами. Native histograms — новая эффективная реализация.
- **Summary** — квантили считаются на клиенте; дёшево, но **нельзя агрегировать** между инстансами.

PromQL:
```promql
# RPS по сервису
sum by (service) (rate(http_requests_total[5m]))

# Доля ошибок 5xx
sum(rate(http_requests_total{code=~"5.."}[5m]))
  / sum(rate(http_requests_total[5m]))

# p99 латентности
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m])))
```

- `rate()` — средняя скорость роста в секунду за окно, учитывает сбросы счётчика. Окно должно быть ≥ 4× scrape interval.
- `irate()` — по двум последним точкам; для «живых» графиков, не для алертов.
- `histogram_quantile` — интерполяция внутри корзины: точность зависит от выбора границ бакетов.
- Правило: сначала `rate`, потом `sum` (не наоборот).

## Q: Что такое кардинальность метрик и почему она важна?
level: senior
type: theory
freq: 3
tags: prometheus, масштабирование

**Кардинальность** — количество уникальных временных рядов = произведение уникальных значений всех лейблов метрики. Каждый ряд занимает память в Prometheus (head block) и место на диске.

Пример взрыва: `http_requests_total{user_id="...", path="/order/12345"}` — миллионы рядов, Prometheus потребляет десятки гигабайт памяти и падает по OOM.

Правила:
- Не использовать в лейблах **неограниченные значения**: user_id, email, полный URL с ID, request_id, timestamp. Их место — в логах и трейсах.
- Нормализовать пути (`/order/:id`).
- Осторожно с гистограммами: каждый бакет — отдельный ряд × все остальные лейблы.

Диагностика: страница TSDB Status в UI Prometheus, `topk(10, count by (__name__)({__name__=~".+"}))`, `prometheus_tsdb_head_series`. Защита: `sample_limit` и `label_limit` в scrape config, `metric_relabel_configs` для удаления лейблов, лимиты в Mimir/VictoriaMetrics.

## Q: Как правильно строить алертинг? Как бороться с alert fatigue?
level: senior
type: practice
freq: 3
tags: алертинг, slo

Принципы:
- **Алертить на симптомы, а не на причины**: «пользователи получают ошибки / выросла латентность» (нарушение SLO), а не «CPU 80%». Высокий CPU без влияния на пользователя — не повод будить человека.
- Каждый **пейджинговый алерт** должен требовать **немедленного действия человека**. Остальное — тикеты или дашборды.
- **Runbook** в каждом алерте: что значит, как проверить, как исправить.
- Severity: critical (будить ночью) / warning (рабочее время).
- `for:` — избегать флапов от кратковременных пиков.
- Группировка и **inhibition** в Alertmanager: при недоступности дата-центра не слать сотню алертов на каждый сервис.

**SLO-алерты по burn rate** (Google SRE Workbook): сравнивать скорость сжигания error budget с допустимой, на нескольких окнах:
- быстрое сжигание (burn rate 14.4 за 1 ч и 5 мин) → пейджинг: при такой скорости бюджет на 30 дней сгорит за ~2 дня;
- медленное (burn rate 1–6 за 6 ч–3 дня) → тикет.
Это даёт и чувствительность, и мало ложных срабатываний.

Борьба с усталостью: регулярный ревью алертов (сколько сработало, сколько требовало действий), удаление шумных, ответственность владельцев сервисов за свои алерты, метрики on-call нагрузки.

## Q: Как определить SLI и SLO для сервиса? Что делать при исчерпании error budget?
level: senior
type: design
freq: 3
tags: slo, sre

1. **Определить пользовательские пути** (critical user journeys): открыть каталог, оформить заказ.
2. **Выбрать SLI** — отношение «хороших событий» к «всем событиям», измеряемое как можно ближе к пользователю (балансировщик, а лучше — RUM/синтетика):
   - availability: доля запросов без 5xx;
   - latency: доля запросов быстрее 300 мс (а не «средняя латентность»);
   - freshness/корректность для конвейеров данных.
3. **Установить SLO** исходя из потребностей бизнеса и исторических данных: 99.9% за скользящие 28–30 дней. Не 100% — это недостижимо и бесконечно дорого, а пользователь не отличит 99.99% от 100% из-за собственного интернета.
4. **Согласовать error budget policy** с продуктом заранее.

При исчерпании бюджета (по политике):
- заморозка фич-релизов, допускаются только исправления надёжности и безопасности;
- приоритет задачам из постмортемов;
- более строгие проверки релизов.

Если бюджет постоянно не расходуется — можно ускорять релизы или SLO слишком мягкий/слишком строгий. Инструменты: Sloth, Pyrra, OpenSLO, Grafana SLO.

## Q: Как организовать централизованное логирование? ELK vs Loki.
level: senior
type: design
freq: 2
tags: логирование

Архитектура: приложения пишут **структурированные логи (JSON) в stdout** → агент на ноде (Fluent Bit, Vector, Promtail/Alloy, Filebeat) собирает, обогащает метаданными (pod, namespace, node), фильтрует → буфер (Kafka при больших объёмах) → хранилище → интерфейс (Kibana, Grafana).

**ELK/OpenSearch**: полнотекстовый **индекс по всему содержимому** — мощный поиск и аналитика, но дорого по CPU/RAM/диску, сложная эксплуатация (шарды, ILM, маппинги, heap).

**Loki**: индексирует **только лейблы**, содержимое хранится сжатыми чанками в объектном хранилище; поиск — перебор по отобранным потокам (LogQL, похож на PromQL). Значительно дешевле, проще, хорошо интегрируется с Grafana и метриками. Минус — медленный полнотекстовый поиск по большим диапазонам, нельзя высокую кардинальность лейблов.

Также: ClickHouse-based (SigNoz, Uptrace, свои решения) — быстрая аналитика по огромным объёмам.

Практики: единый формат и поля (trace_id, request_id, user_id в теле, а не в лейблах), уровни логирования, сэмплирование debug-логов, маскирование PII и секретов, ретеншн по классам (аудит дольше), алерты на лог-паттерны с осторожностью.

## Q: Что такое distributed tracing и OpenTelemetry?
level: senior
type: theory
freq: 2
tags: трейсинг, opentelemetry

**Трейс** — дерево **спанов**, описывающее путь одного запроса через сервисы; спан — операция с началом, длительностью, атрибутами и статусом. Контекст (trace_id, span_id) передаётся между сервисами в заголовках (W3C `traceparent`).

Что даёт: где именно тратится время в цепочке из 10 сервисов, какой вызов падает, N+1 запросы к БД, карта зависимостей.

**OpenTelemetry** — вендор-нейтральный стандарт CNCF:
- API и SDK для языков, **автоинструментация** (Java-агент, Python, .NET, eBPF-based);
- протокол **OTLP** для метрик, логов и трейсов;
- **OTel Collector**: receivers → processors (батчинг, фильтрация, tail sampling, обогащение k8s-атрибутами) → exporters в любой бэкенд (Tempo, Jaeger, Datadog). Позволяет сменить бэкенд без изменения кода.

**Сэмплирование**: head-based (решение в начале — дешево, но можно упустить ошибки) vs **tail-based** (решение после завершения трейса в коллекторе — сохраняем все ошибки и медленные запросы, но нужно буферизовать).

## Q: Как мониторить сам мониторинг? Что если Prometheus упал?
level: senior
type: practice
freq: 1
tags: надёжность, мониторинг

- **Dead man's switch / Watchdog**: всегда активный алерт (`vector(1)`), который отправляется во внешний сервис (Healthchecks.io, PagerDuty heartbeat, Opsgenie). Если алерты перестали приходить — внешний сервис поднимает тревогу.
- **HA-пары Prometheus**: две реплики собирают одни и те же цели, Alertmanager в кластере (gossip) дедуплицирует алерты.
- **Мета-мониторинг**: отдельный Prometheus мониторит основной (`up`, `prometheus_rule_evaluation_failures_total`, длительность scrape, `prometheus_notifications_dropped_total`, заполненность диска, кардинальность).
- **Внешняя синтетика** (blackbox exporter из другого региона, внешние uptime-сервисы) — проверка с точки зрения пользователя, независимая от инфраструктуры.
- Мониторинг расположен **отдельно** от того, что мониторит (другой кластер/аккаунт), иначе при аварии пропадёт одновременно.

## Q: Что такое четыре золотых сигнала? Чем они отличаются от RED и USE? Какие метрики собирать для приложения?
level: middle
type: theory
freq: 3
tags: метрики, golden-signals, red, use

**Четыре золотых сигнала** (Google SRE Book) — минимальный набор метрик для любого сервиса, обращённого к пользователю:

| Сигнал | Что это | Пример метрики |
|---|---|---|
| **Latency** | время обработки запросов; **успешные и ошибочные считать раздельно** (быстрая ошибка 500 занижает среднее) | p50/p95/p99 `http_request_duration_seconds` |
| **Traffic** | нагрузка на систему | RPS, сообщений в секунду, одновременных сессий |
| **Errors** | частота ошибок: явные (5xx), неявные (200 с неверным содержимым), по политике (ответ дольше 1 с — ошибка) | доля 5xx от всех запросов |
| **Saturation** | насколько «заполнен» сервис — утилизация самого ограниченного ресурса и очереди | CPU, память, пул соединений к БД, длина очереди, потоки |

Насыщение часто **опережающий** индикатор: латентность начинает расти, когда утилизация приближается к 100%.

**RED** (Tom Wilkie) — для каждого **сервиса/эндпоинта**, взгляд «снаружи», со стороны запросов:
- **R**ate — количество запросов в секунду;
- **E**rrors — количество/доля ошибочных запросов;
- **D**uration — распределение времени ответа (гистограмма).

**USE** (Brendan Gregg) — для каждого **ресурса** (CPU, память, диск, сеть, пулы):
- **U**tilization — процент времени, когда ресурс занят;
- **S**aturation — очередь работы, которую ресурс не успевает обработать (run queue, iowait, swap);
- **E**rrors — ошибки ресурса (ошибки диска, сетевые дропы).

Как их сочетать: **RED для сервисов** (что видят пользователи) + **USE для инфраструктуры** (почему это происходит). Золотые сигналы ≈ RED + Saturation.

**Лучшие практики метрик приложения:**
- Инструментировать RED на входе (HTTP/gRPC middleware) и на **каждом исходящем вызове** (БД, кеш, внешние API) — так видно, какая зависимость тормозит.
- Латентность — **гистограммой**, а не средним; разумные бакеты под ваш SLO.
- Лейблы низкой кардинальности: `service`, `route` (шаблон пути, а не URL с ID), `method`, `status_code` или класс `2xx/5xx`.
- Метрики насыщения рантайма: пулы соединений, очереди, потоки/горутины, GC-паузы, heap.
- **Бизнес-метрики**: заказы, платежи, регистрации — часто первыми показывают проблему, которую технические метрики не видят.
- Метрики версии сборки (`build_info{version=...}`) — чтобы связывать изменения с деплоями.
- Дашборды по иерархии: обзор сервиса (RED + SLO) → зависимости → ресурсы (USE).
- Алерты — на симптомы (нарушение SLO по ошибкам и латентности), а метрики насыщения — для диагностики и capacity planning.

## Q: Расскажите, как у вас был организован сбор метрик и логов. Как работает Filebeat?
level: senior
type: practice
freq: 3
tags: метрики, логирование, filebeat, опыт

Это вопрос **про ваш опыт**: интервьюер ждёт связной рассказ об архитектуре, причинах выбора, масштабе и проблемах. Структура хорошего ответа:

1. **Масштаб**: сколько сервисов/нод, объём метрик (активных рядов) и логов (ГБ/ТБ в сутки), ретеншн.
2. **Метрики**: путь от источника до алерта.
3. **Логи**: путь от приложения до поиска.
4. **Проблемы, с которыми столкнулись, и как решили** — самое ценное.
5. **Что бы улучшили сейчас.**

**Пример: метрики**
- Приложения отдают `/metrics` (клиентские библиотеки Prometheus или OpenTelemetry SDK), инфраструктура — экспортеры: node_exporter, kube-state-metrics, cAdvisor (через kubelet), postgres/redis/nginx exporters, blackbox_exporter для проверок снаружи.
- В Kubernetes — **Prometheus Operator** (kube-prometheus-stack): цели описываются `ServiceMonitor`/`PodMonitor`, правила — `PrometheusRule` в репозитории сервиса.
- HA-пара Prometheus → `remote_write` в долговременное хранилище (**VictoriaMetrics**/Thanos/Mimir) с ретеншном 13 месяцев и downsampling.
- **Alertmanager** → маршрутизация по командам (лейбл `team`) в Slack/Telegram и PagerDuty/дежурства для critical.
- **Grafana** с дашбордами как код (JSON в Git или Grafonnet), SLO-дашборды.

**Пример: логи**
- Приложения пишут **JSON в stdout**, контейнерный рантайм складывает их в `/var/log/containers/*.log` на ноде.
- **Filebeat** (DaemonSet) читает файлы, добавляет метаданные Kubernetes, отправляет в **Kafka** (буфер на пики и при недоступности хранилища) → **Logstash** (парсинг, обогащение, маскирование персональных данных) → **Elasticsearch/OpenSearch** с ILM-политиками (hot → warm → delete) → **Kibana**.
- Альтернатива подешевле: Promtail/Grafana Alloy или Vector → **Loki** → Grafana.

**Как работает Filebeat** (лёгкий агент Elastic на Go):
- **Inputs** (раньше prospectors) — что читать: `filestream` (современный, вместо устаревшего `log`), `container`, journald, syslog, TCP/UDP, Kafka.
- Для каждого файла запускается **harvester**: читает файл построчно, отслеживает ротацию по inode и device, держит файл открытым (`close_inactive`, `clean_removed` — иначе удалённые логи продолжают занимать диск).
- **Registry** — позиция чтения (offset) каждого файла хранится на диске (`data/registry`). После рестарта Filebeat продолжает с того же места. Гарантия **at-least-once**: возможны дубли, потери — нет (пока файл не удалили).
- **Processors** — обработка на агенте: `add_kubernetes_metadata`, `add_host_metadata`, `decode_json_fields`, `drop_event`, `dissect`; **multiline** — склейка многострочных стектрейсов (Java) в одно событие.
- **Autodiscover** (Kubernetes/Docker provider) — динамически настраивает inputs по аннотациям подов (`co.elastic.logs/...`).
- **Modules** — готовые конфиги и ingest-пайплайны для nginx, PostgreSQL, system и т.д.
- **Outputs** — Elasticsearch, Logstash, Kafka, Redis (одновременно только один). Внутренняя очередь (в памяти или на диске) и **backpressure**: если получатель тормозит, Filebeat замедляет чтение, а не теряет события.

**Типичные проблемы, которые стоит упомянуть:**
- многострочные логи разбиваются на отдельные события — настройка multiline или JSON-логи;
- взрыв числа полей/маппингов в Elasticsearch от неструктурированных логов — единая схема (ECS), строгие маппинги;
- потеря логов при быстрой ротации или удалении пода — буферизация, достаточный размер логов на ноде;
- стоимость хранения — сэмплирование debug-логов, разные ретеншны по классам, переход на Loki;
- высокая кардинальность метрик — лимиты и relabeling;
- связь сигналов: `trace_id` в логах, exemplars в метриках, переходы между ними в Grafana.

## Q: Что такое exporter? Как добавить новый сервис в мониторинг Prometheus?
level: middle
type: practice
freq: 3
tags: prometheus, exporter

**Exporter** — программа, которая собирает метрики из системы, не умеющей отдавать их в формате Prometheus, и публикует их на HTTP-эндпоинте `/metrics`:
- **node_exporter** (порт 9100) — CPU, память, диски, сеть хоста;
- **blackbox_exporter** — проверки «снаружи»: HTTP-коды, TLS-сертификаты, TCP, ICMP, DNS;
- **postgres_exporter**, **mysqld_exporter**, **redis_exporter**, **nginx-prometheus-exporter**, **kafka_exporter**;
- **kube-state-metrics** — состояние объектов Kubernetes; **cAdvisor** — метрики контейнеров.

Собственные приложения инструментируются **клиентской библиотекой** Prometheus (или OpenTelemetry) и отдают `/metrics` сами.

Формат метрик (text exposition):
```
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",code="200"} 1027
```

**Добавить цель — статически** (`prometheus.yml`):
```yaml
scrape_configs:
  - job_name: node
    static_configs:
      - targets: ['10.0.1.10:9100', '10.0.1.11:9100']
        labels: { env: prod }
  - job_name: api
    metrics_path: /metrics
    scrape_interval: 15s
    static_configs:
      - targets: ['api.internal:8080']
```
Применить: `curl -X POST http://prometheus:9090/-/reload` (при `--web.enable-lifecycle`) или SIGHUP. Проверка — страница **Status → Targets** (состояние UP/DOWN и последняя ошибка) и запрос `up{job="api"}`.

**Через service discovery:** `kubernetes_sd_configs`, `consul_sd_configs`, `ec2_sd_configs`, `file_sd_configs` + `relabel_configs`, чтобы выбрать нужные цели и сформировать метки.

**В Kubernetes с Prometheus Operator** — ресурс `ServiceMonitor`:
```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: api
  labels: { release: kube-prometheus-stack }   # должна совпадать с serviceMonitorSelector
spec:
  selector: { matchLabels: { app: api } }       # метки Service
  endpoints:
  - port: http-metrics                           # ИМЯ порта в Service
    interval: 30s
```
Частые причины, почему цель не появилась: не совпали метки ServiceMonitor с селектором Prometheus, указан номер порта вместо имени, NetworkPolicy закрывает доступ, неверный `metrics_path`.

## Q: Как создать дашборд в Grafana и настроить простой алерт?
level: middle
type: practice
freq: 2
tags: grafana, алертинг

**Grafana** — визуализация и алертинг поверх разных источников данных (**data sources**): Prometheus, Loki, Elasticsearch, PostgreSQL, ClickHouse, облачные мониторинги.

**Дашборд:**
1. Добавить data source (URL Prometheus).
2. Создать панель (**panel**), выбрать визуализацию: Time series, Stat, Gauge, Table, Heatmap (для гистограмм латентности), Logs.
3. Написать запрос PromQL, например RPS по статусам: `sum by (code) (rate(http_requests_total{job="api"}[5m]))`.
4. Настроить единицы измерения (req/s, ms, %, bytes), пороги цветов, легенду (`{{code}}`).
5. **Переменные** дашборда (`$env`, `$service`, `$instance`) — выпадающие списки, один дашборд для всех сервисов: `label_values(up, job)`.
6. Сохранить и экспортировать в JSON. Хранить в Git и разворачивать через **provisioning** (файлы или ConfigMap с sidecar в Kubernetes), Terraform-провайдер или Grafonnet, а не только кликами в UI.

Не надо изобретать с нуля: на grafana.com есть готовые дашборды (Node Exporter Full и др.), kube-prometheus-stack ставит набор дашбордов для Kubernetes.

**Хороший дашборд сервиса:** сверху — главное (RED-метрики и SLO), ниже — зависимости и ресурсы. Не больше 10–15 панелей, понятные названия и описания.

**Алерт в Prometheus** (правило в отдельном файле, отправка через Alertmanager):
```yaml
groups:
- name: api
  rules:
  - alert: ApiHighErrorRate
    expr: |
      sum(rate(http_requests_total{job="api",code=~"5.."}[5m]))
        / sum(rate(http_requests_total{job="api"}[5m])) > 0.05
    for: 10m                         # условие должно держаться 10 минут
    labels: { severity: critical, team: backend }
    annotations:
      summary: "API: больше 5% ошибок"
      runbook_url: https://wiki.example.com/runbooks/api-errors
  - alert: InstanceDown
    expr: up == 0
    for: 5m
    labels: { severity: warning }
```
Alertmanager маршрутизирует алерты по меткам (`team`, `severity`) в Slack, Telegram, почту, PagerDuty, группирует их и позволяет ставить silence на время работ.

**Grafana Alerting** — альтернатива: правила создаются в Grafana поверх любых источников (в том числе логов), есть contact points и notification policies. Удобно, когда источники не только Prometheus.
