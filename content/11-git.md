# Ключевые концепции

### Объектная модель
Git — **content-addressable** хранилище. Четыре типа объектов, адресуемых хешем (SHA-1, переход на SHA-256):
- **blob** — содержимое файла;
- **tree** — каталог: имена → blob/tree;
- **commit** — ссылка на tree, родителей, автора, сообщение;
- **tag** (annotated).

**Ветка** — просто файл-указатель на коммит (`refs/heads/main`). **HEAD** — указатель на текущую ветку (или коммит в detached HEAD).

### Три области
Working directory → **index (staging area)** → репозиторий (`.git/objects`).

### Команды, которые стоит уметь объяснить
`rebase -i`, `cherry-pick`, `revert` vs `reset` (soft/mixed/hard), `reflog`, `bisect`, `stash`, `merge --no-ff`, `log --graph`, `blame`, `worktree`, сабмодули vs subtree.

## Q: Чем merge отличается от rebase? Когда что использовать?
level: middle
type: theory
freq: 3
tags: merge, rebase

- **merge** создаёт **merge-коммит** с двумя родителями, сохраняя историю как она была. Безопасно для общих веток, история «нелинейная». Fast-forward, если целевая ветка не ушла вперёд.
- **rebase** **переписывает** коммиты ветки поверх новой базы — новые хеши, линейная история, легче читать и делать `bisect`.

Золотое правило: **не делать rebase опубликованных веток**, с которыми работают другие, — у коллег разойдётся история. Если всё же нужно для своей ветки в MR — `git push --force-with-lease` (не перезапишет чужие коммиты, в отличие от `--force`).

Практика:
- обновлять свою feature-ветку от main через rebase;
- `rebase -i` для приведения в порядок коммитов перед ревью (squash, fixup, reword);
- в main — merge-коммит или squash merge (политика команды);
- конфликты при rebase решаются по одному коммиту; `git rerere` запоминает решения.

## Q: Сравните GitFlow, GitHub Flow и trunk-based development.
level: senior
type: theory
freq: 3
tags: ветвление

- **GitFlow**: долгоживущие `main` и `develop`, ветки `feature/*`, `release/*`, `hotfix/*`. Подходит для продуктов с версионными релизами (коробочное ПО, мобильные приложения, поддержка нескольких версий). Минусы — сложность, долгие ветки, большие мержи, медленная обратная связь; не сочетается с continuous delivery.
- **GitHub Flow**: одна `main` всегда готова к деплою, короткие feature-ветки и PR, деплой после мержа. Просто, подходит для веб-сервисов.
- **Trunk-based development**: все коммитят в trunk (main) напрямую или через **очень короткоживущие** ветки (часы–день), незавершённые фичи скрыты **feature flags**, релизы с main (возможно, release-ветки для стабилизации). Рекомендуется исследованиями DORA для высокой частоты деплоя. Требует хорошего покрытия тестами и быстрого CI.

Senior-ответ: выбор зависит от модели поставки; для облачных сервисов с CD — trunk-based/GitHub Flow; переход с GitFlow — через сокращение жизни веток и внедрение feature flags.

## Q: Как восстановить «потерянный» коммит или ветку после reset --hard?
level: middle
type: practice
freq: 2
tags: reflog, восстановление

**reflog** записывает каждое перемещение HEAD и веток локально (по умолчанию хранится ~90 дней):

```bash
git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~3
# f4e5d6c HEAD@{1}: commit: важная работа
git branch recovered f4e5d6c   # или git reset --hard HEAD@{1}
```

Если удалена ветка — тот же reflog (`git reflog show --all`) или `git fsck --lost-found` для «висячих» коммитов.

Не восстановятся: изменения, которые **никогда не были закоммичены** или добавлены в индекс (после `reset --hard` или `checkout -- file`). Добавленное в индекс, но не закоммиченное, можно найти как dangling blob через `git fsck`.

## Q: Чем revert отличается от reset? Как отменить изменения в общей ветке?
level: middle
type: theory
freq: 2
tags: revert, reset

- **`git revert <commit>`** создаёт **новый коммит**, отменяющий изменения указанного. История не переписывается — **безопасно для общих веток**. Revert merge-коммита: `git revert -m 1 <merge>` (указать «основного» родителя); повторное вливание той же ветки потом потребует revert самого revert.
- **`git reset`** перемещает указатель ветки:
  - `--soft` — коммиты отменены, изменения остаются в индексе;
  - `--mixed` (по умолчанию) — изменения в рабочей директории, индекс сброшен;
  - `--hard` — изменения удалены.
  Переписывает историю — только для локальных/неопубликованных коммитов.

В общей ветке (main) — всегда `revert`. Это же основа отката в GitOps: `git revert` коммита с новой версией → ArgoCD откатывает деплой.

## Q: В репозиторий закоммитили большой бинарник или секрет. Как удалить его из истории?
level: senior
type: scenario
freq: 2
tags: история, секреты

Для секрета: **сначала отозвать/ротировать** — удаление из истории не отменяет компрометацию.

Переписать историю:
```bash
# git-filter-repo (рекомендуемый инструмент вместо filter-branch)
git filter-repo --path secrets.env --invert-paths
git filter-repo --strip-blobs-bigger-than 50M
# или BFG Repo-Cleaner
bfg --replace-text passwords.txt
```

Затем:
- принудительный push всех веток и тегов;
- **все участники** должны переклонировать репозиторий (иначе старая история вернётся при push);
- на GitHub/GitLab — очистка кешей и ссылок на PR/MR через поддержку или housekeeping, т.к. старые объекты могут оставаться доступными по хешу;
- координация с командой, временная заморозка изменений.

Для больших файлов в будущем — **Git LFS**, `.gitignore`, pre-commit хук с ограничением размера, push rules на сервере.

## Q: Как найти коммит, который внёс баг, среди сотен коммитов?
level: middle
type: practice
freq: 1
tags: bisect

**`git bisect`** — бинарный поиск по истории:
```bash
git bisect start
git bisect bad                 # текущая версия сломана
git bisect good v1.4.0         # эта версия работала
# Git переключает на коммит посередине — проверяем и отмечаем good/bad
git bisect run ./test.sh       # или автоматически скриптом (exit 0 = good)
git bisect reset
```
Для 1000 коммитов нужно ~10 шагов (log₂). Работает лучше при линейной истории и коммитах, каждый из которых собирается (аргумент в пользу атомарных коммитов и rebase/squash).

Также полезны: `git log -S 'строка'` (pickaxe — коммиты, добавившие/удалившие строку), `git log -G regex`, `git blame -w -C` (игнорируя пробелы и отслеживая перемещения кода).
