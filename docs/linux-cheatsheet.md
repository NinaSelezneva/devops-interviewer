# Linux: шпаргалка к собеседованию

Порядок разделов идёт от базы к диагностике: сначала устройство системы, потом процессы, память, диски, права, systemd и в конце разбор задачи «сервер тормозит». Каждый раздел опирается на предыдущие.

> Как учить: сначала прочитайте **жирные определения**, потом команды, потом блоки «💬 На собесе» — это готовые ответы, которые можно проговорить вслух.

---

## 1. Базовая модель: ядро и пространство пользователя

- **Ядро (kernel)** управляет железом, памятью, процессами, сетью и файлами.
- **User space**: все программы (bash, nginx, docker). Напрямую к железу они не обращаются.
- **Системный вызов (syscall)**: через него программа просит ядро что-то сделать (`open`, `read`, `write`, `fork`, `execve`, `kill`).
- **«Всё есть файл»**: устройства (`/dev/sda`), процессы (`/proc/<pid>`), сокеты и пайпы доступны как файлы.

| Каталог | Что там |
|---|---|
| `/etc` | конфиги |
| `/var/log` | логи |
| `/proc` | виртуальная ФС с информацией о процессах и ядре |
| `/sys` | виртуальная ФС с устройствами и драйверами |
| `/dev` | файлы устройств |
| `/tmp` | временные файлы |
| `/home`, `/root` | домашние каталоги |
| `/usr/bin`, `/usr/lib` | программы и библиотеки |

💬 **strace и ltrace:** `strace` показывает системные вызовы (обращения к ядру), `ltrace` показывает вызовы библиотечных функций. `strace -p <PID>` помогает понять, на чём завис процесс.

## 2. Загрузка системы (boot)

Цепочка, которую стоит выучить наизусть:

```
BIOS/UEFI → загрузчик (GRUB) → ядро + initramfs → PID 1 (systemd) → target'ы → сервисы
```

1. **BIOS/UEFI** проверяет железо и находит загрузчик.
2. **GRUB** загружает ядро и initramfs.
3. **initramfs** — временная корневая ФС с драйверами, нужными, чтобы смонтировать настоящий `/`.
4. **Ядро** монтирует `/` и запускает **PID 1**, сейчас это `systemd`.
5. **systemd** доводит систему до цели (`multi-user.target`, `graphical.target`).

## 3. Процессы

**Процесс** — запущенная программа: у него есть PID, родитель (PPID), память, открытые файлы и владелец.

**Как создаётся процесс:** `fork()` делает копию родителя, затем `exec()` заменяет её код новой программой. Когда процесс завершается, родитель забирает его код возврата через `wait()`.

**Состояния** (столбец `STAT` в `ps`):

| Код | Значение |
|---|---|
| `R` | выполняется или ждёт CPU |
| `S` | спит, прерываемо (ждёт событие) |
| `D` | спит **непрерываемо**, обычно ждёт диск или NFS. Убить нельзя даже `kill -9` |
| `Z` | зомби |
| `T` | остановлен |

- **Зомби** — процесс уже завершился, но родитель не вызвал `wait()`. Ресурсов он не ест, только запись в таблице процессов. Убить зомби нельзя: нужно исправить или перезапустить **родителя**.
- **Сирота** — родитель умер раньше потомка. Потомка «усыновляет» PID 1 (или subreaper), и это нормально.

**Сигналы:**

| Сигнал | № | Смысл |
|---|---|---|
| `SIGHUP` | 1 | перечитать конфиг (часто так) |
| `SIGINT` | 2 | Ctrl+C |
| `SIGKILL` | 9 | убить немедленно, перехватить нельзя |
| `SIGTERM` | 15 | вежливая просьба завершиться (по умолчанию в `kill`) |
| `SIGSTOP` / `SIGCONT` | 19 / 18 | пауза / продолжение |

💬 **SIGTERM и SIGKILL:** SIGTERM процесс может обработать: закрыть соединения, сбросить данные на диск. SIGKILL обрабатывает ядро, у процесса нет шанса прибраться. Правильный порядок: сначала TERM, подождать, потом KILL (Docker и Kubernetes делают именно так).

```bash
ps aux | grep nginx        # найти процесс
ps -ef --forest            # дерево процессов
pstree -p
top / htop                 # интерактивный мониторинг
kill -15 <PID>; kill -9 <PID>
pkill -f pattern; killall nginx
nice -n 10 cmd; renice 5 -p <PID>   # приоритет (-20 высший, 19 низший)
```

## 4. Load Average

Три числа в `uptime` и `top` — средняя длина очереди за **1, 5 и 15 минут**: процессы в состоянии **R** (работают или ждут CPU) плюс **D** (ждут ввод-вывод).

- Сравнивать нужно с **числом ядер** (`nproc`). LA = 4 на 4 ядрах означает полную загрузку, на 16 ядрах — запас.
- Высокий LA при низком CPU почти всегда означает **процессы в D, которые ждут диск**. Смотрите `iowait` в `top` и `iostat`.
- Тренд: `1m > 15m` — нагрузка растёт, `1m < 15m` — спадает.

## 5. Память

```bash
free -h
```

- **used** — занято приложениями.
- **buff/cache** — кеш файлов. Ядро отдаёт его приложениям по первому требованию.
- **available** ← **смотреть сюда**: столько реально можно выделить.

💬 **«free показывает, что памяти почти нет»:** Linux заполняет свободную память файловым кешем, потому что пустая RAM ничего не ускоряет. Главная метрика — `available`.

- **Swap** — память на диске. Свопинг сильно замедляет систему (`vmstat`, столбцы `si`/`so`). Kubernetes исторически требует отключать swap, потому что иначе ломается учёт памяти и лимиты.
- **OOM Killer** — когда память кончилась совсем, ядро убивает процесс с наибольшим `oom_score`. Следы искать так: `dmesg -T | grep -i oom`, `journalctl -k`.
- **Виртуальная память:** у каждого процесса своё адресное пространство. `VIRT` — сколько процесс «зарезервировал», `RES` (RSS) — сколько реально лежит в RAM.

## 6. Файловая система, inode, ссылки

**Inode** — запись с **метаданными** файла: права, владелец, размер, время, указатели на блоки данных. **Имени файла в inode нет**: имя хранится в каталоге, а каталог — это таблица «имя → номер inode».

| | Жёсткая ссылка (`ln a b`) | Символическая (`ln -s a b`) |
|---|---|---|
| Что это | ещё одно имя того же inode | отдельный файл с путём внутри |
| Другая ФС | нельзя | можно |
| На каталог | нельзя | можно |
| Удалили оригинал | данные живы | ссылка «битая» |

Данные удаляются, только когда счётчик жёстких ссылок равен 0 **и** файл никто не держит открытым.

**Классика: «No space left on device», а `df` показывает свободное место.**
1. **Кончились inode** (миллионы мелких файлов) → `df -i`.
2. **Файл удалён, но процесс держит его открытым**, и место не освободилось → `lsof +L1` или `lsof | grep deleted`. Решения: перезапустить процесс или сделать `: > /proc/<PID>/fd/<N>`.
3. Место зарезервировано для root (5% на ext4).

💬 **Как безопасно освободить место от огромного лога:** не делайте `rm`, если файл открыт процессом. Обнулите его: `truncate -s 0 app.log` или `: > app.log`. Дальше настройте `logrotate`.

```bash
df -h; df -i                  # место и inode
du -sh /var/* | sort -h       # кто занимает
ncdu /                        # удобный интерактивный du
ls -li                        # номер inode
stat file                     # все метаданные
```

## 7. Права доступа

```
-rwxr-x---  1 alice devs  file
 │└┬┘└┬┘└┬┘
 │ u  g  o     u = владелец, g = группа, o = остальные
 тип: - файл, d каталог, l симлинк
```

`r=4, w=2, x=1` → `chmod 750` = `rwxr-x---`.

- **Для каталога:** `r` — смотреть список, `w` — создавать и удалять файлы, `x` — заходить внутрь.
- **umask** — какие биты убрать у новых файлов. `umask 022` даёт `644` для файлов и `755` для каталогов.

**Специальные биты:**

| Бит | Число | Значение | Пример |
|---|---|---|---|
| **SUID** | 4000 | программа запускается с правами **владельца** файла | `/usr/bin/passwd` |
| **SGID** | 2000 | на файле — права группы; на каталоге — новые файлы наследуют группу | общие папки команд |
| **Sticky** | 1000 | в каталоге удалить файл может только его владелец | `/tmp` (`drwxrwxrwt`) |

```bash
chmod 644 f; chmod u+x f; chown user:group f; chmod -R ...
getfacl / setfacl            # ACL, точечные права сверх ugo
lsattr / chattr +i f         # immutable: даже root не удалит, пока не снимет
```

💬 **«Почему файл не удаляется?»** Нет прав на **каталог** (`w` и `x`), sticky bit, атрибут `chattr +i`, ФС смонтирована только на чтение (`ro`), SELinux/AppArmor, файл занят (на Linux это не мешает удалению, но место не освободится).

**Пользователи:** `/etc/passwd` (учётки), `/etc/shadow` (хеши паролей), `/etc/group`. Команды: `useradd -m -s /bin/bash u`, `usermod -aG sudo u`, `id u`. Sudo-права редактируйте только через `visudo`.

## 8. Файловые дескрипторы

**FD** — номер открытого ресурса в процессе: файла, сокета, пайпа. `0` = stdin, `1` = stdout, `2` = stderr.

- Лимит на процесс: `ulimit -n`, у systemd-сервиса — `LimitNOFILE=`. Общесистемный: `fs.file-max`.
- Если лимит кончился, в логах появится **«Too many open files»**.

```bash
ls /proc/<PID>/fd | wc -l       # сколько FD открыто
cat /proc/<PID>/limits
lsof -p <PID>
```

Перенаправления: `cmd > out 2>&1` (stdout и stderr в файл), `cmd 2>/dev/null`, `cmd | tee file`.

## 9. systemd

**Unit** — объект, которым управляет systemd. Типы: `.service`, `.socket`, `.timer` (замена cron), `.mount`, `.target` (группа юнитов), `.path`, `.slice` (группа cgroup для ресурсов).

Минимальный сервис `/etc/systemd/system/app.service`:

```ini
[Unit]
Description=My App
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=app
ExecStart=/opt/app/bin/app
Restart=on-failure
Environment=PORT=8080
MemoryMax=512M
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload          # после правки unit-файла обязательно!
systemctl enable --now app       # автозапуск + старт
systemctl status app
systemctl restart / reload app
systemctl list-units --failed
systemctl cat app                # итоговый unit
systemctl edit app               # override без правки оригинала
journalctl -u app -f             # логи сервиса в реальном времени
journalctl -u app --since "10 min ago" -p err
journalctl -b                    # с последней загрузки
```

💬 **Типы сервисов:** `simple` (процесс из `ExecStart` и есть сервис), `forking` (демон уходит в фон), `oneshot` (одноразовая задача), `notify` (сервис сам сообщает о готовности).

💬 **Почему сервис не стартует:** забыли `daemon-reload`, неверный путь или права на бинарник, `Type` не соответствует поведению программы, не тот `User`, порт занят, ошибка в конфиге. Начинать всегда с `systemctl status` и `journalctl -u`.

## 10. Логи и cron

- Логи: `/var/log/syslog` или `/var/log/messages`, `/var/log/auth.log`, логи приложений; journald (`journalctl`); ядро — `dmesg -T`.
- Ротация: `logrotate`, конфиги в `/etc/logrotate.d/`.

**Cron:**

```
* * * * *  команда
│ │ │ │ └ день недели (0-7, 0 и 7 = вс)
│ │ │ └── месяц (1-12)
│ │ └──── день месяца (1-31)
│ └────── час (0-23)
└──────── минута (0-59)

*/5 * * * *    каждые 5 минут
0 3 * * 1-5    в 03:00 по будням
```

`crontab -e`, `crontab -l`. **Подвох:** cron запускает команды с минимальным `PATH` и окружением, поэтому в скриптах пишите полные пути и перенаправляйте вывод в лог.

## 11. Диски, LVM, fstab

```bash
lsblk                    # диски и разделы деревом
blkid                    # UUID
fdisk / parted           # разметка
mkfs.ext4 /dev/sdb1      # создать ФС
mount /dev/sdb1 /data
```

**LVM** состоит из трёх уровней: **PV** (физический диск) → **VG** (пул) → **LV** (логический том, на нём ФС). Главный плюс — тома можно расширять на лету.

```bash
pvcreate /dev/sdc
vgextend vg0 /dev/sdc
lvextend -r -L +10G /dev/vg0/data   # -r сразу расширит ФС
# вручную: resize2fs (ext4) / xfs_growfs /mnt (xfs; XFS нельзя уменьшить!)
```

**/etc/fstab** — что монтировать при загрузке. Указывайте **UUID**, а не `/dev/sdX`, потому что имена устройств могут поменяться:

```
UUID=xxxx  /data  ext4  defaults,nofail  0 2
```

Перед перезагрузкой проверьте: `mount -a`. Ошибка в fstab может помешать системе загрузиться (`nofail` страхует).

## 12. /proc, /sys, sysctl

```bash
cat /proc/cpuinfo /proc/meminfo /proc/loadavg
cat /proc/<PID>/status        # память, состояние процесса
cat /proc/<PID>/cmdline; ls -l /proc/<PID>/cwd /proc/<PID>/exe
cat /proc/<PID>/environ | tr '\0' '\n'
```

**sysctl** меняет параметры ядра (`/proc/sys/...`):

```bash
sysctl -a | grep somaxconn
sysctl -w net.core.somaxconn=4096        # до перезагрузки
echo 'net.core.somaxconn=4096' > /etc/sysctl.d/99-tune.conf && sysctl --system  # навсегда
```

Часто спрашивают: `net.core.somaxconn` (очередь входящих соединений), `net.ipv4.ip_local_port_range`, `net.ipv4.tcp_tw_reuse`, `fs.file-max`, `vm.swappiness`, `net.ipv4.ip_forward` (нужен для Docker и Kubernetes).

## 13. Namespaces и cgroups: основа контейнеров

💬 **Контейнер — это обычный процесс Linux**, которому:
- **namespaces** ограничили, **что он видит**;
- **cgroups** ограничили, **сколько ресурсов он может потратить**.

| Namespace | Изолирует |
|---|---|
| `pid` | дерево процессов (внутри свой PID 1) |
| `net` | сетевые интерфейсы, порты, маршруты |
| `mnt` | точки монтирования |
| `uts` | hostname |
| `ipc` | межпроцессное взаимодействие |
| `user` | UID/GID (root внутри ≠ root снаружи) |
| `cgroup` | вид иерархии cgroup |

**cgroups (v2)** ограничивают CPU, память, I/O и число PID. Лимиты в Docker и Kubernetes (`--memory`, `resources.limits`) реализованы именно через cgroups. Если превысить лимит памяти, процесс убьёт OOM внутри cgroup.

```bash
lsns; nsenter -t <PID> -n ip a   # зайти в сетевой namespace процесса
unshare --pid --fork --mount-proc bash
```

## 14. Безопасность: SELinux / AppArmor

- **DAC** — обычные права (`rwx`), владелец сам решает. **MAC** (SELinux, AppArmor) — политика системы, которую нельзя обойти даже root.
- SELinux работает на метках (контекстах) и есть в RHEL; AppArmor работает на профилях путей и есть в Ubuntu.
- Команды: `getenforce`, `setenforce 0` (временно), `ls -Z`, `restorecon -Rv /path`, `ausearch -m avc`.

💬 **«Почему не отключать»:** это последний рубеж защиты. Если сервис взломают, MAC не даст ему выйти за пределы своих файлов. Правильнее найти отказ в логах (`audit.log`) и поправить контекст или политику.

## 18. Главная задача: «Сервер тормозит, что делать?»

Действуйте по порядку: **CPU → память → диск → сеть → приложение**. Это методика USE: для каждого ресурса проверить **U**tilization, **S**aturation, **E**rrors.

**«60 секунд на сервере» (Brendan Gregg):**

```bash
uptime                 # 1. Load average: растёт или падает?
dmesg -T | tail        # 2. ошибки ядра, OOM, проблемы с диском
vmstat 1               # 3. r (очередь CPU), si/so (своп), wa (iowait)
mpstat -P ALL 1        # 4. загрузка каждого ядра (одно ядро на 100%?)
pidstat 1              # 5. какие процессы едят CPU
iostat -xz 1           # 6. диски: %util, await
free -m                # 7. память (смотреть available)
sar -n DEV 1           # 8. сетевой трафик
sar -n TCP,ETCP 1      # 9. TCP-соединения и ретрансмиты
top                    # 10. общая картина
```

**Как читать `top`, строку `%Cpu`:**
- `us` — пользовательский код, `sy` — ядро (много syscall'ов);
- `wa` — **iowait**: CPU ждёт диск, нужно смотреть `iostat`;
- `st` — **steal**: соседи по гипервизору забирают CPU (облако);
- `id` — простой.

**Шаблон ответа на собесе:**
1. Уточнить симптом: что именно медленно, с какого момента, что менялось (деплой?).
2. Посмотреть мониторинг и общую картину (`uptime`, `top`).
3. Пройти ресурсы по USE и найти узкое место.
4. Найти процесс-виновник, затем заглянуть внутрь: `strace -p`, `lsof -p`, логи.
5. Сначала сгладить влияние (перезапуск, перевод трафика), потом искать корневую причину и писать постмортем.

## 19. Быстрые ответы: проверь себя

| Вопрос | Ответ в одну строку |
|---|---|
| Что такое PID 1? | init (systemd); усыновляет сирот и запускает систему |
| Зомби — как убить? | Никак; нужно чинить или перезапустить родителя |
| `kill -9` не убивает процесс | Процесс в состоянии D (ждёт I/O) или уже зомби |
| Где имя файла? | В каталоге, а не в inode |
| Место есть, а записать нельзя | Кончились inode (`df -i`) или удалённый файл держит процесс (`lsof +L1`) |
| Нет памяти по `free` | Смотри `available`, кеш освобождается сам |
| Высокий LA, CPU простаивает | Процессы в D, проблема с диском или NFS |
| Кто слушает порт? | `ss -tulpn` / `lsof -i :PORT` |
| Поменял unit-файл, ничего не изменилось | `systemctl daemon-reload` |
| Контейнер = ? | Процесс + namespaces (видимость) + cgroups (ресурсы) |
| SUID? | Запуск с правами владельца файла (`passwd`) |
| Sticky bit? | В каталоге удаляет только владелец файла (`/tmp`) |
| Hard vs soft link? | Hard — второе имя того же inode; soft — файл с путём |
| Too many open files | Лимит FD: `ulimit -n`, `LimitNOFILE`, `/proc/PID/limits` |
